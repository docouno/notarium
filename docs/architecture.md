# Notarium architecture manifesto

> The result of spike #9, fixed 2026-06-10. This manifesto is the durable output; the underlying research reports are kept outside the repository. The goal is not to design EVERYTHING but to fix the principles by which we grow the backend incrementally. Changes to principles go through discussion, with a reference to the reason.

## Vision

Notarium is a "brain": a tool that absorbs information and lets both people and agents work with it effectively, creating synergy between them. Initially — a thin layer over an external knowledge engine; the target vision — a standalone product with pluggable storage, versioning, collaboration, and desktop and cloud modes.

## Target layered model

```
┌─────────────────────────────────────────────────────┐
│  Shells/transports: SPA (REST) · MCP (agents) ·     │
│  Desktop shell · Realtime collab relay              │
├─────────────────────────────────────────────────────┤
│  Core: domain logic (KnowledgeStore, services)      │
├──────────────────────────┬──────────────────────────┤
│  Knowledge engine        │  Meta/journal (our DB)   │
│  (derived index:         │  (not derivable from     │
│  parsing, graph, search; │  files: version history, │
│  today — our own engine) │  owner/space scope,      │
│                          │  cross-graph)            │
├──────────────────────────┴──────────────────────────┤
│  Working set: local materialization of files         │
│  (desktop: the user's folder; cloud: a mirror)       │
├─────────────────────────────────────────────────────┤
│  Storage adapters: localfs · s3 · seafile · webdav… │
│  → source of truth = the user's storage             │
└─────────────────────────────────────────────────────┘
```

## Principles

- <a id="p1"></a>**P1. File-first.** The user's files in the user's storage are the source of truth. The files stay complete and usable without us; the user can leave at any moment. **Applicability limits** (the Logseq/SiYuan lesson, see research): the unit of data is a file-note, not a block; entities smaller than a file (blocks, properties) are not introduced as first-class — that is the fork where Logseq went DB-first. And we never rely on "we'll bolt on two-way DB↔markdown sync later" — the industry considers that an unsolved problem.
- <a id="p2"></a>**P2. Derived data is rebuildable.** Index/graph/search are reassembled from scratch by a rescan. The non-rebuildable part (version history, scopes, annotations) lives in one explicitly separated place (a db file on desktop / our DB in the cloud); its loss degrades gently, without breaking the files.
- <a id="p3"></a>**P3. We do not own the storage exclusively.** External changes are a normal mode, not an error. Every write is optimistic (compare-and-swap by a version token); on divergence — a merge flow. Hard rules (conclusions from the sync research): **never lose data silently** — auto-merge for md (word-tokenized 3-way against the base from the journal), otherwise a conflict copy alongside (the Syncthing/Joplin pattern); atomic writes (tmp+rename); the watcher is only a hint, a periodic full inventory plus a restart-safe bounded content-integrity sweep is the source of correctness; the sync layer has a persistent state DB of "what I've seen" (otherwise a deleted item resurrects); etag/mtime/change-token are opaque cheap hints, the arbiter of identity is the content hash.
- <a id="p4"></a>**P4. One core, many transports.** REST (people), MCP (agents), desktop — over one core. The transport adapts, the core decides → feature parity (a note from an agent is versioned/scoped like one from the UI).
- <a id="p5"></a>**P5. Storage is an adapter with capabilities.** External storage is just an adapter to us. The minimal contract: list the tree (for init), read, write, stat/delete/move. Anything that supports it (localfs, s3, Seafile, at the limit even Confluence) is pluggable; "how to sync it" is the pain of the adapter and the working-set layer, not the core. Beyond the contract — a capabilities declaration (watch, atomic-rename, etag, lossless format round-trip, native versions…). Features degrade by capabilities rather than break. **Refinement #76 (DB-storage adapter):** a DB is the same kind of storage adapter below the `FileStore` port (a cloud/enterprise profile for those who do not need file-first portability). A hard invariant (P9): **export is byte-for-byte identical to the FS layout** ("file-first" → "file-portable"). Therefore the DB adapter stores **rendered files as blobs** (one row = bytes + path; `bytea`, the tree implicit in the path; export = dump = identity by construction), NOT a normalized model: re-rendering markdown from columns/AST is provably lossy (CommonMark AST↔md is not identity; SiYuan/Logseq/Notion/Anytype/Joplin all break on round-trip). The normalized store/FTS stays DERIVED over the seam (P2) — the same discipline of "bytes are truth, index is derived" (Fossil/git/sqlar). Canon — the multi-tenant security spike (#76).
- <a id="p6"></a>**P6. Collaboration is an ephemeral layer.** A live session (cursors, CRDT/relay) runs on our service (or p2p); into storage go a deferred debounced write + a mandatory flush on completion. The durable truth stays a file; **the CRDT state is ephemeral** — initialized from the file once per session and not surviving it (a persistent CRDT = "two masters", deliberately rejected, see the collab research). The adoption ladder: presence + soft-lock → a live session with an ephemeral Yjs (the lock screen offers "join", the XWiki pattern) → a persistent CRDT only if offline CRDT-merge is really needed.
- <a id="p7"></a>**P7. A note's identity is our internal note-id, mirrored into the file's frontmatter.** It survives move/rename and a storage swap. (Unlike a permalink, which is fixed at creation and does not follow a move.) The ID is in the file itself (the Dendron pattern), not only in the DB: otherwise an external rename/move past us orphans the version journal and the scopes. The journal and metadata are bound to the ID, not to the path; rename detection in sync is an optimization, correctness rests on the ID.
- <a id="p8"></a>**P8. The index engine is replaceable.** The core depends on the domain `KnowledgeStore`, not on a specific engine. Replaceability is a proven mechanism, not a theoretical one: the first engine-layer implementation (an external MCP engine) was swapped for Notarium's own engine (#69) and then **removed entirely** (#131; earlier — reasons from #74: proven leaks of unscoped tools, a fail-open default project, instability of the external MCP API). Notarium's engine is the only canon; the per-space `engine` collapses to a single value (an enum stub is kept, P8).
- <a id="p9"></a>**P9. One codebase = one SPA + one portable TS core.** Node (server/Electron), the browser, and — potentially — a mobile runtime (Hermes/RN) are **hosts** of the core, not part of it (the Joplin backend / snjs / @notesnook/core pattern). Consequences: Node-isms (`fs`, an HTTP framework, better-sqlite3, chokidar) live only in thin adapters at the edges (the framework is not fixed by the manifesto — it is a swappable edge adapter; currently Express from the prototype, at the #19 refactor — Fastify: schema validation at the boundary = our API contract, native TS, pino), the domain layer is pure TS; the engine's SQL interface is narrow and async-compatible (better-sqlite3 ↔ op-sqlite ↔ wa-sqlite — interchangeable drivers); the SPA talks to the core only through `/api/*`. The desktop/cloud differences are only in the set of plugged-in layer implementations, no forks. The feature gap is measured by contract tests against `KnowledgeStore` (one spec across all implementations, including the stateful fake from #18). **The mobile ladder** (see the mobile research): (1) a PWA thin client to the cloud core (now, ~0 code) → (2) an offline index in the browser on wa-sqlite/OPFS after the Notarium engine (#69) → (3) RN/Capacitor with the same core, files in the app container, sync via the cloud hub. NOT nodejs-mobile, NOT "a shared folder + third-party sync" (the Logseq trap).
- <a id="p10"></a>**P10. An extension is an app over the core contract, not code inside our processes.** An extension is a client with a manifest and a **scoped token** (scopes: `notes:read/write[space]`, `events:subscribe`, `net:<domains>`, `ui:<contribution points>`; the WebExtensions+GitHub Apps model, installed "into a specific space") talking to the core through the same REST/MCP as people and agents, plus a subscription to events (webhooks/SSE from the journal). The ladder: apps → declarative contribution points + a sandboxed iframe in the SPA (a UI class, no direct DOM) → a dedicated extension host next to the core (the VS Code Remote pattern) — only on ecosystem demand. Foreign code inside the core process is forbidden (in-process plugins break cloud parity — the n8n anti-precedent). **We do not do runtime compatibility with Obsidian plugins** (nobody in the industry managed it; ~85% of their API is UI internals; their security model is incompatible with cloud) — compatibility only at the level of the vault-format data. See obsidian, plugin-architectures.
- <a id="p11"></a>**P11. File classes × mount points (two orthogonal notions).** A **class** sets semantics/lifecycle: *user file* (notes — truth, versioned, indexed) / *user attachment* (attachments — truth, not indexed as knowledge) / *derived artifact* (TTS audio, previews, renders — regenerable: key = content-hash of inputs, GC/TTL, loss = regeneration; the DVC/Gatsby pattern, the anti-pattern being Jupyter outputs in the source). A **mount** sets placement: a workspace = a set of typed mounts over the same storage adapters (P5) — a notes mount, an assets mount, a derived mount, … (the role registry is open: exports, trash…). Mounts may have a different nature/provider (notes in Seafile, derived in cheap S3; on desktop — just separate folders). The derived mount is managed by us by default (app-data / our object storage), but it is the same kind of adapter — replaceable. Link rules: links to derived **do not go through markdown** — only derived anchors in the meta DB (a multi-selector: paragraph content-hash + context + position, the Hypothesis re-anchoring cascade; orphaning = a visible state + regeneration; NOT a block-id in the text, NOT first-class entities smaller than a file — the P1 boundary is not violated). For user content the default is attachments in the same storage as the notes (relative links, portability without us); a separate assets mount for user attachments is a deliberate option (links resolve only through us), out of the early scope. Escalation derived → attachment only by an explicit user action. See derived-artifacts. **Refinement #74 (populating the registry for our own engine):** a "class" is not a single bit "service/user", but a **policy set** (`index`/`graph`/`feed`/`tree`/`userSearch`/`agentRecall`/`versioned`/`replicate`); visibility is a "surface × class" matrix, and for hidden classes the exclusion from user surfaces is a **policy invariant, not a bypassable default `WHERE`** (the Obsidian lesson "excluded ≠ exclude": hiding from output ≠ excluding from the index). The class is derived from the mount by default (enforced; a per-file frontmatter override is optional and only if it really affects indexing), identity rests on `notarium-id` (#51), not on the path (rename/move does not change the class silently; the Logseq-namespace/Dendron-dots/Foam-filename anti-pattern). The role registry is populated: **user-doc · attachment · derived · agent-memory · profile · skill** — canon; **profile** (#159) is a reserved "about me" note in the personal domain: human content (provenance — the user, NOT an agent), its own dot-mount `.notarium/profile` hides it from ALL discovery surfaces (`tree/graph/feed/userSearch=false`) — reachable only from Settings → Profile and loaded to the agent in `start_session` (by id, not via search/recall); **encrypted-note** — a per-note variant with locked policies (`index`/`graph`/`feed`/`userSearch`/`agentRecall`=false, the body an opaque envelope, the key never reaching the server; the only principled per-note source of a class, an exception to "class from mount"; sanctioned by P12, implementation in the security spike; NOT the engine and NOT ACL — encryption is orthogonal both to the P8 engine and to P14 access); **chat** (conversation, #75) — the role is reserved, the store form is open (a chat is internally a tree/DAG, the truth is structural, markdown is a read-only projection; pure md as the sole source of chat truth is a trap); **ephemeral/local-state** (layout, graph positions, UI state) — deliberately NOT a mount but the axes `replicate?`/`version?` + a Meta/client layer outside the storage registry. The index is one per space with a `class` column/partition (not an index-per-class; a hybrid FTS5 + `vec0` via RRF over a shared rowid); the agent's memory is a separate **mount in the same space** (eager/lazy, the Letta-MemFS pattern; provenance from the journal #12; visibility refined in #21: visible to the user in a separate section of the personal domain — read/edit/delete, not reorganize; eager = a derived index from `summary`, lazy = files). The canon of decisions and prior art — the data-model spike (#74); the final toolset on this model — the MCP tool-design spike (#21).
- <a id="p12"></a>**P12. We do not do E2EE — Notarium is a file-first system with a smart server.** Server-side FTS+semantics, the version journal, the collab relay, artifact generation (TTS), AI agents — each of these features requires plaintext on the server; E2EE would negate the product (the whole industry split into two camps: E2EE = "a thick client + a dumb server" with no server-side features — Standard Notes / Obsidian Sync / Anytype; a smart server = no E2EE — Notion/Evernote). Our privacy guarantees: file-first (leaving is trivial) + TLS/at-rest in the cloud + **self-host** (the same core at home) + desktop (data never leaves the machine). We honestly cut off: "zero-knowledge" in marketing and the privacy segment for which E2EE is a gate. We leave open: per-note client-side encryption (the Evernote/Bear pattern: a note drops out of the indexes/AI) — #74 gave a mechanism to express this as the `encrypted-note` class with locked policies (see P11), implementation in the security spike; and an E2EE space as a deliberately trimmed mode later (the payoff is low — it cuts all server-side features; not a priority). Encryption ⟂ access control: "only certain people read this per compliance" is authz/ACL (P14/#67), the server reads the note but serves it by grant — not to be confused with per-note encryption. See the e2ee research. **Refinement #76 (three axes separately + an envelope encrypted-note):** (1) **encrypted-note** (per-note client-side) — the server does not read it, the key is not with the server; the envelope = the **`age`** format in an md fence (audited, CLI-compatible `age -d` = zero lock-in, AEAD ChaCha20-Poly1305 — not CBC, does not leak a key-id), the header is plaintext (a deliberate metadata leak, the body opaque), the decrypted form **only in memory**, no recovery by design; the locked policies of #74 = a "server dead zone" (search/AI/diff/merge/graph die, metadata lives). (2) **ACL** (P14/#67) — the server reads, serves by grant. (3) **at-rest/BYOK** — the server reads (for FTS/AI), the client's keys are for compliance/audit/a revoke kill-switch, NOT confidentiality-from-the-operator (Slack EKM "this is not E2EE"; per-tenant keys give a blast radius only for cold storage/backups, not against a live RCE). Crypto-AC is rejected (you cannot revoke what has been decrypted; Oracle: "never use encryption to solve access control"). Canon — the multi-tenant security spike (#76).
- <a id="p13"></a>**P13. Semantics is an engine capability; embeddings are a canonical derived artifact; agent memory = explicit notes.** In the `KnowledgeStore` contract: `capabilities {fts, vector, hybrid, graphExpand}` + `search(query, {scope, pageSize})` (FTS↔hybrid is chosen by the engine's capability — vector is ready and warm — NOT a caller mode; #81) — a scope/permission filter is mandatory (the Notion AI lesson); without vector — an honest degradation to FTS. Embeddings: the key = `(chunk content_hash, embedder_id, chunker_version)` (API embeddings are non-deterministic — identity only by inputs), live in the index DB (sqlite-vec+FTS5 on desktop ↔ pgvector in the cloud, RRF fusion), `embedder_id` is part of the index's identity. The wikilink graph is our unique ranking signal (1-hop expansion; the HippoRAG precedent). MCP memory operations are first-class: remember (write_note + provenance: which agent/when), recall (hybrid search + build_context — a graph walk with a token budget; recall ≠ search), forget (invalidation via the journal, not deletion — the Zep pattern), consolidate (a skill on top, not the core). We do not do automatic fact extraction (mem0-style) in the core — the agent's memory must be readable notes (the Letta pole and similar file-first memory systems; the newest Letta-MemFS is a precedent in our direction). Vector/hybrid are **implemented** (#81; #74 — the deliberate price of leaving the external engine): `sqlite-vec` (vec0) next to FTS5 in the index DB, the key `(chunk content_hash, embedder_id, chunker_version)`, the hybrid via RRF (k=60) over a shared rowid (a pooled-SQL FTS5+vec0, the channel fusion in code — a 3rd graph channel added, default-off), the content-hash the arbiter of invalidation (mtime is only a pre-filter). The implementation's mechanics, tiers/settings, and pitfalls — [search.md](search.md). See also the semantic research, local-embeddings-vector.
- <a id="p14"></a>**P14. Access: space-level membership + a generalized principal; outward — capability links and publish-as-artifact.** Phase 1: `space_member(space, principal, role: owner|writer|reader)`, a member sees everything in the space (the Anytype/Shared Drives model), "share a subset" = a separate space. The principal is generalized: `{user, agent/integration, share-token}` — a guest, an agent, and a link = one grant mechanism. Access semantics: `effective = scopes(token) ∩ grants(principal)` (the GitHub Apps formula); scopes are about actions, grants are about place; the scope's resource parameter is extensible (`[space]` → `[space/note-id]`); one authz check `can(principal, action, resource)`. Phase 2: a share link = a separate capability entity (token, mode=read, revoked_at, expires_at, a list of active links — W3C Capability URLs; 94% of Drive open-links are forgotten) + **publishing = a derived artifact** (a static render with no access to the live API — the lesson of the Notion incident). Per-note ACL — only on a proven need and only additively (the Outline pattern), without inheritance with overrides. Public note IDs are unpredictable. See the sharing research. **Refinement #76 (multi-tenant isolation, a second boundary under `can()`):** `can()` is one layer, not a boundary (AWS: auth ≠ isolation). For pooled open registration an honest second boundary is **three-pronged** (the in-process reversal of #74 removed not one boundary but three — RLS does not close all of them): (1) **data-at-rest** — Postgres RLS (the DB profile; protects only Postgres rows) OR an FS boundary Landlock/mount-ns/uid (the FS profile, where the body is on disk; <5%, not a container); (2) **the meta DB** — RLS (pitfalls: a non-owner role + `FORCE ROW LEVEL SECURITY`, `SET LOCAL`/pooler, off-by-default + a CI assert, a test as the app role); (3) **compute** — per-tenant event-loop isolation (a worker pool, concurrency caps, `statement_timeout`, input/regex limits — day-one for open registration: a noisy neighbor = a DoS on single-threaded Node). A full process/microVM silo is an enterprise upsell (needed for foreign code, which we do not run, or a regulatory tenant), "a silo = a clone of the pooled binary for one tenant". Canon — the multi-tenant security spike (#76).

## Key consequences / synergies

- The version journal (#12) stores content snapshots ⇒ it gives a **base for a 3-way merge** in the merge flow (P3, P6).
- The working set as an explicit element: any FS engine indexes local files ⇒ for non-local storage a "storage ↔ working copy" sync is needed. On desktop the layer degenerates (working set == the user's folder).
- Desktop: packaging a third-party python engine into an app is hard ⇒ P8 is not theoretical — on desktop the Notarium engine (#69, the desktop profile) with reduced capabilities (acceptable under P5 degradation).

## Fixed decisions (discussed 2026-06-10)

- **The working set + sync is an accepted architectural element** (the largest addition to #9). On desktop the layer degenerates (working set == the user's folder).
- **Metadata has exactly one home per workspace** (the desktop db file OR the cloud). Moving the home is an explicit operation; we do not promise syncing two metadata homes in the early phases.
- **External storage = just an adapter** (see P5). The manifesto does not list "allowed" backends — suitability is defined by the minimal contract; all sync specifics are encapsulated in the adapter.
- **Feature degradation on desktop is acceptable** (P5/P9); its concrete forms are defined by the divergence map below and refined as the cloud makeup clarifies.
- **One Notarium engine instead of a "lite" variant** (decision 2026-06-12, epic #69): the term lite-engine is abolished; the desktop/cloud differences are build profiles (pluggable SQL/search/storage backends over the P5/P9 seams), not separate engines and not inheritance. Syncing external storage is a separate milestone (#70), not part of the engine. Our own engine in the cloud is a goal, not an option.
- **The data model for our own engine: classes × mounts** (spike #74, decision 2026-06-13): the second architectural spike after #9, detailing P8/P11 "from our own engine." Decided: a class = a policy set (not a boolean), derived from the mount (enforced) with identity on `notarium-id`; one index per space with a `class` column; the historical pre-#307 v1 registry = user-doc · attachment · derived · agent-memory (canon) + chat (the role reserved, the form → #75) + ephemeral/local-state (a policy axis, not a mount); a project inside the domain = folders/MOC, not an entity; the external engine is removed, vector/hybrid → our derived-todo. It gates the finalization of the #21 toolset. Canon — the data-model spike (#74) + the refined P11 above.
- **Refinement of the project model (#13, decision 2026-06-17):** `project` inside the domain is unfolded from "not an entity" (#74-F3) into a **lightweight OPTIONAL entity** — a marked folder with a stable identity (the marker `.notariummeta` = id-in-file, the #51 pattern at folder granularity) + a derived `projects` registry in the meta DB. Optionality preserves the essence of F3 (we do not force structure/empty folders), the entity is metadata-only (not a heavy normalization); addressing — the handle `(space, slug)`, the space implicit behind it. It fixes the "project=space" conflation at the MCP edge (#21). Path-as-project is rejected (it would make the path the container's identity — the #74-F1 anti-pattern). Canon — [projects.md](projects.md); the F3 ADR amendment — in data-model-decisions.
- **Safe multi-tenancy: isolation, DB-storage, encryption** (spike #76, decision 2026-06-14): an adjacent security spike out of #74 (leaving the external engine removed the process-per-space — the trigger); it details P5/P12/P14. The main reframe: the "second boundary" is not one — RLS protects only Postgres rows, while the in-process reversal also removed the **FS** and **event-loop** boundaries that a process gave for free. Decided: the second boundary is **three-pronged cheaply** (RLS meta DB + an FS boundary Landlock/namespace + per-tenant compute isolation), a silo = an enterprise upsell; the DB-storage adapter = **blob bytes** at the `FileStore` seam (export identical to the FS by construction, the normalized model rejected); the three encryption axes separately (encrypted-note ⟂ ACL ⟂ at-rest/BYOK), the envelope encrypted-note = `age`. Implementation — a separate **Cloud milestone** (it gates opening public registration); MVP/Beta = single-tenant self-host. It closes the open question of #10 / Phase 4 of the roadmap. Canon — the multi-tenant security spike (#76) + the refined P5/P12/P14 above.

## Desktop vs Cloud: the divergence map

The gap is localized by layer; everything not listed is shared code (P9).

| Layer | Desktop | Cloud | Nature of the gap |
|---|---|---|---|
| SPA/UI | the same | the same | none |
| Core (domain) | the same, a local process | the same, a server | none |
| Storage adapter | localfs | s3/seafile/… | shared contract, different implementations |
| Working set/sync | degenerate | a mirror + sync | the module is on/off |
| Engine | the Notarium engine (desktop profile) | the Notarium engine (cloud profile, #69) | the gap is closed: one engine, build profiles |
| Meta/journal | a SQLite file | the service's DB | one schema, different drivers |
| Auth / owner/space | one user, off | on | a feature flag |
| Collab realtime | only through a cloud account | yes | a cloud-only service |

Notes:
- Packaging a third-party python engine into desktop is hard, and the upstream is not moving there ⇒ the desktop engine = the Notarium engine (#69): our own `KnowledgeStore` implementation (remark parsing, a wikilink graph, SQLite + FTS5, an async SQL interface). Per the research this is weeks, not months (references: Foam, Quartz); the shell is Electron with the core in the main process (the Joplin pattern). A python sidecar (PyInstaller) is a fallback: antiviruses/signing/3 OSes make it expensive. There is one engine, desktop/cloud are build profiles (pluggable SQL/search/storage backends, see the decision below); the former external engine was swapped for the Notarium engine and removed (#69/#131) — P8 replaceability is proven and used, we do not keep two parallel paths.
- The `KnowledgeStore` contract tests are the tool for controlling the gap: one spec, run against the Notarium engine and the e2e fake (#18). The desktop/cloud gap = a known list of red tests, not a surprise.
- The same rule applies inside the meta/journal row of the map: `RevisionPersistence` and `GatewayStatePersistence` have one executable contract over the in-memory twin, SQLite, and a live Postgres schema. Both SQL dialects share the checksummed, forward-only history specified in [meta-db.md](meta-db.md). `make test-pg` is the containerized live-dialect gate; ordinary `npm test` skips that target when `TEST_PG_URL` is absent.

## Explicitly deferred areas (we see them, we are not designing them now)

Fixed to distinguish "did not think of it" from "deliberately later"; none of them blocks the foundation:

- **Import/migration** (Obsidian/Notion/Evernote → Notarium): file-first makes it cheap, the Obsidian vault format is compatible at the data level (P10) — product work, not architectural.
- **A query language over the index** (Dataview-like) — a future evolution of the `KnowledgeStore` contract; do not hardcode it into the API prematurely.
- **Trash / soft-delete** — a separate mount role (P11) + the journal; to be designed with #12.
- **Image/operator boundary** — the production image is an appliance with the public entrypoint and command contract specified in [cli.md](cli.md). The canonical online snapshot and fresh-root disaster restore are specified in [backup.md](backup.md). Provider-native backups for scattered/Postgres deployments remain an operations concern.
- **Cloud quotas/billing, generation budgets** (TTS/embeddings) — when a paid cloud appears.
- **Telemetry/observability** — a standard stack, toward production. (Separately: an audit of an agent's retrieval queries (#243) is a POINT product feature — a meta-DB log + a read model for the Agents section — NOT this general telemetry stack; do not inflate it into a platform.)
- **SPA i18n** — product work.
- **Decomposing the monoliths and dissolving `services/` in `server` / `engine` / `engine-memory`** (#56, a separate task) — the reorg to the target code-organization convention has been through `contract` and `core`; the large backend-host and engine files (`api.ts`, `gateway.ts`, `notariumStore.ts`, `inMemoryStore.ts`, the meta-DB adapters) and their `services/` layout are tidied in a separate session — so as not to force a risky split on top of an already large diff under time pressure. Until then `engine*`/`server` **deliberately** keep the former layout: this is deferred scope, NOT a reference to copy (the reference is `core`).

**Verdict: the industry does not refute P1, it refines its limits.** Our model = the Obsidian model (the only market-successful file-first one: a smart merge layer + versions in a separate DB = our journal), reinforced by the fact that our edits go through the core. The counterexamples (Logseq → DB-first, SiYuan → JSON AST, Anytype → CRDT) moved away from files because of **block granularity and RTC** — factors that P1 does not have (the limits are fixed in P1).

The main enemies per the research (rather than what we feared initially):

1. **Generic file sync under our folder** (iCloud/Dropbox/OneDrive/Syncthing compete with the core for the files) — the #1 cause of corruption even for Obsidian; OneDrive Files On-Demand replaces files with 0-byte placeholders. We plan for: atomic writes, placeholder detection, conflict copies, loud warnings.
2. **The drift of "metadata in the DB ↔ files changed past us"** — cured by the ID in the frontmatter (P7) + reconciliation on reindex.
3. **Sync without a state DB** resurrects deleted / deletes created — a state DB is mandatory (P3).
4. **Pleasant surprises**: AWS S3 supports native CAS (`If-Match`, 2024) — our optimistic write maps straight onto the API (but for S3-compatibles this is a capability to probe); debounced write-back for collab is literally the default of the Yjs ecosystem (Hocuspocus), and Obsidian Relay is built on a fork of y-sweet along our own scheme.

## Open questions

1. **The working set for large non-local storage** — a full mirror vs lazy materialization? In the manifesto we fix only that the working set *may* be partial.
2. **The cloud version's makeup** — what exactly it includes (collab? semantic search? agent features #21) — will clarify as MVP progresses; the concrete forms of desktop degradation depend on it.
3. **Merge flow UX** — the direction is decided by the research (see merge-ux): the ladder "a clean merge silently + a passive indicator 'merged, view/rollback' → overlapping edits = inline conflict cards in the editor (a suggestion pattern, no git terminology and no 3-pane) → a conflict copy only as an emergency fallback with a diff UI". An agent's edits use the same UI (pending suggestions + keep/undo). A conflict does not block saving/syncing; visibility (a banner + a global counter) matters more than the mechanism. A new requirement for the journal #12: store both sides of a conflict + the merge attribution. Remaining: designing the concrete screens at implementation.
4. **Watch without a watcher** (S3) — the direction is decided: a periodic LIST = truth, push events = a trigger for an early LIST; the tuning is open (intervals, cost on large buckets).
5. **P2P for collab** — kept as "maybe", by default a relay through our server (a p2p precedent exists — Peerdraft).

## A single data root <a id="data-root"></a>

Everything Notarium writes lives under **one root** — `DATA_DIR`. Every internal path is derived from it **in code** ([`apps/server/dataPaths.ts`](../packages/server/src/apps/server/dataPaths.ts)), and **none of them is a required env**:

```
DATA_DIR/            # /data in the image; $XDG_DATA_HOME/notarium (or ~/.local/share/notarium) on a host
├── meta.db          # #51 identity, #12 journal, #16 spaces, #10 auth — non-rebuildable (P2)
├── replay-keyring/  # installation HMAC keys + active generation pointer — non-rebuildable
├── engine/<slug>.db # derived FTS5+graph+vector indexes (P2) — delete → reindex
├── jobs/            # export artifacts (P11) + jobs/imports — durable import staging
└── spaces/<slug>/   # the user's .md — truth (P1)
```

The rule and its cost: **an internal setting must not be mandatory**, otherwise it will be forgotten — not hypothetically, but in practice. A deployment pointed meta and engine at a writable volume, forgot the path to the artifacts, and that produced the worst class of bug: boot green, `/api/health` — `ok`, `POST /export` answers **`202 Accepted`**, and the job fails in the background with `EACCES: mkdir '/app/.data'`. A forgotten variable must yield a working default, not a failure.

Hence three invariants:

- **The default is absolute, never cwd-relative.** The former `.data/*` was the trap itself: under `WORKDIR /app` (root-owned, the process is uid 1000) they are unwritable, and outside the container they silently follow someone else's cwd. The image creates `/data` and `chown node` before `USER node`.
- **A check on boot, not on the first write.** Stores create directories lazily, so a non-working root surfaced deep in runtime. `ensureDataRoot` creates and **writes a probe** into each directory before `listen` — and fails with one clear message with the path and the fix. Each directory is probed separately: with overrides they may sit on different mounts, and a writable root proves nothing about the rest.
- **`spacesRoot` is not just a path but a capability gate** (`spaceCreate`, purge). Therefore the default `<DATA_DIR>/spaces` applies **only** in the zero-config branch ([`spacesFromEnv.ts`](../packages/server/src/apps/server/spacesFromEnv.ts)): a host with an explicit topology (`SPACES_CONFIG` / legacy `ENGINE`+`NOTES_DIR`) asked for static and must not silently get space creation and deletion over a root it did not name.

Overrides remain — as an operator's choice, not as a requirement: `META_DB_URL=postgres://…` (shared state), `SPACES_ROOT` (the notes live elsewhere — class A: "where YOUR notes are"), `ENGINE_DATA_DIR`/`JOBS_DATA_DIR` (derived data on another disk). The trap was the default, not the presence of a handle.

The replay keyring follows the metadata topology. Canonical file SQLite uses
`<DATA_DIR>/replay-keyring` with no setting and can replace a completely lost
keyring because the database and files share one local failure domain. Any
external meta-DB topology must set `NOTARIUM_REPLAY_KEYRING_DIR` to one absolute,
durable path shared by every serving process. A stable database witness with a
missing external keyring is ambiguous and stops boot before space discovery;
copying per-replica keys or silently minting a replacement would split replay
identity across servers.

**`META_DB_URL` is classified in exactly one place** ([`services/metaDb/metaDbUrl.ts`](../packages/server/src/services/metaDb/metaDbUrl.ts)): `postgres://…` / `postgresql://…` (scheme case-insensitive, per RFC 3986), `sqlite:<path>`, `sqlite::memory:`, or a bare file path. **Any other scheme is a boot error, not a filename** — and that strictness is the point, not pedantry. A lenient classifier reads `postgress://…` as a relative path, so the host creates that file, starts green on an empty database, and a password host re-opens the **public** first-run screen: the first visitor becomes owner while the real data sits intact and unread (the takeover [`legacyMetaDbAt`](../packages/server/src/apps/server/dataPaths.ts) guards — except that guard stands down precisely when `META_DB_URL` is set). The connection password would also become a directory name and appear in the boot banner. A bare path stays a path, so a directory called `postgres-backup/` is never mistaken for a server, a URL naming no database at all (`sqlite:`) is refused rather than resolved against the cwd, and so is a connection string that lost its scheme (`host=db password=…`, `//user:pw@host/db`) — taken as a path it would become a directory named after the credential, created on disk and printed by anything that reports paths. Everything that asks "Postgres or a file, and which file" — the boot resolver, the write-probe, the online-backup layout gate, `/api/about`, the admin CLI — asks that one classifier, so no two of them can read the same URL differently. What each does with a correctly classified target stays its own policy: the admin CLI additionally turns down `sqlite::memory:` (nothing to recover in it), and `AUTH_MODE=password` refuses it at boot — a meta-DB that forgets every user on restart hands out the first-run screen again, so "present" is not "durable". Wherever a meta-DB URL is printed, a SQLite target is named by its path and anything else by its scheme alone, so a Postgres password is not quoted back into a log. The env edge additionally refuses a credential-carrying value where a path belongs, because such a directory name would also reach messages Notarium does not format — an fs error naming the path it failed on.

## Code canon: comments and literal placement

### Comments, canon, and references <a id="comments"></a>

A comment describes the **local truth of this place, not derivable from the signature**: why the nullability, where wire and domain diverge for a specific field, units/ranges, an "honest gap" ([P5 degradation](architecture.md#p5)). An architectural invariant or a manifesto principle is **not retold** in code — a reference is placed to it.

- **The canon lives in the doc, the code references it.** One greppable tag: `// canon: docs/<file>.md#<anchor>` (in JSDoc — `@see docs/<file>.md#<anchor>`), no more than one canon reference per concern/block. Example: above `NoteClassSchema` — `// canon: docs/architecture.md#p11 · docs/note-model.md#note-classes`, not a retelling of the visibility matrix.
- **Minimalism: only the non-derivable and not-in-canon.** A comment exists only if it carries truth that is NOT visible from the code AND is NOT in a canon doc. What is covered in `docs/*` (architectural narrative, the domain model, cross-subsystem history) — a `// canon:` reference, not a retelling. Keep it 1–3 lines; a file header = 1–2 lines of "what it is" + a reference; a complex algorithm — a short contract of rules. A litmus per sentence: "would it be at home in a canon doc?" → yes = there it goes, with a reference; no (local mechanics) = keep it short.
- **Provenance is NOT in the code.** The "why it appeared" (a task/issue number `#NNN`) lives in git history, the tracker, and the canon doc, NOT in a comment: an issue is closed, the knowledge moves to the canon. The only durable pointer in a comment is a `// canon:` reference ("where the norm is written"). Bare `#NNN` in prose we do not carry.
- **A casual `P7` in prose** is a human-readable label, not a reference; the canon truth is via a `// canon:` reference to [`architecture.md#p7`](architecture.md#p7).
- **No changelog-in-comments.** The migration history (`v1..v7`), phased evolution ("#102 phases 1..6") — in git history and the canon doc; only the current invariant stays in the code.
- **Define once.** An invariant common to N fields/facets is stated once (on a shared type / in a section header), the rest reference "see above" instead of repeating the paragraph.
- **Delete the obvious.** JSDoc that repeats a field's name+type (`/** Product version */` above `version: z.string()`) carries no information.
- **A gross violation is retelling the derivable or the canon itself.** This is a ban, not a "dispreferred": a comment that repeats what the code or a `// canon:` reference already says is cleaned out. Three canonical slop patterns: **(1) retelling a type derivation** — `/** union DERIVED from NOTE_CLASS (no parallel list) */` above `type NoteClass = (typeof NOTE_CLASS)[keyof typeof NOTE_CLASS]` (exactly what the line already says); **(2) retelling a canon rule** — `reference NOTE_SORT.modified, not the raw literal` above every dict duplicates [`#literals`](architecture.md#literals), one `// canon:` reference per file is enough (and on a self-evident dict of simple values — often not even that: the rule is repo-wide); **(3) a field's name+type** (see above). In an agent codebase such slop is a direct tax on context and inflates files for nothing.
- **A shared instrument — only its own invariant.** A comment on a reusable symbol (a status dict, a generic utility, a cross-domain primitive) describes the truth of the SYMBOL itself, not how one feature uses it. `/** Rate-limited — login throttled (#10) */` above `TOO_MANY_REQUESTS: 429` in a shared status map is slop: 429 is called from anywhere, a binding to one feature is incomplete and leaks a call-site concern into a shared dict. The particular truth lives AT the call site (the route that throttles login), not on the shared code; a shared code dict = a self-evident dict (like `AUTHOR_KIND`), with no per-element comments. The same test catches a **per-value gloss on a bare dict** (`keep = keep the block`, `user = own notes`): slop when the meaning is carried by the value NAMES themselves OR when it has a home on the usage-site schema (that is where it belongs — once); on the dict we keep only a genuinely non-derivable dict-only fact (a deliberate value exclusion, a guard invariant). A litmus on any comment: **whose truth is this** — the symbol's or its caller's.
- **Form: JSDoc for the contract, `//` for the local.** A `/**…*/` goes on an exported symbol whose essence is not visible from the signature (hover/IntelliSense shows it); `//` is for local notes and sections inside a module. Do not convert the form en masse for uniformity — the rule is about content, not syntax.
- **Cleanup touches comments, not code.** When tidying a comment, do not rewrite the layout/logic beneath it and do not touch functional directives (`@ts-expect-error`, `eslint-disable`, pragmas) — those are separate changes.
- **The gate:** `npm run canon:check` ([scripts/check-canon-links.mjs](../scripts/check-canon-links.mjs)) validates that every `// canon:` reference resolves to a real doc anchor; a broken reference = red.

### Literal placement <a id="literals"></a>

A placement layer by the "range" of a value — the rule for where to write a domain literal/dict specifically in THIS monorepo (the general principle "`enum` → a const object, reference the named const" is in the code-organization canon):

- **`@notarium/contract`** — everything that crosses the wire (client↔server↔engine): `QUERY_KEY`, `SSE_EVENT`, `STORE_EVENT`, `HTTP_STATUS` (pure `as const` dicts), cross-layer business invariants (`ACTIVITY_WEEKS`), time units (`DAY_MS`). The wire's domain enum dicts live in the **zod-free** bucket [`contract/src/consts/`](../packages/contract/src/consts) (the subpath `@notarium/contract/enums`), so the SPA does not pull zod into the bundle. One source for both sides — a value desync is impossible by construction.
- **`core`** — domain invariants not tied to the wire (note classes, visibility).
- **web `consts.ts` per feature folder** — UI-local values (storage keys, route segments, panel dimensions).
- **A backend module-top `const X_MS = …`** — allowed only for single use inside one file.

A domain enum's value is taken from a const object (`NOTE_CLASS.userDoc`), not a raw literal — greppability, a safe rename, no silent drift where TS does not check the value (a log, a string DB column). A cross-package enum needed by `core` and `contract` lives as TWO independent copies (P8 decoupling), reconciled by the gate [`test/enumDrift.test.ts`](../test/enumDrift.test.ts).
