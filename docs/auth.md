# Authentication and multi-user

Canon for auth (#10). Decisions locked in on 2026-06-12 (discussion in #10 on top of the space-isolation security research and the prior-art research on self-host authentication). The permissions model is stage 1 of manifesto P14 ([architecture.md](architecture.md)).

## Model

- **The principal is generalized** (P14): a human with a session, an agent with a PAT, and (in the future, stage 2) a share-token — one mechanism. On each request the principal is assembled ONCE at authentication time (from grants in the meta-DB) and thereafter the decision is purely synchronous: `can(principal, action, resource)`.
- **Decision formula**: `effective = scopes(token) ∩ grants(principal)`. Scopes are the ceiling of actions for the credential (session = `manage`, PAT = `read`|`write`); grants are the membership `space_member(space, username, role: owner|writer|reader)`. Management actions (issuing a PAT, members, users, creating spaces) sit ABOVE `write` — a leaked PAT cannot issue a token or grant access.
- **Roles within a space**: a reader sees everything in the space, a writer mutates notes, an owner manages members. "Share a subset" = a separate space. Finer granularity — #67.
- **Username immutable** (the same rule as SpaceSlug): the key for membership, the journal, and management routes; the renameable field is `displayName`.
- **Host-admin ≠ data access**: an admin manages users, creates spaces, and repairs the membership of any space (a recovery path for spaces born from config), but READING a space's data requires membership. Boot rule: a space without a single member gets owner rows for all active admins (this covers the first launch and spaces added via config); curated membership is not touched by boot.
- **Refusal semantics**: anonymous → 401 (with `reason: setup_required` while there are no users); authenticated without a grant → the same 404 as "no such thing" (anti-enumeration, §2 of research #16). The `/api/spaces` list is itself a membership filter; `/api/config` returns only `capabilities` (the host-global `defaultSpace` was removed in #99 as a legacy vestige — the client lands on `me.personalSpace`, otherwise the first readable one from `/api/spaces`; #73 previously returned a membership-relative `defaultSpace`, its null branch became unreachable by construction and the field was removed from the wire).
- **Ability resolution uses the full principal**: every Owned location is filtered through `can(space:read)` before list, exact lookup, effective precedence, attachment loading, REST detail, or MCP activation. A PAT/OAuth principal narrowed away from the user's Personal Space therefore cannot recover Personal roles or skills merely from its username; the result is the same not-found/empty response as any other inaccessible placement.
- **Attribution in the journal** (#12): `user:<username>` | `pat:<username>:<patId>` | `'ui'` (mode none — what pre-#10 deployments wrote).

## Modes

- `AUTH_MODE=password` (default) — secure by default. Requires a meta-DB; you don't need to configure it — since #101 it always exists (`sqlite:<DATA_DIR>/meta.db`, [canon](architecture.md#data-root)), and `META_DB_URL` is needed only to move to an external Postgres. A host without a meta-DB is reachable only programmatically (`createServer` without `metaDbUrl`) — there password mode does not start, and auth has no degraded fallback. Nor does it start on an in-memory meta-DB (`sqlite::memory:`): present is not durable, and one that forgets every account on restart would re-open the first-run screen to whoever reloads first. Zero users → all data routes return 401 `setup_required`, the client renders the first-run screen; `POST /api/auth/setup` creates the owner (admin + owner of all configured spaces) and closes forever.
- `AUTH_MODE=none` — a single all-access principal, an explicit operator opt-out (desktop, dev, trusted intranet). Auth routes respond 404, the login UI does not exist. This is the "Auth / owner-space: desktop = off" feature flag from the manifesto.
- External identity (OIDC, a trusted header from Authelia/authentik) — deliberately later: the schema does not resist it (`password_hash` is nullable, identity is separable), the `AuthMode` enum is extensible. Prior art: 7 of 8 self-host peers started with a local password.

## Credentials

- **Passwords**: scrypt from `node:crypto` (argon2 in Node = a native dep, against P9), OWASP parameters `N=2^17, r=8, p=1`, encoded in the hash string — a parameter upgrade does not invalidate old hashes, and login transparently rehashes. Login does not distinguish "no user" from "wrong password", neither by response nor by timing (dummy-verify). Password length is capped (`max(1024)`) — each one is hashed with scrypt, and an unbounded body would be an amplification lever. The rate limit is two-tiered, and both gates close BEFORE scrypt: 10 failures/15 min per username+ip (account brute-force) + 20 failures/15 min per ip across ALL usernames (amplification: logging in an unknown user also hashes a dummy, and without an ip gate rotating the username would force unbounded scrypt work). One verify consumes roughly 128 MiB at these parameters, so a shared process-local semaphore admits at most 2 concurrent verifies across BOTH login transports (`/api/auth/login` and inline `/oauth/authorize`); excess attempts get 429 before scrypt. Counters and semaphore are in-memory, per-process.
- **Sessions**: server-side in the meta-DB (the `sessions` table), an httpOnly cookie `nt_session` (SameSite=Lax, Secure behind https), value `nts_<256 bit>`, sha-256 in the DB. TTL 30 days, sliding (touch no more than once an hour). JWT is deliberately absent: revocation must be instant (disabling a user kills sessions and tears down SSE; a password change tears down ALL sessions — the current tab is issued a fresh token, and other devices are kicked out).
- **PAT**: `ntp_<id>_<secret>` (the GitHub/GitLab/Karakeep pattern: the prefix for greppability in leaks, the id half for O(1) lookup, the secret half as sha-256 in the DB, shown exactly once). Scope `read`|`write` + optional narrowing by a list of spaces (intersected with live membership on every check — revoking a grant instantly narrows the token), optional expiry, revocation. **The name + permissions (scope + narrowing) are mutable after issuance (#162)**: `PATCH /api/me/tokens/:id` changes the name (a display label), the level, and/or the set of spaces WITHOUT recreating the secret. The principal is reassembled on EVERY request (`authenticate` re-reads the PAT string), so the change takes effect from the next call — there is no principal cache that would hold the old scope; `dropSse` on the token's principal is a belt modeled on revoke (the live SSE snapshot is held by the human session, not the token). `manage` is unreachable even on the patch (enum `read|write` — the "a leaked token does not manage" belt holds). Finer granularity — finalized by research #21.
- **Invite/reset links**: there is no SMTP, so bootstrapping a credential = a one-time link `/invite#<token>` (the token in the fragment — it does not land in access logs; it travels to the server in the POST body). One mechanism, two purposes: invite (no password, TTL 7 days) and reset (TTL 24 hours; acceptance kills old sessions). One live link per user; an admin never knows anyone else's password.

## Wire

The anonymous flow (explicit `{ public: true }`): `GET /api/auth/session` (a boot endpoint: mode/setup/me), `POST /api/auth/login|setup|logout|invite-info|accept-invite`. Everything else goes through `can()`: `GET /api/me`, `POST /api/me/password`, `GET|POST /api/me/tokens`, `PATCH /api/me/tokens/:id` (permission change #162), `DELETE /api/me/tokens/:id` (self), `GET /api/me/connections`, `PATCH /api/me/connections/:id` (level change #162 + per-space narrowing #181), `DELETE /api/me/connections/:id` (self — OAuth connections #96), `GET|POST /api/users`, `POST /api/users/:username/invite`, `PATCH /api/users/:username` (admin), `GET /api/s/<slug>/members` (member), `PUT|DELETE /api/s/<slug>/members/:username` (owner/admin; the last owner is protected, as are self-disable / the last admin). The schemas are in `packages/contract/src/schemas/rest/auth.ts`, section "Auth (#10)".

## CSRF and proxy

The first line is SameSite=Lax; the second is an Origin check on cookie-authenticated mutations: Origin is compared against `X-Forwarded-Host` (if present; this is how the browser sees the host) or `Host`. Bearer requests are excluded (no cookie — no CSRF surface). The deployment consequence is unchanged: the reverse proxy must send `X-Forwarded-Host` (or not rewrite Host) and overwrite forwarded values — otherwise mutations from the UI get a 403.

Login and new OAuth client admission (DCR + pending CIMD) use Fastify's canonical `req.ip`, never a raw `X-Forwarded-For`. Unset `TRUST_PROXY` (the default) makes forwarded client IPs inert. Behind a reverse proxy, set it to the direct proxy's comma-separated IP/CIDR allowlist so the real client IP is counted; booleans, hop counts, named ranges, and all-address `/0` ranges are rejected at boot. This IP-only opt-in leaves the existing forwarded host/protocol integration contract unchanged.

## Access recovery (admin CLI)

There is no SMTP and only an admin issues a reset link — which means "lost the password of the only admin" = lockout without an out-of-band tool (the same gap that Gitea/Immich close with a CLI). The tool is `packages/server/src/apps/server/commands/admin/main.ts`; it works directly against the meta-DB (SQLite WAL tolerates a second writer — you can do it with the server live; Postgres always):

- dev: `npm -w @notarium/server run admin -- <cmd>` (via tsx);
- prod (docker): `docker compose exec notarium admin <cmd>` — `admin` is a public command shipped in the image and reaches the same CLI as `notarium admin`.

Commands: `list` · `passwd <user> [--password <pw> | --random]` · `create-admin <user> [--random] [--display "Name"]` · `grant <user> <space> <owner|writer|reader>`. A password without a flag is read from stdin with echo suppressed (it does not land in history/scrollback). The CLI finds the meta-DB on its own: first the **explicitly named** one (`META_DB_URL`, or the root from `DATA_DIR` — the same resolution as the server, [canon](architecture.md#data-root)); then up the tree to `docker/volumes/data/meta.db`, and after that to the pre-#101 layouts `docker/volumes/notarium-state/meta.db` and `.data/meta.db` (recovery must also find an unmigrated deployment); and only **last** — the implicit host default `~/.local/share/notarium/meta.db`. The order is exactly this because that file is materialized by any bare `npm run server`: prefer it and `list` would show "no users", while `create-admin` would create an admin in an unrelated DB, whereas the real deployment sits one folder up and REFUSES to silently create an empty DB — a wrong path fails with an error rather than looking like "no users". The scheme of an explicit `META_DB_URL` is read by the [one classifier](architecture.md#data-root) the driver itself uses, never a local prefix test: a path that merely looks Postgres-shaped (`postgres-backup/meta.db`) stays a path and meets the existence guard, an unknown scheme is refused outright, and `sqlite::memory:` is refused as having nothing to recover. The meta-DB is echoed on every run: a SQLite target by its full path — the one recovery actually needs, since opening the wrong file is the failure this guards — and a Postgres one by its scheme alone, because no rule for finding where a password ends survived review, and the driver names host, database and user in its own connection error anyway. `setPassword`/`createAdmin` are available ONLY from the CLI: there is no HTTP path (no current-credential proof), this is the host's operator boundary.

The same binary also exposes the installation-only command
`recover-replay-key --expected-key-id <stable-id> [--apply]`. It is narrower
than account recovery: it exists only for an external meta-DB whose stable
witness remains while the shared keyring is completely absent. The first call
is a dry run. Before repeating with `--apply`, stop every serving process and
recheck both `META_DB_URL` and `NOTARIUM_REPLAY_KEYRING_DIR`; the command checks
the topology, stable id, and complete absence again immediately before starting
the witnessed replacement saga. Present, corrupt, or mismatched files are never
overwritten by this recovery path.

`grant` accepts what an operator can actually have: the current space slug, a retired
slug alias, or the exact stable space id. Slug/alias resolution uses the same
`current > alias` precedence as the server, but the membership row always receives the
stable id; success prints the canonical current slug. An unknown reference fails with
`no such space`; an archived space fails explicitly too — restore it first, then grant.
An alias shared by multiple spaces is ambiguous and therefore fails as unknown rather
than depending on registry order. Neither refusal writes a membership, so the recovery
CLI cannot report success while `/api/spaces` remains empty. The final active-space
check and membership upsert are one driver-level atomic operation; concurrent archive
or purge therefore either happens before the grant (which refuses) or after the
completed grant. Purge then removes the membership; archive preserves it for restore.
Neither operation can land between validation and a false-success write.

## SSE: revoke = disconnect

Open `/api/s/<slug>/events` streams are registered (principal, user, space) in the auth service's registry. Removal from members tears down that user's sockets on that space; disabling a user — all of their sockets; revoking a PAT — that token's sockets; **a permission change to a PAT/OAuth connection (#162)** tears down that principal's sockets via the same `dropSse` — reducing permissions forces a reconnect under the new ceiling (for ordinary request/response the ceiling already applies from the next request — the principal is reassembled). There is no silent going-quiet: the client EventSource will see the break, and the reconnect will hit a 401/404.

## Loss of access at runtime: explicit takeover (#111)

The server-side "revoke = disconnect" left the client in a silent breakage — the socket tears down, the reconnect and the data routes start returning 401/404, and the UI simply "stops loading". The client turns this into an explicit state. The server does not need to change for this: the distinction comes from the **trigger + authority** pairing.

- **Triggers** (something changed, recheck): the death of the SSE stream — `EventSource.onerror` with `readyState === CLOSED` (per spec a non-200 reconnect, i.e. the 401/404 of a revoked principal, FAILS the connection into CLOSED; a network blip stays CONNECTING and self-heals, not a trigger) — and the first 401/403/404 on a space-scoped route of the active space (a probe in the api layer). Both are only a hint.
- **Authority** (what exactly happened): a single `GET /api/auth/session`. The server recomputes grants on every request, so a fresh session is the truth; you cannot guess from the response code (anti-enumeration #16 makes 404 ambiguous).
  - `me === null` → **the session has ended** (a stale cookie / disabled — disabling kills the session, so a disabled user correctly reduces to "logged out"): the client reloads the session, and the existing AuthGate lands on login.
  - `me` is present, but the active space is not in `me.spaces`/`me.personalSpace` → **access to the space is lost** (revoke / archive #110 / deletion — for the user this is one state; distinguishing revoke from archive is neither needed nor possible over the wire): a full-screen takeover with a switch to the personal (#99) or first readable space. **Alias-tolerance (#123)**: the match goes by the current slug OR past slugs (`me.spaces[].aliases`) — otherwise a rename of the ACTIVE space (the new slug is in `me.spaces`, while the client's `active` lags on the old one at render time) would produce a false `space-lost`. The same alias-aware match is in `canWriteSpace`/`canManageSpace`, so that read-only chrome does not flicker on a rename.
  - grants are in place → a false alarm (an engine/network restart): nothing is unmounted, the stream reopens, and the user does not notice.
- **The safety of immediate revocation**: a confirmed loss UNMOUNTS the entire data subtree (the takeover renders above the providers) — the dead space's content leaves RAM/DOM at once. An unsaved draft is deliberately NOT rescued and not persisted: that would be retaining the content of a space to which there is no longer access, which contradicts revocation (the server would reject the save anyway). Takeover/unmount happens only on a CONFIRMED loss — a transient blip does not carry away work.

**Symmetrically — granting access without a refresh.** The named channels are one small registry (`SSE_EVENT`), separate from the read-model `data:` frames: `access`, `members`, `rename` and `agent-sessions` are empty-body nudges whose truth is a named REST route, while `job` carries the job's wire status ([jobs.md](jobs.md)). The same model in reverse: when membership is GRANTED (or a role is changed, or a NON-active space is revoked), the server does not tear down the socket but pushes a **named SSE event `access`** into the user's live stream (a channel separate from the read-model `data:` frames — the `StoreEvent` contract is untouched). `dropSse(match)` tears down, `notifySse(match)` pushes — twins over a single per-user SSE registry (`putMember` → notify the user; `removeMember` → drop on THIS space + notify the user's remaining streams). A third producer of `access` is **space creation** (`POST /api/spaces` → `auth.notifyGrantsChanged`, #154/#155): the creator becomes the owner of the freshly created space outside the `putMember` flow. The nudge is deliberately NOT inside `grantOwner` — that one re-confirms the idempotent owner row of the personal domain on every login/accept/agent-touch (`personalSpace.ts`) and would spam tabs; only the creation handler produces it. The initiating tab meanwhile does not wait for the round-trip: it reflects the owner grant locally (`addLocalGrant` — so that a transient failure of the session-GET does not drop the client into a phantom `none` mode), while the addressed `access` wakes the creator's OTHER tabs/PWA (#155). On `access` the client does `refresh()` (refresh `me`/role) + `reloadSpaces()` → the new space appears in the switcher, a role change is applied, a revoked non-active one is de-listed — without a reload. The event body is deliberately empty: the truth is `/api/auth/session`, not the payload. The user's stream is open on ANY of their active spaces, so we match by username, not by space.

**Space rename — the `rename` twin (#123).** When a space's slug changes (`PATCH /api/s/:space`, see `docs/spaces.md`), the server sends **`rename`** — a broadcast to all live viewers of the space by id (`notifyRenameOf(spaceId)`, the shape of `notifyMembersOf`, not the addressed `notifySse`). The client (`SyncProvider.onRename`) does `reloadSpaces()` (pulls the list with the new slug + the old one in `aliases`; `reloadSpaces` also re-canonicalizes the active slug by alias for space-free surfaces `/n/<id>`, `/`) + `refresh()` (updates `me.spaces` so that the alias-aware classifier knows the new slug). This way a second tab with the same space picks up the rename live: `SpaceProvider`'s URL canonicalization steers `/s/<old>/…` to the current slug, the switcher is relabeled — without a reload and without a false takeover. A viewer in ANOTHER space (whose stream is not on this space) will pick up the new slug on the next switch/reload — a deliberate cosmetic caveat.

Surfaces that hold their OWN snapshot of membership (the Members tab) are re-pulled on TWO signals (#121-follow-up). (1) The addressed `access` (one's own grants changed) → `refresh()` changes `me`. (2) The per-space **`members`** — a named SSE event alongside `access`, bypassing the `StoreEvent` contract the same way: `putMember`/`removeMember`, after the addressed nudge, do `notifyMembersOf(space)` — a broadcast to ALL live viewers of the space. The client accumulates it in `SyncProvider.membersRev`, and `MembersTab` passes exactly it as `reloadKey` into `SpaceMembers` → the list is re-read. `membersRev` ITSELF also covers a change to ONE'S OWN role (the broadcast reaches the subject too — they are also a viewer of the space), so there is no need to also fold `access`/one's-own-role into the key; chrome/gating meanwhile updates separately via `access`→`refresh()`→`me`, so the list badges and affordances stay consistent. The result: add/remove/role change of ANY member is visible live to anyone watching the list, without a reload. A removed user does not receive `members` (their stream is already closed by `dropSse` → takeover); the broadcast goes to the remaining viewers. The event body is empty — the truth is in `GET /api/s/<slug>/members`.

**Agent episodes — the owner-scoped channel.** `agent-sessions` rides the same named-SSE machinery and the same empty body, but it is matched by OWNER rather than by space: `notifyAgentSessionsOf` walks every live stream of that principal, whichever space each one is watching, because episodes are owner-global while `access`/`members`/`rename` are all statements about one space. The trusted authless host is its own owner (`@system`), so changing `AUTH_MODE` cannot deliver one principal's nudge to the other. Tabs refetch the owner-gated REST view; nothing about the episode travels in the frame.

**Read-only chrome for a reader.** The write permission on the ACTIVE space is a single client flag `SpaceProvider.canWrite` = `canWriteSpace(me, mode, space)` (`libs/access`), an exact mirror of the server's `can(space:write)`: role ≥ writer, one's own personal domain, or the host in `none` mode. **Host-admin does NOT count** — the server's admin-override is only for `need:'owner'` (management/recovery), not for writing data (`authz.ts`), so trusting `admin` here would mean re-showing affordances that the server would later reject. Every create/edit/delete element is gated on `canWrite`: the rail/tree "New…", the context menu (only read items remain — Open/Copy), Edit/Delete in the editor, DnD (`draggable`), the trash (restore/purge), history (`RevisionView restorable`), the Import tab, ghost-create from a broken `[[link]]`. The root protection is in `EditingProvider` (startNew/startEdit/createFromGhost/seed-`?new`), so that a reader does not enter a write flow even past the UI. A reader reads everything (notes, search, graph, feed, history, members, export) — precisely writing is gated.

Project management (mark/unmark/create — `POST/DELETE /api/s/<slug>/projects`) is also `space:write`, so `ProjectsProvider.canManage` = the same `canWriteSpace(me, mode, space)` (#121). This closes the same "affordance shown → server will reject" trap one tier above the reader role: a host-admin who is merely a reader/non-member of the active space NO LONGER sees the active Mark-root toggle / the Unmark button in `ProjectsTab` (the tree menu was already gated on `canWrite`). By contrast: `MembersTab.canManage` REMAINS `admin ∨ owner` — `members:manage` = `need:'owner'`, and the server's admin-override on an owner-need is correct there.

## Deployment: the single-instance invariant

The default is a single container; for it everything is correct. Two auth states live **in-memory, per-process**, and this is **deployment invariant v1: a single instance**.

- **The login rate limit and two-verify semaphore** (both gates — per-username+ip and amplification-per-ip) are process-local. Behind an LB with >1 instance and no shared store, an attacker round-robins the instances and multiplies both ceilings by their count.
- **SSE revoke→disconnect** tears down live sockets only on the instance where they are open. Revoking a PAT / removal from members / disabling a user on instance A will not close an EventSource hanging on instance B (it will go quiet only on the next re-authentication of the reconnect).

Horizontal scaling (several instances behind an LB, pg mode) requires a **shared store**: an attempts table in pg or redis for the limit + pub/sub for cross-instance disconnect. This is part of the Cloud/HA milestone (#76: per-tenant rate-limit/concurrency — day-one for open registration), not the default. First-run setup is already multi-instance-safe — the claim under `pg_advisory_xact_lock` (#73) lives in the shared DB; only the limit and the SSE registry remain per-process.

## Deliberate caveats

- **Tenant isolation in cloud** (the caveat closed by spike #76, canon — its security-model decisions): `can()` is primary, but one layer. The bar for opening public registration is a **three-pronged enforced second line** under `can()`: RLS on the meta-DB + an FS boundary (Landlock/namespace/uid; #74 removed process-per-space, and with it the FS and event-loop lines) + per-tenant compute isolation. A full stack/process-per-tenant is an enterprise upsell, not the default. Implementation is a Cloud milestone; until then MVP/Beta remain single-tenant self-host.
- The rate limit and the SSE registry are in-memory, per-process: the canon of the conditions and of what is needed for HA is in the "Deployment: the single-instance invariant" section. per-tenant rate-limit/concurrency is part of security model #76 (day-one for open registration).
- An owner can "probe" the existence of a username via add-member (no_such_user) — accepted for v1; users are created by an admin.
- There is no user deletion — only disable (a username cannot be freed: journal attribution and membership reference it).
- The E2E fake cannot enable auth by a runtime swap of the fixture — the mode is fixed at boot (a mirror of the real host); auth scenarios live on the second webServer.
