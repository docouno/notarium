## Read-model decorator (#60) <a id="read-model"></a>

`CachedStore` wraps any `KnowledgeStore` and normally serves `list/recent/graph` from an **in-memory snapshot** instead of hitting the engine on every request. A class-selective `list({ classes })` is the deliberate exception: it asks the engine's derived class index for the small candidate set, then projects those rows through snapshot identity/metadata and the requested `ReadScope`. A failed selective query falls back to filtering the authoritative snapshot (O(all notes), but only on the degraded path); an engine-passthrough read after a boot error uses the same identity projection. The snapshot is derived state ([P2](architecture.md#p2)): rebuilt from scratch by the boot scan, nothing in it is a second source of truth. It is kept fresh three ways:

- **write-through** — mutations through us patch the snapshot in the same call;
- **read-refresh** — reading a note re-derives its edges from the live body (#35 MVP slice: the body is the arbiter over the engine's relation index);
- **delta-poll** — external changes arrive through the engine's `changes()`.

`search` deliberately stays a passthrough: caching FTS would turn the layer into a shadow engine — exactly the boundary this task (#60) draws. The first-class directory channel is cached too, but every authoritative reconcile replaces it from `listDirs()` so external creation/deletion of an empty folder converges without a restart; if the directory walk fails, `/tree` falls back to the engine instead of trusting stale folder state.

The decorator **equips** a "bare" engine with capabilities it lacks: identity ([P7](architecture.md#p7)), optimistic writes (CAS, #50), a revision journal (#12), a trash (#79). It is also the **sole enforcer** of the class-visibility invariant (#78, [note-model.md](note-model.md#note-classes)): the discovery surfaces (list/graph/search) are scoped here, so the read-model always reports `visibility:true` regardless of the engine. A direct read by id is **not** gated — the user owns their own agent-memory. Once a request is recognized as a stable identity, every identity-capable inner boundary (read/write/move/remove and synchronous preview peek) receives the reserved identity envelope; a missing id can never fall through to a human namesake. A path-keyed engine consumes that envelope through the snapshot's authoritative id→path projection. Snapshot mutations mark the projection dirty; exact consumers publish it synchronously on demand, and bulk broadcasts publish it before announcing their notes. This keeps interactive reads exact in the middle of an import without rebuilding the whole map after every create.

Capabilities (`StoreCapabilities`) degrade honestly ([P5](architecture.md#p5)): without a meta-DB, identity and the journal run in-memory (history for the process lifetime); without a vector channel, search falls back to FTS — an optional capability, not an error.

## Phased boot (#60) <a id="phased-boot"></a>

A cold start must not hang the surfaces. Boot is phased — `cold → notes → graph → ready`:

- a cheap inventory (`changes(null)`) makes `list()`/`graph()` answer within seconds;
- a full `list()` adds creation dates;
- a `graph()` sweep adds edges.

`/api/status` and the event bus report where we are so the client loads interactively. Reads wait only on the cheap phase-1 barrier (`ensureNotes`) — never an unbounded hang: a failed boot also opens the barrier and switches reads to a passthrough to the engine. Mutations have a separate, later barrier: they are admitted only after the full-list merge, frontmatter `notarium-id` sweep, and directory seed attempt, all under one quiescent storage checkpoint. A stale list therefore cannot re-add a file/folder changed in the boot window. A phase-1 reader can briefly observe a provisional registry id; the sweep records its successor, so an operation already queued with that id resumes against the durable id. If empty-folder discovery fails, it stays a soft degradation and `listDirs()` reads the engine directly instead of trusting an incomplete cache. The boot scan is idempotent and retries with a capped backoff on an engine error; a watcher signal that arrives inside the boot window is held (re-armed) until the snapshot is ready.

## SWR graph (#60/#195) <a id="swr-graph"></a>

Shaping the snapshot into a graph is cheap, but a communities pass (Louvain) + force-layout over thousands of nodes is not (~27s for 3k nodes). So enrichment is computed **at most once per snapshot revision** and **never on the request path**:

- **cold-SWR (#195):** while there is no settled map yet, `graph()` immediately returns the bare topology (nodes/edges/degrees) and the first enrichment starts on the next macrotask; the landing pass emits `graph`, and connected clients refetch.
- **warm-SWR (#60):** once a settled map exists, the request path never again pays communities+layout — it returns the CURRENT topology (write-through is visible in the same call) dressed in the last enrichment; the recompute catches up to the snapshot off a debounce timer. The synchronous prefix of enrichment (Louvain + the first layout ticks) is deliberately **not** kicked inline — it would seize the loop while this response serializes.

`rev` ticks on every snapshot mutation (any `changed` event or a fresh edge baseline). A reset also advances a separate generation: enrichment that started against the discarded snapshot may finish, but it cannot publish positions, links, or settled state over the replacement. Promise cleanup is generation-local, so an old completion cannot clear a newer pass. `layoutPositions` warm-start the next layout so the map doesn't jump between rebuilds; a layout computed before any edges exist (0 links) is a degenerate seed, not a warm-start. The debounce is gated: under a bulk import re-enrichment is suppressed (endBulk kicks a single catch-up pass); under `stopped`/non-`ready` it is not scheduled.

The heavy pass also consumes the process-global background scheduler (#196): one turn before synchronous Louvain, then another at every existing size-dependent force-layout yield. A request arriving between ticks therefore parks the next batch until the quiet window, while the shared drip floor still guarantees progress and arbitrates with embedding workers across every space. Louvain itself is one non-preemptible unit — once entered it runs to completion — but it never starts through a closed gate. A reset/dispose aborts any parked layout wait without consuming a later drip turn, so an obsolete pass cannot keep competing with its replacement. Hosts without the scheduler keep the ordinary macrotask yields, so graph enrichment remains an optional capability rather than a hard host dependency.

## Graph derivation (#62) <a id="graph-derivation"></a>

The pure (host-agnostic) graph build lives in `core` without an engine: `buildLinkIndex` (resolution priority stable id > exact raw current path > normalized current name > slug > note-alias > folder-alias, #100), `deriveNoteEdges` (edges from a note's body), `shapeGraph` (snapshot → nodes+edges+ghosts, hidden classes excluded #78), `enrichGraph` (communities + layout in one pass, shared across all hosts). The raw-path rung keeps two legal files that differ only by case or Unicode composition aligned with the direct engine reader; a non-exact spelling still uses the deterministic normalized collision winner. Ambiguous folder-history claims are withheld rather than chosen by input order. A derived edge carries internal unresolved-target provenance through deduplication; graph shaping then allocates its ghost key outside the set of live opaque note ids and unmarked edge targets. The conventional `ghost:<target>` spelling is retained only when free, so a valid real id cannot capture an unresolved edge and a stable edge to that id can coexist with the ghost. Clustering is deterministic (stable order); layout is a server-side force-simulation with warm-start and a deterministic seed for newcomers (by id hash — reproducible across hosts). The graph's cross-cutting anchors (CAS, filters) live in the contract's context; name-resolution semantics — [note-model.md](note-model.md#note-ontology).

## Write-through and reconcile (#54) <a id="write-through"></a>

Every in-process mutation through the read-model enters fair, process-local coordinated checkpoints. The storage claim combines the stable note-id, exact source/destination paths, and folder prefixes; equal ids/paths and path↔prefix or overlapping-prefix relations conflict, while unrelated notes keep their parallel throughput. Claims derived from mutable state are re-read after waiting: if a preceding move changed a path or its owner, the waiter retains every observed resource and atomically requeues its original ticket until the claim is stable. Its ticket keeps priority over later waiters that are still queued; work that was genuinely unrelated under the old claim may already be active and is allowed to finish. The storage checkpoint spans host-owned preparation, CAS verify, path selection, the engine mutation, identity/snapshot updates, synchronous enqueue of the journal state, and host-owned project/folder registry finalization. It orders overlapping write/move/remove operations and the storage leg of restore; a folder move/delete cannot interleave with a child write, directory create, or create in its destination subtree. Folder delete re-enumerates its victims after acquiring the prefix and holds it through every tombstone plus `removeDir` — a note written through this `CachedStore` cannot appear after the initial list and be erased without history. Conflicting waiters keep arrival order across stable-claim retries, so a waiting folder operation cannot starve behind a stream of later child writes.

A direct read takes a storage checkpoint before engine I/O and its identity, preview, or edge repair. A stable note-id continues to mean that note if its former path is reused, while path/title resolvers are resolved again after earlier queued mutations. A bare-engine body can reveal a new frontmatter identity even for an already-materialized note: the first pass only discovers it, then repeats the read under a stable claim expanded with every disclosed id before applying rekey/preview/edges. Mutation admission remains closed across those passes, so neither an already-admitted forced-id operation nor a later caller can cross the identity transition, while reads of independent known notes retain narrow-claim parallelism. Read and mutation admission alternate in fair cohorts: once the opposite side is waiting, later peers cannot extend the active cohort, and mutation admission is released as soon as the narrow resource claim is queued rather than after engine I/O. An otherwise unresolved engine resolver still takes the rare global checkpoint. A cold raw-file preview fill takes the note/path checkpoint as well, so a delayed old fill cannot overwrite a newer write-through preview.

The journal append itself stays fire-and-forget for a normal save (it never fails the file write, [P2](architecture.md#p2)), but `record()` joins the per-note journal chain before the storage fence is released; a following delete therefore queues strictly after that save and awaits its own tombstone. A distinct trash-namespace fence orders the delete tombstone, restore precondition/completion, and permanent purge for the same note. Per-note trash paths keep unrelated transitions parallel; folder delete and `all` restore/purge claim the namespace prefix so membership cannot shift between offset pages. Operations that need both identity admission and trash use the fixed order **admission → trash → storage**. A trash restore owns its outer mutation-admission scope through the trash lease and nested storage write; a raw-body chase takes read admission before waiting on trash, so neither can hold one resource while waiting for the other. After either an API delete or a delta-observed external delete, cached inbound sources are re-read and their edges re-derived against the post-delete index before publication: the prior deduplicated edge cannot encode whether its body held a human target, stable-id envelope, or both. A graph reader joins the whole delete/re-derive transition, and likewise joins a delta's snapshot/re-derive/publication transition, so it sees either coherent side rather than a hybrid. Delta reconciliation takes a rare global storage checkpoint around its inventory read, snapshot patch, frontmatter sweep, and final event publication. If raw-body identity inspection is unavailable or fails for a changed path, reconciliation must read that note through the engine before choosing its journal/trash id; a previously materialized file may have received a different frontmatter id externally. Only then does it enter the exact **durable-id** trash path for a live external revision or tombstone and revalidate the transition after waiting; a background body chase therefore cannot land above a newer local delete, nor can a queued external delete survive a later re-add or quiet metadata refresh. These are two deliberately separate guarantees: an arbitrary forced-id write does not claim trash, and purge does not claim live storage.

Mutations await the full metadata/id/directory checkpoint before claiming resources; if it never lands they fail closed instead of acting on an empty or temporarily keyed snapshot. Initial graph adoption and a graph-only retry also take the global storage checkpoint, so a stale baseline cannot overwrite a concurrent mutation edge patch. A late graph failure does not trigger a second inventory scan, invalidate stable mutation readiness, or turn writes off.

The coordinator is deliberately per `CachedStore` process, matching the current single-writer self-host topology. Its guarantee covers callers entering through that read-model. The primitive itself is domain-agnostic and lives in `core/libs`; a second consumer sits ABOVE the read-model rather than inside it — the agent-memory append fences a category's whole find-modify-write window on its own coordinator instance, one per store ([note-model.md](note-model.md#agent-memory)). Same per-process boundary, same replacement seam for a multi-writer deployment; a separate instance because the read-model's own queue also carries the periodic global reconcile claim, and nesting one inside the other would let a fence wait behind a claim that conflicts with everything. The global claim is reserved for boot/rescan/delta/graph snapshot checkpoints and the rare read whose engine resolver cannot yet be mapped to a note/path; ordinary mutations retain narrow claims and independent-note throughput. A removal claims its victim plus every current inbound source whose cached edge it will re-derive. It also owns a derived prefix for each target; a graph-visible body write owns a source-specific child path under every live target resolved from its new content. Thus it cannot introduce a phantom inbound edge after the delete sampled its sources, while two independent writers linking the same popular target do not conflict with each other. If a source body cannot be read, the post-delete identity map is fed into the engine and only that source bucket is adopted from its fresh graph; replacing the whole baseline under this narrow lease would erase unrelated concurrent writes. After either waiter runs, stable-claim retry re-evaluates the changed resolver set; independent deletes remain parallel too. A future deployment with multiple writer processes must replace this with a storage/distributed lease at the same seam; serializing every ordinary mutation by space is not an acceptable fallback. Likewise, an out-of-band filesystem writer can still create a file between folder victim enumeration and the engine's recursive directory removal; the process-local fence cannot see it. Closing that external-writer window requires a storage-conditional/lease primitive, not a stronger claim made by this in-memory coordinator.

Graceful shutdown first closes mutation admission, wakes cold waiters fail-closed, joins the active boot/reconcile generation, and drains every active or queued admission cohort. A public read that was still waiting at stop fails before touching the inner engine. Shutdown then crosses the trash and storage queues, drains coordinator-queued external history work and any graph enrichment already using the snapshot, and closes the inner engine. `settle()` waits for that close before taking the final journal/identity tail snapshot, so a mutation released by the shutdown checkpoint cannot enqueue durability work after the drain. It also joins an already-running boot or reconcile, so a caller cannot observe durability completion while that reconcile is still preparing external revisions.

A mutation patches the snapshot optimistically in the same call. Delta-poll catches up external changes: the engine's inventory only knows the day, so a fresh `modifiedAt` is taken from the poll clock (the change happened on our watch) while an old day comes from the engine (an edit made while we were down) — an "honest modifiedAt". A note's title is a projection of its body's H1: `promoteBodyTitle` normalizes them consistently across every engine and the client.

Create-collision policy is resolved HERE rather than in the engines ([note-model.md](note-model.md#create-collisions)). The read-model refuses from its snapshot, which is the only layer that knows the occupant's identity, so the error can name the note to open; the engines refuse from disk truth underneath and stay the arbiter. `uniquify` needs both: the free name is chosen from the snapshot **before** the storage claim — so the checkpoint fences the path actually written, and the stable-claim retry above re-derives it if a queued move shifted the destination — while an engine refusal (a file the index never saw, or a concurrent peer that won the same name) drives a retry onto the next one. Each attempt is a fresh claim, which is what keeps concurrent duplicates from agreeing on a destination.

## Cooperativeness under load <a id="cooperative"></a>

Three subsystems damp storms on the shared SSE bus by reading LAZILY / coalescing instead of fanning out one event per subscriber:

- **bulk coalescing (#192):** a streaming import lands thousands of notes; a per-note `changed` would fan out to every space subscriber. beginBulk/endBulk buffer the upsert/removed ids and broadcast a single merged `changed` on a timer; the per-note durable identity flush and the inner engine's id→path projection are deferred to the same batched boundary; the engine's background embedding is paused. An id is both durable and exactly addressable BEFORE a client learns of the note, while an interactive exact read in the middle of the import synchronizes the dirty projection on demand. Re-entrant (a depth counter).
- **watch cadence (#146):** the external-change watcher is only an invitation ([P3](architecture.md#p3): the truth arbiter is a full rescan). A trailing debounce coalesces a burst into one reconcile after quiet; a max-wait cap keeps a never-quiet stream (a bulk import, our own write-through fsyncs, a churning log) from deferring the reconcile forever. The periodic-backstop cadence is **derived**, not stored (watched → an operator-tunable rare backstop; unwatched → a cap so we never poll slower than before the feature).
- **index-progress (#199):** the engine's embed-backfill nudges us as the vector queue drains; a trailing throttle coalesces many-per-second ticks into one `status` frame with the LATEST counters (coalescing loses only the intermediate values; the final pending-0 frame still arrives).

A streaming import also marks itself busy on the **process-global** scheduler (#196) so that embed-backfill and graph enrichment in OTHER spaces yield to it (per-space suspendBackground only quiets its own loop). All background consumers share one drip budget while traffic is continuous; when the process reaches its quiet window they may progress together, so the scheduler does not manufacture a serial queue on an idle host.

## Identity (P7) <a id="identity"></a>

`IdentityRegistry` is an in-memory `filePath ↔ note-id` registry with write-behind persistence. Lookups/mutations are synchronous (the read-model patches the snapshot synchronously), flushes batched-async and serialized through one tail: overlapping timer/manual/settle flushes cannot publish older state after newer state, callers join the active writer, and dirt added while it is in flight becomes the next batch. A failed batch is merged back without overwriting a newer live binding or tombstone. Losing the flush tail still degrades softly ([P2](architecture.md#p2)): auto-ids regenerate on the next boot, materialized ids are re-adopted from the files themselves. The meta-DB is the first tenant of the persistence seam (the `IdentityPersistence` port lives in core, the driver at the edge, [P9](architecture.md#p9)). An id survives move/rename (identity on the id, not the path); a frontmatter claim on an external move (remove+add) re-adopts the tombstoned id.

## List layer <a id="list-layer"></a>

The pure derivations of the list surfaces (Feed/tree/buckets/tag-facet) live in `core/listing`, not in the HTTP transport: the server only calls them. The tree is **server-authoritative** — the directory channel (#97) holds every visible folder, empty ones included (never-prune), and is served from memory, not an FS-walk per request. The one inclusion language of the facets (folders #93, tags #109, class) — [contract.md](contract.md#filters); the tag axis and normalization — [note-model.md](note-model.md#note-ontology).
