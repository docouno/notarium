# Dev Environment

This is the portable development-environment contract for this repository.

## Commands

- Parallel task checkouts use Worktrunk. `wt switch --create <type>/<slug>` creates
  an isolated sibling checkout. User-configured entrypoints call the shared scripts
  from the primary worktree, so they also bootstrap branches that predate the scripts:
  copy the local environment, reserve a free dev port, assign a unique Compose project
  and start `make dev`. `wt remove` stops that checkout's stand before deletion.
  One-time setup, path layout, lifecycle and recovery are in [worktrees.md](worktrees.md).
- `make deps` installs npm dependencies for the current checkout when `node_modules` is missing or stale. **No-embedder by default**: it installs every workspace except the deps-only carrier `@notarium/engine-vector`, so the ~360 MB CPU embedder (`onnxruntime-*`, `@huggingface/transformers`) is never downloaded. `sqlite-vec` (200 KB) is not part of that exclusion — it is an ordinary `@notarium/engine` dependency and ships in both profiles, so the vec0 suites run on a default checkout. A no-embedder checkout degrades to FTS at runtime; the dev overlay defaults `VECTOR_SEARCH=off` to match.
- `make deps-vector` installs the same dependencies **including** the embedder through the canonical `deps:full` script — use it for embedding work, the license corpus, or anything that needs the real model rather than a mock. The script pins onnxruntime-node to its CPU-only payload; a bare `npm ci` instead downloads another ~302 MB of unused CUDA/TensorRT providers from NuGet. Pair the full install with `VECTOR_SEARCH=on` in `.env`.
- Switching a checkout **back** to no-embedder (to reclaim the ~360 MB after a `make deps-vector`) needs `rm -rf node_modules && make deps`: plain `make deps` is idempotent (it no-ops when the workspace links already resolve) and so will **not** prune an already-installed embedder. A fresh worktree gets the lean profile automatically.
- `make doctor` validates the environment before a dev server or test stand uses it: host workspace links, Docker Compose config, dev-image build, `ps` availability in the container, writable Vite config directory, and root-level workspace dependency resolution.
- `make dev` runs `make deps`, prepares bind volumes, builds the dev image, and starts the HMR stack.
- `make down` stops and removes the current checkout's stack.
- `make test-coverage` builds the unprivileged Docker `test` stage on top of `builder` and runs the full Vitest coverage suite there. That full-dependency, glibc environment adds what the default profile leaves out — the native embedder the license corpus reads; the `node` user keeps permission guards meaningful; and building the parent stage also proves the production build without mutating the dev stand's bind-mounted `node_modules`. Vitest uses the repo profile (CPU ceiling 4, four workers, coverage processing 4); larger runtimes never expand it and smaller runtimes clamp every component. The same run writes text/JSON/HTML plus Cobertura, including on failure. The standalone target still owns and removes its image; a full `make checkup` retains the exact image through the PostgreSQL leg instead.
- `make backup-smoke` is the destructive backup → fresh-volume restore drill, and the ONE orchestration owner of it for both this checkout and CI. It builds two stages of `docker/Dockerfile` — `runtime` (the appliance under drill) and `builder` (the workspace sources the durable-import fixture needs) — and tags each with a name no other checkout and no other run can be holding: `notarium-backup-smoke:<checkout>-<run>-runtime` and `…-fixture`. The tag is not how the images are addressed — `--iidfile` hands the driver a content id, which no neighbour can retag out from under a live run — it exists so the run OWNS its images and gives them back; the recipe drops exactly its own two tags on exit, including on SIGINT/SIGTERM/SIGHUP (a SIGKILLed run is the one path that cannot, and its leftovers are named rather than dangling, so a routine `docker image prune` will not reclaim them either). **Removing an image by ID is what the target must never do**: an id is shared by whoever else holds those bytes, and deleting it takes the image out from under them, whereas dropping a tag only untags while another reference exists. Leaving the builds untagged was the wrong answer: `--load` writes a *dangling image into the local image store*, not into BuildKit cache, so `docker builder prune` never reclaims it, and buildx exports a fresh manifest digest per build — so even an unchanged tree added another dangling entry on every single invocation, with nothing in the repo owning its removal. (Those entries share layers, so the wasted disk is far below the sum of their reported sizes; what grew without bound was the entry count.) `--load` itself stays required — without it a non-default Buildx driver leaves nothing runnable behind. `BACKUP_SMOKE_RUNS=3 make backup-smoke` repeats the drill on the SAME two image ids; the value is validated before either build, because a gate that silently runs zero times is worse than one that fails.
- The drill's durable-import fixture runs as a one-shot container off that `builder` stage (`test/backup/durableImportFixture.ts`) and stages its upload + enqueues its queue row through the same `dataPathsFromEnv` / meta-DB / staging seams the server composes. **The runtime image gains no fixture entrypoint and no test-only API** — that is the reason for the second stage rather than a flag on the appliance.
- `make checkup` is a thin entry to one versioned session driver. It snapshots tracked plus untracked non-ignored worktree bytes (with explicit private/generated deny rules and an allow-list for external visual PNGs), writes a manifest/content digest, and executes static checks from a disposable work copy; later checkout changes cannot mix into the run. The static prefix deliberately owns one lean install, while the production coverage image owns its separate full install/build. Before the lease and every heavy consumer, a closed-world verification rejects changed, removed **or added** snapshot bytes. Heavy phases hold one repository-stable Docker-daemon lease with owner/heartbeat/timeout/stale recovery, use session labels plus immutable container/image identities, and leave a JSON report under `test-results/checkup/` with primary phase exits separated from lease/cleanup diagnostics. Recovery removes only the exact stale container it inspected, never a successor; candidate cleanup refuses foreign resources rather than deleting by name. The owner updates its lease heartbeat through one coalesced `docker cp` at phase changes and a one-minute cadence. An unresolved timed-out create is reported as incomplete ownership instead of claiming cleanup around a finite guess. Coverage receives the resolved effective profile, builds the production PWA-on/test image once and feeds it to PostgreSQL while the one-worker browser contour runs in parallel. Backup-smoke remains a following standalone ownership phase. Browser resolves the pinned Playwright tag once to an immutable local image ID, then owns one compatible install and one manifest-bound PWA-off build reused by fake, real and installed visual baselines. Visual remains an explicit skip when external PNGs are absent. Standalone `make test-coverage`, `make test-pg`, `make backup-smoke` and `make test-browser` remain self-contained, share the private-byte copier deny set and do not require a prior session.
- `make test-pg` starts an isolated ephemeral Postgres and runs the shared meta-DB behavioral contracts plus migration regressions from `node:24-slim` on the private database network. The lean dependency install and source snapshot live only in a disposable Docker workspace volume. It uses a checkout+invocation-specific Compose project, exposes no database port on the host, and removes both database and workspace volumes on exit. Direct `npm run test:pg` is the CI/expert entrypoint when `TEST_PG_URL` already points at a disposable database; without that env the live suites skip under ordinary `npm test`.
- `npm run meta-migrations:check` validates the ordered SQLite/PostgreSQL SQL pairs and their tracked checksums without opening a database. `npm run meta-migrations:checksum -- 0001_name` prints the checksum for a newly added pair but never rewrites the manifest. The migration policy and ledger protocol are canonical in [meta-db.md](meta-db.md).
- `make test-browser` remains the standalone clean-snapshot Playwright path. Inside a full checkup the session driver instead copies its already-verified source once into a Playwright-compatible volume, installs once, builds web once with `VITE_PWA=off`, stamps every dist byte with source/image identities, and makes fake/real/visual verify that manifest before their servers open. Production PWA-on dist is never accepted as this browser artifact. Playwright retries may still collect a trace, but `failOnFlakyTests` makes any retry-pass red. The real-stack wrapper starts both seed and long-lived server through the fenced Node executable; readiness timeout or readiness-port bind failure stops and awaits that child before deleting its data root, so a failed attempt cannot poison the next one with an orphan on the same port. All three Playwright configs preserve an existing desktop bus and otherwise pass `DBUS_SESSION_BUS_ADDRESS=disabled:` only to the browser child: without it Chrome mutates the process environment during launch, beside an [upstream-documented TSan race](https://chromium.googlesource.com/chromium/src.git/+/2fc330d0b93d4bfd7bd04b9fdd3102e529901f91), and can die natively inside `getenv`. The pinned image also carries Node 24.15, where browser builds have produced native V8 deaths under contention. Every browser-side build, budget check, runner, preview composer and long-lived TSX server therefore uses `node --no-maglev` as a narrow best-effort fence. It is not a retry or a root fix: [the related Node 24 corruption](https://github.com/nodejs/node/issues/64841) is not fundamentally Maglev, and the durable fix is Node [26.8.0+](https://nodejs.org/en/blog/release/v26.8.0) or a future fixed Node 24 image.
- `make import-bench` drives 10 000 Markdown members (`NOTES=` trims the corpus) through the production composition — a real `createServer` over localfs+sqlite with embedding off, the real HTTP route, the real durable job — into a data root inside the container, while a parallel reader keeps hitting the server. The default `SOURCE=archive` preserves the Markdown-ZIP gate; `make import-bench SOURCE=folder NOTES=10000` sends the same corpus as real multipart entries through the streaming folder bridge before the common planner/writer. `SOURCE` is passed into the Docker invocation and printed in the result, so a requested folder run cannot silently measure the archive default. Both modes require one upload to create one job. The target uses the same disposable snapshot+volume as `make test-pg`, so the numbers come from a known Node and a clean dependency profile and the checkout is never written to. Its **correctness** half is a test — exact totals, the reproduced tree, copy identity, rewritten links (both of a note's live exact links repointed, its fenced copy still the authored bytes), the bounded result, monotonic progress, reads answered inside the import window with no stretch of it longer than a third going unanswered, and a cancel that stops a live import strictly part-way through its corpus all exit non-zero on failure. The elapsed/RSS/event-loop numbers are diagnostics, never thresholds, because a duration pinned to one machine is a flaky test wearing a benchmark's clothes — and the consequence is stated rather than glossed: the read check proves the server never stopped answering, NOT that it stayed responsive, so a run that got slower or lost the write loop's cooperative yield passes it. Cooperativeness regressions are read off `eventLoopMaxMs`/`parallelReadP99Ms`/`parallelReadMaxGapMs` by eye against the recorded numbers ([import.md](import.md#resource-limits-on-a-markdown-tree-302)). `npm run bench:import-markdown-tree` is the same harness on the host.
- `make seed CASE=<name>` (re)fills the stand from a declarative catalog case — `make seed-list` to list them, `make seed-coverage` for the coverage matrix. It stops the stack, wipes the volumes, seeds the real engine **in-process with a backdated journal** (so the heatmap/feed/trash look real, not one "today" spike), and restarts. **Default login on the seeded stand: `admin` / `admin`** (override `SEED_USER`/`SEED_PASSWORD`; printed as a banner at the end). See [seeds.md](seeds.md).

## Invariants

- **One declared toolchain, enforced by npm itself.** `package.json` declares the npm version once (`packageManager`) and the floor both it and Node have to clear (`engines`); `.npmrc` sets `engine-strict`, which turns that from a warning into a refusal. Nothing in the repository re-checks it: an install below the floor stops with `EBADENGINE` before it resolves anything. What that buys is the lockfile — below npm 11.18 a root `overrides` entry behind a workspace link is dropped from the lockfile while the installed tree stays correct, so the damage only shows up in what gets committed. Note what is enforced is the FLOOR, not the exact version: an npm newer than `packageManager` names installs fine, and the pin is what keeps the contours on one version anyway. Contours whose base image carries an older npm install the declared one before they install anything (both `docker/Dockerfile` stages, the CI lanes that run `npm ci`, and the four containerised `make` runners); the pin is self-verifying, since dropping it makes the very next install refuse — which is why `.npmrc` is copied into the image next to the manifests rather than arriving later with the sources.
- Each checkout owns its own root `node_modules`; the dev container bind-mounts it as `/app/node_modules`. Because the dev container reuses the host `node_modules`, the host install profile (`make deps` vs `make deps-vector`) decides whether the dev stand can embed.
- The embedder is an **optional install unit**, not a runtime fork. `@notarium/engine-vector` is a deps-only carrier workspace (no code, like `@notarium/desktop`); the engine loads `@huggingface/transformers` through a dynamic `import`, so excluding that one workspace at install time (the default `make deps`) skips the whole subtree without touching any platform-native binaries the toolchain needs. The Docker image ships the full install so `-e VECTOR_SEARCH=on` works without a rebuild.
- **The install unit is the embedder, not vec0.** `sqlite-vec` is a plain `@notarium/engine` dependency: 200 KB, present in every profile, still `createRequire`d lazily so a platform without the native binary (musl) degrades rather than fails. It was inside the carrier until #317, and the cost was invisible — the vec0 gate stayed closed on every lean run and on every default checkout, so 47 tests that need only a mock embedder went unexercised until a change reached `main`. What is genuinely excludable is the CPU embedder subtree — `@huggingface/transformers` plus its onnxruntime backends, ~360 MB measured — and only that. onnxruntime-node's optional CUDA/TensorRT providers are neither part of this capability nor installed.
- Skips in `npm test` are **environment gates, not disabled tests**, and the run says which: a suite whose gate is closed is skipped under a name carrying a `[gate: …]` marker, and `test/skipSummary.ts` folds those into one line — `⇢ N skipped: … postgres (make test-pg), … full deps (make deps-vector)`. The reason is declared next to each gate (`vectorGate.fixture.ts` for vec0, `postgresHarness.ts` for the live database, `test/release/fullDepsGate.ts` for the license corpus case that reads installed native packages), so a gate added later is summarized for free. An `unlabelled` group in that line is the signal to look at: it means a test was disabled rather than gated. `make checkup` opens every gate.
- `npm test` needs **`make` on PATH**: `test/backup/makefile.test.ts` drives the real `make backup` / `make restore` targets to pin the archive-publication durability contract (partial retention, hard-link commit, rollback), with `docker` stubbed. Any container running the suite therefore needs a toolchain image (`node:24`, not `node:24-slim`) — in slim the suite fails with an ENOENT on an archive that was never produced, which reads as a product bug rather than a missing binary.
- The dev image uses the Dockerfile `builder` stage, whose apt layer carries two declared packages: `procps`, because `concurrently -k` shells out to `ps` while shutting down child processes after a failure, and `perl-base`, which owns the `/usr/bin/perl` the engine's atomic directory no-replace runs through ([release](release.md#platform)). Drop either and the loss says nothing about its cause — the first only at shutdown; the second closes every `[gate: atomic no-replace …]` in the suite and, past them, turns the engine's folder-move contract red, because the store-contract suites publish directories outside any gate. Both read as a machine that cannot rather than as an image that no longer carries the package.
- `packages/web` is bind-mounted as a whole writable directory. Vite writes temporary bundled config files beside `vite.config.js` (`vite.config.js.timestamp-*.mjs`), so file-mounting only `vite.config.js` is not safe.
- Vite cache lives outside `packages/web/node_modules` via `VITE_CACHE_DIR=/tmp/.vite/web`; `/app/packages/web/node_modules` is hidden behind an anonymous volume so package-local host dependencies cannot shadow the checkout root dependencies.
- Dev build identity falls back to `null`/empty commit when git metadata is not available in the container; missing git must not produce noisy shell errors.

## Troubleshooting

If an existing checkout carries an older dev overlay, it may restart-loop with `EACCES: permission denied, open '/app/packages/web/vite.config.js.timestamp-*.mjs'`.

Update that branch to a base that contains the current dev-environment contract, then run:

```sh
make doctor
make dev
curl -sS http://localhost:$PORT/api/health
```
