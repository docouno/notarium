# Import from Claude / ChatGPT / memory.json (#11)

Pull an existing knowledge base — claude.ai, ChatGPT, and MCP memory-server exports — into a space in a single upload. Import is the mirror of export (#17), inverted: export reads the engine's on-disk truth and streams it, import **parses on the host and writes through the port**. The parsers are pure (format → notes), and writing goes through the ordinary write-path (`store.write`) — no separate backend is needed, import works on any engine.

## Data path

1. **Parsers are pure functions in `core`** (`importer/`): `string → ImportNote[]`, zero IO/store, fixture-testable. A normalized `ImportNote { title, body, directory, tags?, noteType?, createdAt?, frontmatter?, fileName, source }` (provenance via `tags`; raw authored metadata via `frontmatter`; `source` also governs the memory destination). The format is detected by content (`detectFormat`/`detectSingleObject`), not by file name (everyone ships a `conversations.json` file). The parsers cover these formats:
   - **claude-conversations** (`conversations.json`, array) — one note per conversation, messages as `### Human/Assistant (ts)`, attachments as `**Attachment: <name>**` + fenced, uploaded files (binary references `file_name`/`file_uuid` with no text) as a `**File: <name>**` breadcrumb (provenance; the bytes wait on the attachment-class seam, same as export). **Empty messages** (export ships an envelope with no text/content) do NOT print an orphan heading, and **a conversation without a single renderable fragment does not become a note** (#113 — a real Claude dump carries empty envelopes; over 150 dialogs, 24 fully empty, 0 content loss) — the number skipped goes into the per-file warning. Same on the chatgpt side (an empty/voice/asset-only dialog → skip).
   - **chatgpt** (`conversations.json`, array) — a conversation is a `mapping` graph; we linearize it with a pre-order DFS from the root (`parent==null`). **The shape of the graph edges (#113)**: the classic export carries explicit `children` arrays (branch order is encoded), but the CURRENT openai export (2026) is a **parent-pointer tree**: every node has a `parent`, and `children` is absent entirely. A DFS over `children` then never descends below the root (the root has `message:null`) → **every body comes out empty** (the main #113 bug on real data). The fix: when no node has explicit `children`, `childrenOf` reconstructs the edges from the `parent` pointers, sorting siblings by `create_time` (the key order in `mapping` is not chronological), so the transcript reads in time order. **Text extraction**: `content.parts` in the current export is often OBJECTS (`{content_type:'text',text:'…'}`/`{type:'text',text:'…'}`), not strings; `partText` reads both strings and `part.text`/`part.content` (the naive "strings-only" approach zeroed out ALL bodies — a real-data bug). **Visibility filter** (`isVisible`, not just `is_visually_hidden`): we drop system (except `is_user_system_message`), the `tool` role, internal content_types (tether/thoughts/reasoning_recap/system_error), and assistant messages with `recipient≠'all'` (tool calls) — otherwise service noise leaks into the body. code→fenced, with a fallback to `content.text/result/content`. The modern export also shards the history (`conversations-000.json`…`-025.json`); each shard is a self-contained JSON array of `mapping` graphs, and detection/streaming handle them as ordinary ZIP members.
   - **memory-json** (`memory.json`, **JSONL**) — one note per entity, observations→`- <obs>`, outgoing relations→`- <relType> [[target]]`. Wikilinks → edges of our graph fall out for free. This is the MCP memory-server (`{entities,relations}`), NOT Claude's `memories.json` (see claude-memory).
   - **claude-projects** (`projects.json` array OR `projects/<uuid>.json` single object, #113) — a project folder: docs in `docs/`, custom instructions in `prompt-template.md`. Claude's evolved export ships a project file-by-file (one object per file) rather than as an array — `parseClaudeProjects` accepts both forms, and single-object detection is `detectSingleObject`.
   - **claude-memory** (`memories.json`, array, #113) — the Claude account's memory: markdown blobs under `*_memory` keys (today `conversations_memory` — an "about the user" summary; `projects_memory` on some accounts). One note per `*_memory` blob, `source:'memory'` → the memory-destination option (folder/space/skip) governs it the same way as memory-json. NOT an entities/relations graph.
   - **claude-design-chat** (`design_chats/<uuid>.json`, single object, #113) — a design/artifact chat: `messages` (not `chat_messages`), each with `content` = `{role, content:<text>}` (the text nested one level down). One chat → one note, rendered like the transcripts, grouped under `design-chats/<project>`.
2. **The host service** (`server/services/import/`) — **streaming, bounded memory at any archive size**. The upload is streamed to disk into a temporary file (not a Buffer); ZIP members are extracted one at a time by stream (`yauzl`) into temp files; a JSON array is parsed **element-by-element** (`stream-json` + `stream-chain`, one conversation at a time), JSONL line-by-line (the memory graph is bounded by the graph size, not the file); each note is written before the next is pulled (backpressure). **Single-object members** (`projects/<uuid>.json`, `design_chats/<uuid>.json`, #113) are read in full — they are small (size-capped by the same limit), and `detectSingleObject` picks the parser. Peak memory is on the order of one conversation plus the write buffers, regardless of size. A single Claude archive imports ALL recognized members (conversations, projects, memories, design-chats). **A silent skip is only for the provably-non-importable** (`users.json`, set `SILENTLY_IGNORED`); any OTHER JSON member that is not recognized goes into the summary as `format:'unsupported'` with a warning — data loss is visible, not silent (#113). The summary is `{imported, skipped, failed, files[], errors[]}`.

> **Why streaming is mandatory, not "just raise the limit".** The synchronous path (`toBuffer`+`JSON.parse` of the whole thing) dies on a real export: a JS string cannot be longer than ~512 MB (V8's hard limit), so a `conversations.json` from a 600 MB archive (1–2 GB uncompressed) crashes even `buffer.toString()`, before parsing — no matter how much RAM you give it. Streaming removes this: parsing is O(1) per element. Measured: a 625 MB file (>512 MB, the old path fails with `Cannot create a string longer than 0x1fffffe8 characters`) imports into 1000 notes; peak RSS depends on the SHAPE (count×note size), not the file size.

## Durable import via the jobs layer (#191)

When the host carries a meta-DB (the norm for self-host), import is by default a **durable job** — the second consumer of the [jobs layer](jobs.md) after async export. The synchronous flow (below) holds the request for the entire write, and a dropped connection / closed tab / server restart loses the progress. The durable path removes this: the upload is streamed into a **staging store** (durable, `<DATA_DIR>/jobs/imports` — the [single data-root](architecture.md#data-root)), a `kind: import` job is enqueued, and a background worker runs the **same** `runImport` (the bounded-memory core above) off-request. Close the tab, lose the connection, survive a restart — the import lives on; the client sees phases/progress and the outcome.

- **Enqueue = upload.** `POST /api/s/:space/import` (authz `space:write`) — the multipart upload is streamed into staging (`<space>/<jobId>.import`, `ImportStagingStore`), then `jobs.enqueue({kind:'import', params:{uploadRef,filename,format,root,skipExisting,memoryMode,sourceModifiedAt}})`, and the response is **202 + Job**. `sourceModifiedAt` is the validated ISO projection of the optional multipart `lastModified` field; it remains absent when the field is omitted, unknown or invalid. The order is **stage→enqueue**: the row becomes claimable only once the file is fully on disk (a worker will not pick up a half-written source).
- **Handler.** `createImportHandler` resolves the space store, reads the staged upload from disk, extracts ZIP members into an **ephemeral** per-run temp (re-extractable — not durable), and runs `runImport` with `ctx.signal` (cooperative cancellation) and `onProgress → ctx.report({done, phase})`. There is no artifact — the outcome (`ImportSummary`) rides in `job.result`.
- **Progress.** `done` = the number of notes written (a live counter), `total` = null (the number of notes in the ZIP is not known in advance) → an indeterminate bar + phase. `uploading` is a client-side label during the byte upload (before the 202, there is no job yet); the server's `job.phase` goes `writing`→`done`. Embedding/indexing is **outside the job**: bulk mode drains them in the background after the write (#81/#197, indicator #199), and the job terminates at "notes written".
- **Cancellation/resilience.** cancel-only (cooperatively, like export; we do not do pause/resume). At-least-once idempotency rests on the deterministic `fileName` — a re-run after a crash overwrites the same files. A deterministic content error (an unrecognized upload, `ImportError`) → a **terminal fail with no retries** (`TerminalJobError`); a transient failure (I/O, crash) is retried.
- **Endpoints** (shared with export, the job belongs to the principal who enqueued it): `GET …/jobs?kind=import` (the principal's list of imports), `GET …/jobs/:id` (status polling), `POST …/jobs/:id/cancel`. Progress via two channels: the `job` SSE event (owner only) and polling — whichever comes first. Import has no download handle (no artifact).
- **Staging cleanup.** The handler does NOT touch the upload (it is needed on retry/reclaim); it is swept by a **row-aware sweep** on the maintenance runner's cadence (`onMaintenance` → `sweepOrphans`: delete if the job is terminal/absent, with an age threshold over the µs stage→enqueue window) + `removeSpace` on a space purge.

The Import tab's **UI** is driven by the single durable path (a mirror of Export, `useImportJob`): upload → an indeterminate progress bar with a phase and a live counter + "Cancel" → and, when ready, a summary from `job.result`. Leaving the tab and coming back is safe: on mount the hook re-attaches to the principal's latest import (`GET …/jobs?kind=import`) — an in-flight one keeps reporting progress, a finished one shows the summary.

**Degradation.** On a host without a meta-DB (none-mode) there is no jobs layer: `POST /import` serves the synchronous streaming path below, and the `jobs` routes 404. Not two parallel paths for one tier — degradation by capability, like sync export.

## Wire and UI (synchronous fallback)

The synchronous path (none-mode) remains as a fallback: the same `POST /api/s/:space/import` (authz `space:write`) — a **multipart** upload (binary, bypassing the zod body boundary, like the export stream), and the response is a **hijacked NDJSON stream**: periodic `{type:"progress",imported}` (heartbeats keep the connection alive past the proxy's idle timeout and provide a live counter), then a final `{type:"done",...summary}` (validated by `ImportResponse`) or `{type:"error"}` (an unrecognized/failed upload). The result is **in-band** (status 200 as soon as the stream starts). The client distinguishes the modes by the response: **202 → durable Job**, **200 → NDJSON stream**. An optional text field `format` forces the parser. The upload limit is 2 GB (streamed to disk; disk is the boundary, not RAM). Exceeding it → 413. Every N notes the import drains the journal's write-behind (`store.settle()`) so that the #12 queue does not grow without bound on large imports.

Import parameters (multipart fields BEFORE the file — `req.file()` sees only them; shared between the durable and sync paths):
- `root` — the root folder under which the default structure is nested (`<root>/conversations/chatgpt/…`); empty = the space root. Untrusted and structurally normalized as a storage address. An exact legacy POSIX-only root is usable only when it already exists; every component the root itself would create must be portable. The server parameter is ready and tested, but **not exposed in the current UI** (the input field was removed as inconvenient; a proper folder-picker is the next step).
- `skipExisting=true` — on re-import, SKIP notes whose path already exists instead of overwriting (the "I topped up updated history — don't overwrite" case). Implemented via `WriteInput.ifExists:'fail'`; a caught `note_already_exists` → the `skipped` counter. Without the flag — `ifExists:'overwrite'`, stated explicitly because import is the ONE create in the product allowed to replace an occupied path ([note-model.md](note-model.md#create-collisions)); every other channel refuses by default, and `overwrite` is not reachable from the wire.
- `memory=folder|space|skip` — where memory.json entities go: `folder` (visible user-doc notes under root, the default), `space` (the space's agent-mount `.notarium/memory` via the host-internal `targetClass:'agent-memory'` — hidden from the tree/feed by the #78 visibility checkpoint, reachable by the agent through recall; this is a space mount, NOT the global personal domain #13), `skip` (do not import).
- `lastModified=<epoch-ms>` — the optional source-file mtime sent by markdown DnD. The route accepts only a finite positive instant no more than five minutes in the future, stores its ISO projection as durable-job `sourceModifiedAt`, and threads it through the synchronous path identically. It is a date fallback only for a bare forced `markdown` upload; ZIP members and every other import format ignore it.

UI — the **Import** tab in the space settings (`/s/:space/management/import`, a mirror of Export): each option is a separate `SettingsSection` (title+description). A file picker, a **Skip existing notes** section (a switch), a **Memory entries** section (a folder/space/skip segment, default skip). The durable path (see above, `useImportJob`) drives progress/phase/cancel/reconnect and the summary from `job.result`; in the none-mode fallback the same component drives the NDJSON stream into the same shape (a synthetic job). Notes flow in through the ordinary write-path → the tree/feed update on the `changed` SSE event.

## Drag-and-drop of text files (#223)

"Dropped a file into the window — got a note" — a second entry into the SAME pipeline (the durable job #191 / sync fallback), not a separate backend. The UI side lives in `docs/drag-and-drop.md §10`; here is the import side.

- **The `markdown` format** (`core/importer/formats/markdown.ts`, `markdownFileToNote`): a dropped `.md`/`.txt` → ONE note, the file body = the note body (not a transcript). `fileName = slug(basename)` (idempotency by FILE), `directory=''`, `source='file'` (no provenance tag). `.txt` is a sub-case. The file's **own frontmatter is its own data** — see the next section.
- **Force, not detect.** DnD sends `format:'markdown'` — the extension is the signal (an md body may begin with `{`/`[`). On a force, the stream path reads the file in full (`TEXT_FILE_CAP=64MB`) bypassing the `{`/`[` dispatch (`processTextFile`). The job/sync run exactly this `runImport`.
- **Where it lands** — the `root` parameter (the drop folder): a note with `directory=''` lands directly in `root`. The client resolves by zone (see §10): a drop on a **folder in the tree** → that folder; a drop in the **content zone** → the folder of the open note, otherwise the scope root. Name conflicts — `skipExisting:true`.
- **Opening after import.** `ImportSummary.created[]` (the ids of created notes, capped) rides in BOTH carriers (sync `done` and `job.result`); the DnD client opens `created[0]` on a drop of ONE file (`noteRoute`). Multi — we do not jump, the notes flow in over SSE. A multi-drop = N imports (staging #191 — one upload per job).
- **Phasing.** v1 is text (`.md`/`.txt`/…); non-text is rejected by the client. The target is a maximum of formats into md (html→md, docx→md) over the same seam. ZIP-of-text and folder recursion (`webkitGetAsEntry`) are pipeline-ready (the text branch is already in the stream), but not in v1.

### The dropped file's frontmatter is the author's data (#280)

Notarium is file-first: the user brings their own `.md`, and the YAML block on top of it is **their metadata, not service noise**. v1 stripped it wholesale, so a dragged-in vault arrived with no tags, filename titles and every note dated "today" — precisely the things that made the archive worth keeping. Import now **lifts what it models and carries the rest**.

- **Lifted into typed channels** — `title`, `tags`, `type` (→ `noteType`), and the creation date. `tags` reads the three shapes a real file carries (block list, flow list, comma scalar) and peels a hand-written leading `#`; hierarchy and case are left alone (`foldTag` folds at read time, non-destructively). Absent tags stay `undefined`, not `[]` — the write channel's `[]` means *clear*.
- **Preservation has an explicit structural boundary.** The shared reader recognises conservative top-level **plain mapping keys** (Unicode and spaces are fine) and carries their raw entry lines through the host-internal `WriteInput.frontmatter` channel. An unmodelled value below such a key — a nested map or a plugin-owned shape — can therefore survive without being reinterpreted; standalone supported comments survive too. Quoted or explicit keys, complex mapping-key syntax, merge keys, document directives/fences, root sequences and other structural non-mapping/keyless forms are rejected visibly. Refusing a shape whose ownership we cannot prove is safer than relocating it into a different YAML structure while claiming preservation.
- The engine merges accepted carried entries under the existing block and **below our typed fields**. What is *not* carried: **`notarium-id`** (an identity claim is not the author's to donate — the write path mints ours), **`notarium-created`** (our reserved resolved-mtime companion), **`title`** (the write path asserts its own unconditionally, so a carried copy would be replaced anyway), and a lifted key **once its value is really in a typed channel** — otherwise it would be asserted twice and the stale copy would win on the next read. The complete stored frontmatter is capped at **64 KiB UTF-8**, including Notarium's final typed `title`/`tags`/identity/date entries; a source carry close to the limit can therefore be refused with an exact per-note error when those fields are added.
- **YAML anchors and aliases are order-dependent and are not accepted on the write/import channel.** Last-wins duplicate collapse, typed ownership and keywise overwrite merging can delete an anchor definition or move an alias before it; a line-level merger cannot prove the dependency graph safely. A new source containing an anchor or alias is therefore rejected before writing **when a write is actually attempted**. `skipExisting` collision policy runs first, so DnD still skips an occupied path without inspecting or changing that existing note. An externally authored existing note may still be read/exported, but every attempted mutation is refused while those node references remain. Likewise, two consecutive leading frontmatter blocks are rejected as ambiguous instead of letting the real engine merge the second while a file-less fake treats it as body.
- **"We lift this key" and "we read its value" are different facts**, and conflating them is how a file-first importer quietly deletes data. The value shapes the shared reader models are: inline scalar, flow list (`[a, b]`), block list (`- a`), and **block scalar** (`|` literal / `>` folded — what a Jekyll or Hugo post writes its title as). A shape outside that set yields no typed value, so the key stays an unmodelled key like any other and **rides the carry**: a `type:` written as a nested map keeps its lines instead of vanishing because nobody asserted it. The one key this cannot save is `title:` — we always write our own — so an unreadable title shape degrades to the heading/file-name fallback, exactly the collapse an ordinary engine resave of that same file on disk performs.
- **The keys carried into the file become live metadata for free**, because that is how the engine reads any file: an imported `aliases:` joins the alias history (inbound `[[Old Name]]` resolve), an imported `slug:` becomes the note's display slug ([note-model.md](note-model.md#note-ontology)), and the other typed frontmatter keys project normally. The in-memory engine (the e2e fake) has no file to re-read, so it derives the same typed projections from the final merged carry — including presence-but-unreadable as an explicit cleared projection — and gives explicit typed write channels the same last priority as the real serializer.
- **Title precedence — frontmatter `title:` → the body's leading heading (`# H1`/setext) → the file name.** This is not a new rule: it is the same chain [`parseNoteFile`](../packages/engine/src/services/notariumStore/noteFile.ts) applies to any `.md` sitting on disk. "Explicit metadata beats the body's heading" is the #156 rule the MCP `create_note` runs too (`deriveNoteTitle(body, title)`). The heading is peeled out of the body **only when it equals the title** — so a `# H1` that merely differs from an authored `title:` STAYS (nothing is silently dropped), while our own exported file (`title: X` + `# X`) round-trips without a duplicate heading. The last resort is the FILE NAME rather than the editor's Bear-style prose promotion: for an Obsidian note the name IS the title.

**A re-drop does not re-import at all; a re-import refreshes but does not sync.** The two are different paths and the difference is `skipExisting`. **Dropping** an edited file again is a no-op by design — the DnD client always sends `skipExisting`, so a same-named note is SKIPPED (the yellow "already exists — content not compared" toast), because a casual drag must never clobber what is already there. On the programmatic API path that explicitly sends `format=markdown` without the flag, an anchor/alias-free write merges into an anchor/alias-free existing note: accepted author keys are added/updated and ours stay ours, but a key the source has since REMOVED stays in the note — the same semantics as every other write in the product, where a save never deletes a key nobody asked it to delete. A source or existing note carrying a YAML anchor or alias is refused on this mutation path before writing, as described above. The Settings import picker currently exposes only the ZIP/JSON export flows; it is not a markdown re-import surface. Either way import is a create/overwrite, not a two-way mirror; exact source-id merge is #10.

**One frontmatter reader.** Both of the above rest on shared primitives in `core/libs/markdown`, not importer-local copies: `parseFrontmatterBlock`/`frontmatterEntryValue`/`frontmatterScalar` (which the engine's `noteFile.ts` parses and serializes files with) and `headingTitle` (the heading-only subset of `promoteBodyTitle`, from the same scan). The importer lives in `core` and the parser used to live in `engine` — one tier up, out of reach — which is exactly why "just strip it" was the path of least resistance. Moving the parser down removed the reason.

**The title deriver is NOT yet unified, and that is a known tail.** The chain above is the same in both places, but its middle step is not: the importer asks `headingTitle` (the body's LEADING heading, setext included — the #156 canon `docs/editor.md` states), while `parseNoteFile` keeps its legacy-equivalent **column-zero H1 anywhere in the document** scan and knows no setext. So a frontmatter-less file whose first `# H1` sits below a badge block, a lead paragraph or a fenced `# comment` gets one title dropped into the window and another copied straight into the data root (measured on a real corpus: ~10% of `.md` files differ). The importer answer is canonical; `parseNoteFile` is the compatibility side. Its implementation is now a bounded physical-line scan rather than the old backtracking regex, but changing what it recognizes would retitle existing on-disk notes. Only files that carry no `title:` are affected, and every file Notarium writes carries one.

## Dates-as-data

The engine takes `createdAt` from the file's birthtime — a naive import would date everything "today", and the whole history would pile into the Feed in one heap. So import **threads the creation date through as data**: `WriteInput.createdAt` → the engine writes `created:` into the frontmatter AND honors it in the index (`upsertRow` prefers `created:` over birthtime; `parseNoteFile` reads it). This way a note is dated by **when the conversation happened**, and the Feed lays out the imported history by real days; round-trippable (export→import preserves the creation date).

**Where a dropped file's date comes from (#280).** For the `markdown` format the date is read from the frontmatter — `created` (ours, and Obsidian's convention) → `date` (Jekyll/Hugo/11ty) → `created_at`/`createdAt` (programmatic exports), first one that PARSES wins, and an unparseable value does not shadow the fallback. Otherwise the note is dated by **the source file's own mtime**: the browser's `File.lastModified` rides a multipart field, the route validates it and threads it through `job.params` → `runImport` → `markdownFileToNote`. Import time carries zero information about a note written in 2019; the file timestamp is the best truth available. If the source also carries an unreadable authored `created:` (for example `created: someday`), that raw line remains untouched and the resolved mtime is written as reserved `notarium-created:`; distinct keys keep the YAML valid and an explicit later date edit collapses them back to the normal `created:`. The mtime is untrusted, so `0` (the browser's "unknown") and anything in the future beyond a 5-minute clock skew are dropped. Only bare forced `markdown` uses it: an AI export dates each note from the conversation itself, and a ZIP mtime says nothing about its members.

`createdAt` is a **three-state authored channel** (like `tags`/`slug`): `undefined` does NOT touch the existing date (an ordinary body save does not re-stamp it), a value SETs/overwrites it. Import sends it on creation; the user edits the date deliberately from the UI (#186, the "Created" field in the editor's metadata aside) for migrations/historicity corrections. On the wire the channel is a full ISO instant. `read()` returns the resolved `createdAt` (`created:` → reserved fallback → birthtime) so the editor can prefill the field. The unreadable-author-value exception above applies only when that raw entry arrives in the same import carry; an explicit editor/API date set writes ordinary `created:` and removes the fallback. `modified` is NOT editable — it is always the real mtime. Engine: `upsertRow` UPDATE refreshes `created_at` via `COALESCE(claim, existing)` (a note without a claim does not flap on a re-stat of birthtime); the read-model resets the pinned date in the identity registry (`setCreatedAt`) and optimistically in the snapshot.

`modified` is NOT threaded through (there is no `WriteInput.modifiedAt`, and `modified:` is not written): it is always = the file's real mtime — on import this is the import time, then the real edit times. This way it does not go stale, does not "flip" on a read-model poll, and does not conflict with the #12 journal. (There was a bug: a written `modified:` was honored by the engine in the index → on the next poll a note's `modifiedAt` jumped to the conversation date and reverted edits — removed by this decision.)

## Idempotency (dedup on re-import)

The file name is deterministic and tied to `sourceId` <a id="file-names"></a>: `<YYYYMMDD>-<legacyImportSlug(title)>-<hash8(uuid)>` for conversations, `legacyImportSlug(name)` for a memory entity (name = identity), `legacyImportSlug(filename)` for a project doc. Import storage deliberately freezes the pre-#296 ASCII algebra even though ordinary note names and new handles use corrected Unicode romanisation: changing it would make the first re-import after an upgrade miss an old path and duplicate the note. Implemented via the host-internal `WriteInput.fileName` plus an import-provenance root; neither channel exists on REST/MCP schemas. The provenance fence keeps the caller-selected root under the ordinary portability rule, while parser-owned suffixes and the pinned basename retain their historical spelling. The readable part keeps its historical cap, and generated importer-owned directory components preserve every in-limit spelling; an overlong generated directory receives a 96-bit SHA-256 tag only beyond the filesystem's 255-byte component boundary. The effect: re-importing the same ordinary export **overwrites the same files** (upsert by path, no dupes), and 50 "Untitled" conversations do not collide by title alone.

That exactness includes legacy POSIX files named `con.md`, `nul.md`, or placed below an importer-generated `CON`/`NUL` directory. Public writes still escape Windows device names and bound every explicit basename. Import alone reproduces the frozen path on a filesystem that supports it; a fresh or re-import on an incompatible Windows filesystem fails visibly instead of silently selecting a new sibling path and turning compatibility failure into duplication.

The frozen legacy algebra also freezes two old limitations until source provenance gets its own field and a migration can distinguish ownership safely: its 32-bit conversation source suffix has a theoretical/known collision class, and two unromanisable project/doc names share the constant `project`/`doc` fallback. Changing those paths unconditionally would turn the next re-import of an existing vault into duplicates; silently claiming the collision is impossible is worse. Exact source-id dedup/merge is therefore the follow-up boundary below. Provenance currently remains visible only through tags (`claude`/`chatgpt`/`memory`).

Within one streamed run the host reserves the exact final `(class, path)` before writing it. A second source record claiming that key fails visibly instead of overwriting the first; the reservation is retained after an uncertain write failure, because retrying another record into a destination that may already have committed would not be fail-closed. The next independent import remains idempotent by the deterministic path policy above.

## Cooperative responsiveness on large imports (#192)

The engine is a single process with a single event loop, shared across all spaces and users of the instance. Without countermeasures, a mass import (write-loop + embedding backfill + graph enrich) monopolizes the loop and the CPU → everyone else's search, navigation, and SSE slow down. A "slow import" is itself acceptable; what is not acceptable is that it **steals responsiveness from interactive requests**. So import runs in **bulk mode**, where the background work cooperatively yields to the interactive path (the "yield+throttle in the current HTTP model" policy; the durable/worker offload is orthogonal, #191/#105):

- **Cooperative yielding in the write-loop.** After writing each note, the import yields to the macrotask phase (`setImmediate`) so the event loop can service an incoming request rather than piling them up behind the whole stream. `node:sqlite` is synchronous — without this, thousands of writes in a row hold the loop.
- **A bulk bracket on the read-model** (`CachedStore.beginBulk`/`endBulk`, wrapping the whole import): for the duration of the stream (1) the per-create flush of the identity registry into the meta-DB is **batched** (one `upsertMany` per `settle`/end instead of one transaction per note — which is both a cost and a blocker), (2) the background **embedding is paused** (the engine's `suspendBackground`/`resumeBackground` — enqueued rowids accumulate and drain afterwards with yielding; nothing is lost, the boot backfill is a backstop), (3) `changed` events are **coalesced** into one summary broadcast (~300ms) instead of a per-note fan-out to all of the space's SSE subscribers (a refetch storm on other people's tabs), (4) the redundant **delta-poll is paused** (write-through keeps the snapshot alive anyway; one catch-up poll afterwards), (5) the **graph enrich is not recomputed** on every burst — exactly one pass after the import.
- **enrich does not monopolize.** The layout of a large graph yields after each tick (a 3k-node force-tick is ~90ms — that is the grain of the interleaving), so the background does not cause multi-second freezes. An accompanying **structural fix O(N²)→O(N)**: `applyDelta` builds the link-index ONCE per delta and re-resolves ghosts once (previously `patchNoteEdges` built a full index for EVERY note → a catch-up on 3k notes = ~48s of synchronous freeze). It fixes the scaling of any large reconcile, not just import.

Measured (test bench, embed off, 3000 notes, a parallel `/search` every 100ms): the interactive p99 during import **6987ms → 220ms**, the worst continuous event-loop block **~48s → 364ms**, the median ~unchanged (~20ms). In production with embed on, bulk mode removes the embedding's contention for CPU/sqlite for the duration of the stream (without it, importing 1000 notes itself stretched out to minutes).

## Deliberate boundaries

- **The durable offload is done (#191):** import is by default a durable job (above), off-request: true background ("closed the tab"), surviving a server restart, live progress with phases, cancel, reconnect. The synchronous single-request path (bounded memory, a heartbeat against the idle timeout) remains ONLY as the none-mode fallback. What is deliberately NOT in even the durable version: resuming the **upload itself** (the bytes flow through a single connection — an interrupted 600MB upload breaks; durable begins AFTER the 202), pause/resume (cancel only), %/ETA (the number of notes in the ZIP is unknown → an indeterminate bar + counter), moving embedding into the job (indexing in the background, #81/#197). Peak memory under a steady write stream (GC headroom + sqlite buffers, ~1.7 GB on the extreme shape of 1000×640 KB) is inherent to writing that volume quickly.
- **Bulk mode — deliberate caveats:** during an import (a) the per-create flush of the identity registry is deferred off the hot path, but an id is made durable in the meta-DB BEFORE each coalesced `changed` broadcast (`broadcastBulk`: flush→dispatch) — so the id resolves by the moment the client can even learn about the note and click it; no resolveNote-404 window; (b) an EXTERNAL edit of this space (another client) is observed only after the end of the import — rare, the import takes priority; (c) the graph/feed are live again moments after the end of the import (SWR serves the stale-enriched shape within the window).
- memory-json destination — the user's choice (`memory=folder|space|skip`); the default is `folder` (visible user-doc). `space` puts it into the SPACE's agent-mount (`.notarium/memory`) — there is no per-space memory browser UI there (it is visible to the agent through recall); import into the GLOBAL personal domain (Agents>Memory, #13) is a separate future integration.
- Exact source-id dedup/merge is future work: v1 idempotency rests on the deterministic path (the file name encodes the source-id hash), there is no separate `source-id` frontmatter provenance; provenance is via tags (`claude`/`chatgpt`/`memory`).
- DoS hardening against untrusted upload: a per-member size cap (a zip bomb) + a private temp folder (mkdtemp 0700) are done; the durable staged upload lives under `<DATA_DIR>/jobs/imports` and is swept row-aware (terminal/orphan) + purge/removeSpace. A rate limit/quota on repeated uploads and moving staging to object storage are future work (#70).
- Binary attachments of conversations: the `extracted_content` text is embedded into the body; the binaries themselves are not imported (the same seam as export — when the `attachment` class lands).
