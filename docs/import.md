# Import from Claude / ChatGPT / memory.json (#11)

Pull an existing knowledge base — claude.ai, ChatGPT, and MCP memory-server exports — into a space in a single upload. Import is the mirror of export (#17), inverted: export reads the engine's on-disk truth and streams it, import **parses on the host and writes through the port**. The parsers are pure (format → notes), and writing goes through the ordinary write-path (`store.write`) — no separate backend is needed, import works on any engine.

Import authors current notes; it is not a history/recovery replay protocol. Every
successful write is exact-read back into the normal byte-safe revision boundary and
gets a fresh journal row/receipt. Imported archives cannot inject revision ids,
restore-safety labels, owner proof, operation evidence or historical ordering. In the
other direction, history's opaque `contentMode:source` is an inspection surface, not
an import/export package format.

## Data path

1. **Parsers are pure functions in `core`** (`importer/`): `string → ImportRecordOutcome[]`, zero IO/store, fixture-testable. An outcome is one normalized `ImportNote`, a per-record failure, or a skip for a genuinely non-renderable record; a missing durable source id is a failure and never aborts its archive member. `ImportNote { title, body, directory, tags?, noteType?, createdAt?, frontmatter?, fileName, source, sourceLocator?, legacyDirectory?, legacyFileName? }` keeps canonical and legacy relative placement separate; the host applies its root/class once. The format is detected by content (`detectFormat`/`detectSingleObject`), not by file name (everyone ships a `conversations.json` file). The parsers cover these formats:
   - **claude-conversations** (`conversations.json`, array) — one note per conversation, messages as `### Human/Assistant (ts)`, attachments as `**Attachment: <name>**` + fenced, uploaded files (binary references `file_name`/`file_uuid` with no text) as a `**File: <name>**` breadcrumb (provenance; the bytes wait on the attachment-class seam, same as export). **Empty messages** (export ships an envelope with no text/content) do NOT print an orphan heading, and **a conversation without a single renderable fragment does not become a note** (#113 — a real Claude dump carries empty envelopes; over 150 dialogs, 24 fully empty, 0 content loss) — the number skipped goes into the per-file warning. Same on the chatgpt side (an empty/voice/asset-only dialog → skip).
   - **chatgpt** (`conversations.json`, array) — a conversation is a `mapping` graph; we linearize it with a pre-order DFS from the root (`parent==null`). **The shape of the graph edges (#113)**: the classic export carries explicit `children` arrays (branch order is encoded), but the CURRENT openai export (2026) is a **parent-pointer tree**: every node has a `parent`, and `children` is absent entirely. A DFS over `children` then never descends below the root (the root has `message:null`) → **every body comes out empty** (the main #113 bug on real data). The fix: when no node has explicit `children`, `childrenOf` reconstructs the edges from the `parent` pointers, sorting siblings by `create_time` (the key order in `mapping` is not chronological), so the transcript reads in time order. **Text extraction**: `content.parts` in the current export is often OBJECTS (`{content_type:'text',text:'…'}`/`{type:'text',text:'…'}`), not strings; `partText` reads both strings and `part.text`/`part.content` (the naive "strings-only" approach zeroed out ALL bodies — a real-data bug). **Visibility filter** (`isVisible`, not just `is_visually_hidden`): we drop system (except `is_user_system_message`), the `tool` role, internal content_types (tether/thoughts/reasoning_recap/system_error), and assistant messages with `recipient≠'all'` (tool calls) — otherwise service noise leaks into the body. code→fenced, with a fallback to `content.text/result/content`. The modern export also shards the history (`conversations-000.json`…`-025.json`); each shard is a self-contained JSON array of `mapping` graphs, and detection/streaming handle them as ordinary ZIP members.
   - **memory-json** (`memory.json`, **JSONL**) — one note per entity, observations→`- <obs>`, outgoing relations→`- <relType> [[target]]`. Wikilinks → edges of our graph fall out for free. This is the MCP memory-server (`{entities,relations}`), NOT Claude's `memories.json` (see claude-memory).
   - **claude-projects** (`projects.json` array OR `projects/<uuid>.json` single object, #113) — a project folder: docs in `docs/`, custom instructions in `prompt-template.md`. Claude's evolved export ships a project file-by-file (one object per file) rather than as an array — `parseClaudeProjects` accepts both forms, and single-object detection is `detectSingleObject`.
   - **claude-memory** (`memories.json`, array, #113) — the Claude account's memory: markdown blobs under `*_memory` keys (today `conversations_memory` — an "about the user" summary; `projects_memory` on some accounts). One note per `*_memory` blob, `source:'memory'` → the memory-destination option (folder/space/skip) governs it the same way as memory-json. NOT an entities/relations graph.
   - **claude-design-chat** (`design_chats/<uuid>.json`, single object, #113) — a design/artifact chat: `messages` (not `chat_messages`), each with `content` = `{role, content:<text>}` (the text nested one level down). One chat → one note, rendered like the transcripts, grouped under `design-chats/<project>`.
2. **The host service** (`server/services/import/`) — **streaming, bounded memory at any archive size**. The upload is streamed to disk into a temporary file (not a Buffer); ZIP members are extracted one at a time by stream (`yauzl`) into temp files; a JSON array is parsed **element-by-element** (`stream-json` + `stream-chain`, one conversation at a time), JSONL line-by-line (the memory graph is bounded by the graph size, not the file); each note is written before the next is pulled (backpressure). **Single-object members** (`projects/<uuid>.json`, `design_chats/<uuid>.json`, #113) are read in full — they are small (size-capped by the same limit), and `detectSingleObject` picks the parser. Peak memory is on the order of one conversation plus the write buffers, regardless of size. A single Claude archive imports ALL recognized members (conversations, projects, memories, design-chats). **A silent skip is only for the provably-non-importable** (`users.json`, set `SILENTLY_IGNORED`); any OTHER JSON member that is not recognized goes into the summary as `format:'unsupported'` with a warning — data loss is visible, not silent (#113). The summary is `{imported, skipped, failed, files[], errors[]}`.

> **Why streaming is mandatory, not "just raise the limit".** The synchronous path (`toBuffer`+`JSON.parse` of the whole thing) dies on a real export: a JS string cannot be longer than ~512 MB (V8's hard limit), so a `conversations.json` from a 600 MB archive (1–2 GB uncompressed) crashes even `buffer.toString()`, before parsing — no matter how much RAM you give it. Streaming removes this: parsing is O(1) per element. Measured: a 625 MB file (>512 MB, the old path fails with `Cannot create a string longer than 0x1fffffe8 characters`) imports into 1000 notes; peak RSS depends on the SHAPE (count×note size), not the file size.

## Durable import via the jobs layer (#191)

When the host carries a meta-DB (the norm for self-host), import is by default a **durable job** — the second consumer of the [jobs layer](jobs.md) after async export. The synchronous flow (below) holds the request for the entire write, and a dropped connection / closed tab / server restart loses the progress. The durable path removes this: the upload is streamed into a **staging store** (durable, `<DATA_DIR>/jobs/imports` — the [single data-root](architecture.md#data-root)), a `kind: import` job is enqueued, and a background worker runs the **same** `runImport` (the bounded-memory core above) off-request. Close the tab, lose the connection, survive a restart — the import lives on; the client sees phases/progress and the outcome.

- **Enqueue = upload.** `POST /api/s/:space/import` (authz `space:write`) — the multipart upload is streamed into staging (`<space>/<jobId>.import`, `ImportStagingStore`), then `jobs.enqueue({kind:'import', params:{uploadRef,filename,format,root,skipExisting,memoryMode,sourceModifiedAt}})`, and the response is **202 + Job**. `sourceModifiedAt` is the validated ISO projection of the optional multipart `lastModified` field; it remains absent when the field is omitted, unknown or invalid. The order is **stage→enqueue**: the row becomes claimable only once the file is fully on disk (a worker will not pick up a half-written source).
- **Handler.** `createImportHandler` resolves the space store, reads the staged upload from disk, extracts ZIP members into an **ephemeral** per-run temp (re-extractable — not durable), and runs `runImport` with `ctx.signal` (cooperative cancellation) and `onProgress → ctx.report({done, total, phase})`. There is no artifact — the outcome (`ImportSummary`) rides in `job.result`.
- **Progress.** `done` is a live counter of PROCESSED members and `total` is the count once it is knowable — which for a foreign export it never is (`null` → an indeterminate bar + phase), and for a Markdown tree it is, the moment planning ends (#302: `done` of `total`, a determinate bar from there on). `uploading` is a client-side label during the byte upload (before the 202, there is no job yet); the server's `job.phase` goes `planning`→`writing`→`done`, and only `writing` is allowed to touch the store. Embedding/indexing is **outside the job**: bulk mode drains them in the background after the write (#81/#197, indicator #199), and the job terminates at "notes written".
- **Cancellation/resilience.** cancel-only (cooperatively, like export; we do not do pause/resume). At-least-once foreign-import idempotency rests on the persisted source locator; a Markdown tree uses the published plan a retry adopts rather than re-derives, and the identity each write re-proves at its destination (#302, below). A deterministic content error (an unrecognized upload, `ImportError`) → a **terminal fail with no retries** (`TerminalJobError`); a transient failure (I/O, crash) is retried.
- **Endpoints** (shared with export, the job belongs to the principal who enqueued it): `GET …/jobs?kind=import` (the principal's list of imports), `GET …/jobs/:id` (status polling), `POST …/jobs/:id/cancel`. Progress via two channels: the `job` SSE event (owner only) and polling — whichever comes first. Import has no download handle (no artifact).
- **Staging cleanup.** The handler does NOT touch the upload (it is needed on retry/reclaim); it is swept by a **row-aware sweep** on the maintenance runner's cadence (`onMaintenance` → `sweepOrphans`: delete if the job is terminal/absent, with an age threshold over the µs stage→enqueue window) + `removeSpace` on a space purge.

The Import tab's **UI** is driven by the single durable path (a mirror of Export, `useImportJob`): upload → a progress bar with a phase and a live counter + "Cancel" — indeterminate until a total is known, determinate once a tree plan supplies one — → and, when ready, a summary from `job.result`. Leaving the tab and coming back is safe: an ordinary `/management/import` entry re-attaches to the principal's latest import (`GET …/jobs?kind=import`) — an in-flight one keeps reporting progress, a finished one shows the summary. A DnD toast already knows its job and links to `/management/import?job=<id>` instead; that form loads, watches and cancels exactly that id and never substitutes a newer concurrent import.

**Degradation.** On a host without a meta-DB (none-mode) there is no jobs layer: `POST /import` serves the synchronous streaming path below, and the `jobs` routes 404. Not two parallel paths for one tier — degradation by capability, like sync export.

## Wire and UI (synchronous fallback)

The synchronous path (none-mode) remains as a fallback: the same `POST /api/s/:space/import` (authz `space:write`) — a **multipart** upload (binary, bypassing the zod body boundary, like the export stream), and the response is a **hijacked NDJSON stream**: periodic `{type:"progress",imported,phase,done,total}` (heartbeats keep the connection alive past the proxy's idle timeout and provide a live counter; the legacy `imported` stays exactly where it was and the three #302 fields ride beside it additively, so an old reader keeps working and a new one can draw a determinate bar for a tree), then a final `{type:"done",...summary}` (validated by `ImportResponse`) or `{type:"error"}` (an unrecognized/failed upload, carrying a `partial` when there was one — see below). The result is **in-band** (status 200 as soon as the stream starts). The client distinguishes the modes by the response: **202 → durable Job**, **200 → NDJSON stream**. An optional text field `format` forces the parser. The upload limit is 2 GB (streamed to disk; disk is the boundary, not RAM). Exceeding it → 413. Every N notes the import drains the journal's write-behind (`store.settle()`) so that the #12 queue does not grow without bound on large imports.

Import parameters (multipart fields precede the file/tree parts; shared between the durable and sync paths):
- `root` — the root folder under which the default structure is nested (`<root>/conversations/chatgpt/…`); empty = the space root. Untrusted and structurally normalized as a storage address. An exact legacy POSIX-only root is usable only when it already exists; every component the root itself would create must be portable. There is no free-text root field: DnD derives it from the target zone, while the Settings folder picker keeps the selected folder's own top-level wrapper.
- `skipExisting=true` — source-addressable Claude/ChatGPT records skip when their locator already has one owner, independently of its current path. Markdown/memory path-based branches retain the existing destination skip. Without the flag, a source-aware owner is updated by id+CAS while preserving its path; path-based branches retain their explicit internal overwrite policy ([note-model.md](note-model.md#create-collisions)). `overwrite` is not reachable from the note write wire.
- `memory=folder|space|skip` — where memory.json entities go: `folder` (visible user-doc notes under root, the default), `space` (the space's agent-mount `.notarium/memory` via the host-internal `targetClass:'agent-memory'` — hidden from the tree/feed by the #78 visibility checkpoint, reachable by the agent through recall; this is a space mount, NOT the global personal domain #13), `skip` (do not import).
- `lastModified=<epoch-ms>` — the optional source-file mtime sent by Markdown browser intake (DnD or the Settings ordinary picker). The route accepts only a finite positive instant no more than five minutes in the future, stores its ISO projection as durable-job `sourceModifiedAt`, and threads it through the synchronous path identically. It is a date fallback only for a bare forced `markdown` upload; ZIP members and every other import format ignore it.

UI — the **Import** tab in the space settings (`/s/:space/management/import`, a mirror of Export): each option is a separate `SettingsSection` (title+description). One source chooser owns the flow; its file/archive and folder browser pickers are implementation details inside that control, not competing primary actions. The ordinary picker offers ZIP/JSON exports and every supported Markdown/text extension; a selected text file is an explicit Markdown import and carries its browser mtime, while ZIP/JSON stays auto-detected. The internal directory picker (`webkitdirectory`) copies every non-empty `webkitRelativePath`, requires one common root and sends one tree. **Skip existing notes** remains an explicit switch. **Memory entries** keeps its folder/space/skip meaning for foreign exports and gains no folder-tree semantics. The durable path (see above, `useImportJob`) drives progress/phase/cancel/reconnect and the summary from `job.result`; in the none-mode fallback the same component drives the NDJSON stream into the same shape (a synthetic job). Notes flow in through the ordinary write-path → the tree/feed update on the `changed` SSE event.

## Browser files and folders <a id="drag-and-drop-of-text-files-223"></a>

"Dropped files or a folder into the window — got one import outcome" is a second entry into the SAME pipeline (durable job or sync fallback), not a separate backend. The UI side lives in `docs/drag-and-drop.md §10`; here is the import side.

- **The `markdown` format** (`core/importer/formats/markdown.ts`, `markdownFileToNote`): a dropped `.md`/`.txt` → ONE note, the file body = the note body (not a transcript). `fileName = slug(basename)` (idempotency by FILE), `directory=''`, `source='file'` (no provenance tag). `.txt` is a sub-case. The file's **own frontmatter is its own data** — see the next section.
- **Force, not detect.** DnD sends `format:'markdown'` — the extension is the signal (an md body may begin with `{`/`[`). On a force, the stream path reads the file in full (`TEXT_FILE_CAP=64MB`) bypassing the `{`/`[` dispatch (`processTextFile`). The job/sync run exactly this `runImport`.
- **Where it lands** — the `root` parameter (the drop folder): a note with `directory=''` lands directly in `root`. The client resolves by zone (see §10): a drop on a **folder in the tree** → that folder; a drop in the **content zone** → the folder of the open note, otherwise the scope root. Name conflicts — `skipExisting:true`.
- **Opening after import.** `ImportSummary.created[]` (the ids of created notes, capped) rides in BOTH carriers (sync `done` and `job.result`); the DnD client opens `created[0]` only for one direct text file. A multi-file tree, folder or ZIP never jumps to an arbitrary member.
- **Routing matrix.** One text file stays the direct forced-Markdown upload; one `.zip` stays auto-classified, so both Markdown vaults and foreign exports retain their existing classifier. Multiple text files or any drop containing a directory become one tree. Ordinary unsupported files beside text remain metadata-only entries and appear in `ignored`; unsupported-only refuses locally. A top-level ZIP mixed with any other top-level item refuses atomically, while a ZIP nested inside a folder is just an unsupported tree member.
- **Current-tab concurrency.** Tree traversal/upload and the sync fallback are not addressable jobs, so a second DnD reports the active import without an action. After `202` exposes the durable id, the same message can link to that exact job in Settings. This serializes only the two DnD surfaces in the current tab; Settings and other tabs may start their own imports.

### Browser tree bridge

`captureDrop` calls the legacy `webkitGetAsEntry()` synchronously for every file item because `DataTransfer` is browser-owned and expires after the drop handler returns. The later iterative traversal uses those owned entries, calls each directory reader until it returns `[]`, keeps every dropped top-level root and sorts final paths deterministically. A file/directory callback error, a partial resolved/null snapshot or the 100 000th-over-limit discovered entry refuses the whole drop. If the browser exposes file items but every Entry is null, ordinary flat `DataTransfer.files` works only when it contains exactly as many files as that item list; a shorter or longer fallback is incomplete and refuses the whole drop. A legacy browser that exposes no item list may still use `DataTransfer.files` as its only evidence. A zero-byte/type-empty unsupported fallback is also ambiguous: it may be a browser's folder placeholder (including a dotted folder name), so its presence refuses the whole drop with a capability notice and an action to Settings instead of importing neighbouring files or inventing an extension diagnosis. Empty directories have no note representation.

The client sends a browser tree as ordered multipart: `bundle=markdown-tree`, `format=markdown`, optional `root`/`skipExisting`, then one part per entry. A part is named `entry:<lastModified-ms-or-0>` and its filename is `encodeURIComponent(relativePath)`. Supported text carries the original `File`; unsupported content carries an owned zero-byte body, so attachments are counted without uploading their bytes. The server still treats emptiness as a trust boundary and rejects an unsupported part on its first byte.

The route decodes each filename exactly once, requires the decoded UTF-8 path to be canonical, portable and packer-exact, rejects duplicates, and streams the ordered parts into a store-mode ZIP in staging. It does not buffer the corpus and does not create a second importer: durable and sync continue through the same Markdown-tree planner/writer below. Exact browser mtime — including pre-1980 and sub-second values — or `unknown` is carried in a bounded private ASCII ZIP entry comment. Only an explicit internal `folder-tree` source may interpret that marker. The same provenance keeps a user-authored `__MACOSX` path from being mistaken for archive-container noise; ordinary uploaded ZIP comments, timestamps and noise filtering are unchanged.

### The dropped file's frontmatter is the author's data (#280)

Notarium is file-first: the user brings their own `.md`, and the YAML block on top of it is **their metadata, not service noise**. v1 stripped it wholesale, so a dragged-in vault arrived with no tags, filename titles and every note dated "today" — precisely the things that made the archive worth keeping. Import now **lifts what it models and carries the rest**.

- **Lifted into typed channels** — `title`, `tags`, `type` (→ `noteType`), and the creation date. `tags` reads the three shapes a real file carries (block list, flow list, comma scalar) and peels a hand-written leading `#`; hierarchy and case are left alone (`foldTag` folds at read time, non-destructively). Absent tags stay `undefined`, not `[]` — the write channel's `[]` means *clear*.
- **Preservation has an explicit structural boundary.** The shared reader recognises conservative top-level **plain mapping keys** (Unicode and spaces are fine) and carries their raw entry lines through the host-internal `WriteInput.frontmatter` channel. An unmodelled value below such a key — a nested map or a plugin-owned shape — can therefore survive without being reinterpreted; standalone supported comments survive too. Quoted or explicit keys, complex mapping-key syntax, merge keys, document directives/fences, root sequences and other structural non-mapping/keyless forms are rejected visibly. Refusing a shape whose ownership we cannot prove is safer than relocating it into a different YAML structure while claiming preservation.
- The engine merges accepted carried entries under the existing block and **below our typed fields**. What is *not* carried: **`notarium-id`** (an identity claim is not the author's to donate — the write path mints ours), **`notarium-created`** (our reserved resolved-mtime companion), **`title`** (the write path asserts its own unconditionally, so a carried copy would be replaced anyway), and a lifted key **once its value is really in a typed channel** — otherwise it would be asserted twice and the stale copy would win on the next read. The complete stored frontmatter is capped at **64 KiB UTF-8**, including Notarium's final typed `title`/`tags`/identity/date entries; a source carry close to the limit can therefore be refused with an exact per-note error when those fields are added.
- **YAML anchors and aliases are order-dependent and are not accepted on the write/import channel.** Last-wins duplicate collapse, typed ownership and keywise overwrite merging can delete an anchor definition or move an alias before it; a line-level merger cannot prove the dependency graph safely. A new source containing an anchor or alias is therefore rejected before writing **when a write is actually attempted**. `skipExisting` collision policy runs first, so DnD still skips an occupied path without inspecting or changing that existing note. An externally authored existing note may still be read/exported, but every attempted mutation is refused while those node references remain. Likewise, two consecutive leading frontmatter blocks are rejected as ambiguous instead of letting the real engine merge the second while a file-less fake treats it as body.
- **"We lift this key" and "we read its value" are different facts**, and conflating them is how a file-first importer quietly deletes data. The value shapes the shared reader models are: inline scalar, flow list (`[a, b]`), block list (`- a`), and **block scalar** (`|` literal / `>` folded — what a Jekyll or Hugo post writes its title as). A shape outside that set yields no typed value, so the key stays an unmodelled key like any other and **rides the carry**: a `type:` written as a nested map keeps its lines instead of vanishing because nobody asserted it. The one key this cannot save is `title:` — we always write our own — so an unreadable title shape degrades to the heading/file-name fallback, exactly the collapse an ordinary engine resave of that same file on disk performs.
- **The keys carried into the file become live metadata for free**, because that is how the engine reads any file: an imported `aliases:` joins the alias history (inbound `[[Old Name]]` resolve), an imported `slug:` becomes the note's display slug ([note-model.md](note-model.md#note-ontology)), and the other typed frontmatter keys project normally. The in-memory engine (the e2e fake) has no file to re-read, so it derives the same typed projections from the final merged carry — including presence-but-unreadable as an explicit cleared projection — and gives explicit typed write channels the same last priority as the real serializer.
- **Title precedence — frontmatter `title:` → the body's leading heading (`# H1`/setext) → the file name.** This is not a new rule: it is the same chain [`parseNoteFile`](../packages/engine/src/services/notariumStore/noteFile.ts) applies to any `.md` sitting on disk. "Explicit metadata beats the body's heading" is the #156 rule the MCP `create_note` runs too (`deriveNoteTitle(body, title)`). The heading is peeled out of the body **only when it equals the title** — so a `# H1` that merely differs from an authored `title:` STAYS (nothing is silently dropped), while our own exported file (`title: X` + `# X`) round-trips without a duplicate heading. The last resort is the FILE NAME rather than the editor's Bear-style prose promotion: for an Obsidian note the name IS the title. A file whose body opens with a rule that is NOT a block — one preceded by a blank line or an indent, which the parser refuses ([core](core.md#write-through)) — lands on that last resort too: there is no heading to read, so the file name titles the note.

**A re-drop does not re-import at all; a re-import refreshes but does not sync.** The two are different paths and the difference is `skipExisting`. **Dropping** an edited file again is a no-op by design — the DnD client always sends `skipExisting`, so a same-named note is SKIPPED (the yellow "already exists — content not compared" toast), because a casual drag must never clobber what is already there. The Settings folder picker is the explicit Markdown re-import surface: its visible switch decides between that safe skip and overwrite. On an overwrite, an anchor/alias-free write merges into an anchor/alias-free existing note: accepted author keys are added/updated and ours stay ours, but a key the source has since REMOVED stays in the note — the same semantics as every other write in the product, where a save never deletes a key nobody asked it to delete. A source or existing note carrying a YAML anchor or alias is refused on this mutation path before writing, as described above. Either way Markdown import is a path-keyed create/overwrite, not a two-way mirror and not part of foreign source identity.

**One frontmatter reader.** Both of the above rest on shared primitives in `core/libs/markdown`, not importer-local copies: `parseFrontmatterBlock`/`frontmatterEntryValue`/`frontmatterScalar` (which the engine's `noteFile.ts` parses and serializes files with) and `headingTitle` (the heading-only subset of `promoteBodyTitle`, from the same scan). The importer lives in `core` and the parser used to live in `engine` — one tier up, out of reach — which is exactly why "just strip it" was the path of least resistance. Moving the parser down removed the reason.

**The title deriver is NOT yet unified, and that is a known tail.** The chain above is the same in both places, but its middle step is not: the importer asks `headingTitle` (the body's LEADING heading, setext included — the #156 canon `docs/editor.md` states), while `parseNoteFile` keeps its legacy-equivalent **column-zero H1 anywhere in the document** scan and knows no setext. So a frontmatter-less file whose first `# H1` sits below a badge block, a lead paragraph or a fenced `# comment` gets one title dropped into the window and another copied straight into the data root (measured on a real corpus: ~10% of `.md` files differ). The importer answer is canonical; `parseNoteFile` is the compatibility side. Its implementation is now a bounded physical-line scan rather than the old backtracking regex, but changing what it recognizes would retitle existing on-disk notes. Only files that carry no `title:` are affected, and every file Notarium writes carries one.

## Importing a Markdown tree (#302)

Export hands you a ZIP of your notes **as files**, and until #302 import could not read its own archive back: the ZIP walker only ever looked at `.json`/`.jsonl`, so a Notarium export — or an Obsidian-style vault — had to be unpacked and dropped in one note at a time, losing every folder on the way. A `.zip` whose members are `.md` files is now a first-class import: the archive's directories are reproduced under the selected root, the file's own frontmatter is lifted exactly as a dropped `.md`'s is (#280), and links **between** the archive's own notes keep pointing at each other.

**It is a COPY, not a restore.** A member's `notarium-id:` is read as a KEY and never as a claim: the imported note gets a fresh identity, and the claim keys the link remap below. Restoring a corpus WITH its identities, history, grants and jobs is a different operation (backup/restore), and pretending otherwise is how two spaces end up believing they own the same note.

### Classify first, write second

The archive gets **one immutable classification and a complete plan before a single note is written**. That order is the design, not an implementation detail: reproducing a folder tree means every destination — and every collision between two members — has to be known up front. The previous one-pass importer discovered a collision only after it had already overwritten something.

- **Non-ZIP** uploads are unchanged (a bare `.json`, a dropped `.md`).
- **An explicit `format`** decides outright: `markdown` means a tree (JSON members are then ordinary ignored files), any foreign format keeps the existing path. A ZIP uploaded AS `markdown` and holding no `.md` at all is refused in its own words ("No Markdown files found"), not with the JSON-export list below: recommending a Claude/ChatGPT export to somebody who explicitly asked to import a vault answers a question they did not ask.
- **In auto mode** the central directory is walked to its end — or until one recognised foreign export settles the question — emitting no notes and no callbacks but a scan-progress tick: JSON/JSONL members are probed **detection-only** (the MCP-memory shapes first, since the generic detectors return null for them by design, then `detectSingleObject`/`detectFromArrayItem` over just enough of an array to see its first meaningful element). One recognised foreign export wins the archive outright — a stray `readme.md` beside `conversations.json` does not split the run into two importers. Otherwise a single case-insensitive `.md` member makes it a Markdown tree, and an archive with neither returns the existing "No recognised export files" error.

A directory record materialises nothing (no empty folders), and `__MACOSX/` container noise in an ordinary uploaded ZIP is not counted as a user file — neither imported nor reported as loss. An internal browser-folder tree is different: its paths came from the user's directory and a segment named `__MACOSX` is preserved. The archive's own top-level wrapper folder is **kept**, because heuristically stripping it is how an import silently changes where everything lives. External-archive noise is not free, though: it still costs an entry and its declared size against the ceilings below, which is what stops an archive from hiding a hundred thousand headers under that name.

### Paths, dates and what a member becomes

Each `.md` member's archive-relative directory is reproduced under `root`, and its basename goes through the existing importer/storage normalization (idempotency is by FILE, so `my note.md` and `my-note.md` are the same destination — and two members landing on one destination is a **refusal**, not a race). An unsafe member path (absolute, traversing, or claiming a dot-prefixed engine namespace) is fatal rather than a silent skip: dropping a note the user can see in their vault is the failure this import exists to remove.

The creation date follows the same precedence a dropped file has, with the archive entry's mtime as the last fallback. That mtime is **validated, not trusted**: a ZIP's DOS date/time pair carries no zone and cannot say "unknown", so `0/0` (what a stream-built archive writes) would decode into 1979-11-30 and an impossible calendar (month 13, day 0) would roll over into a real instant. An Info-ZIP/NTFS extended timestamp is tried first, but only WINS if it is itself trustworthy — a packer's broken clock is not better evidence than the pair beside it, and letting a present-but-absurd extra field win would strip the date off every member of that archive. Both candidates face the same bar: a real UTC instant, after the epoch, no further ahead than the five-minute skew the `lastModified` field allows; the DOS pair must additionally name a calendar day that exists, since `Date.UTC` rolls Feb 30 into March rather than refusing.

Everything that can refuse — an unsafe path, a duplicate destination, a duplicate identity claim, YAML anchors/aliases, a source that only overflows the 64 KiB frontmatter cap once our typed fields are added, any resource ceiling — refuses during this pass, with **zero notes written**. The write-safety proof uses the real serializer, so "it parsed" and "it can be written" are not confused.

### Copy identity and exact links

Before the first write, the plan settles every entry's identity against current file truth:

1. the store performs a **forced checkpoint** — not a settle. Settling only awaits reconciliation that has already started, which is precisely the case that misses a file whose watcher event never arrived; that file would then be overwritten with a new identity;
2. one `list()` builds destination → identity for live user-doc notes. An occupied destination is **referenced, never re-identified**: import refreshes a note's body, it does not take its identity away from the links pointing at it;
3. a free destination gets a fresh id drawn outside a forbidden set — every existing identity AND every source identity the archive itself names. An id equal to one of the archive's own would make a rewritten link ambiguous (the copy, or the note the archive came from?) even when that source id has no owner here at all.

The complete `source id → target id` map exists before any body is rewritten, so forward, backward and cyclic links are all resolvable. `rewriteWikilinkIdentities` then replaces **only the address slice** of the exact links whose id the map names: the alias, the escaped table separator, the whitespace around the address and every other byte stay as authored. An identity outside this archive is not ours to repoint and keeps its address.

**One traversal of one grammar answers both questions.** "Is this construct a link?" and "where does it sit in the author's bytes?" are the same question asked of the same pass: the Marked lexer that decides what a link is — the grammar the UI renders with — is also what reports the offsets, read off the tokens it already produced. So a `[[notarium-id:…]]` copy inside a code span, a fenced block, an HTML comment or a math region is not *skipped*: it never becomes a candidate, and byte-stability there is a structural property rather than a rule someone has to keep two extractors agreeing on. A second, hand-written grammar that knew only positions is what this replaced, and reconciling two lists of links is unsound in principle — an extra construct in one and a missed link in the other cancel out, and the rewrite then edits the comment and leaves the real link pointing at the source corpus.

**What cannot be rewritten is refused per note, never guessed at.** The rewrite gives up — `WikilinkRewriteError`, producing nothing at all — if a link cannot be placed in the source bytes, if re-reading at that offset does not find the same address, or if re-lexing the finished document does not yield exactly the links the original held with the map applied. That last check is independent of offset reconstruction: it re-parses the result through the same extractor and compares the complete link sequence; a conservative fallback is only a guard against the lexer ceasing to provide usable positions. The import catches the refusal, writes the author's ORIGINAL bytes and attaches a per-file warning (`internal links were left pointing at the source: …`) to that file's row in the summary. The note still counts as imported: a body whose links still name the source corpus is a visible defect a reader can act on, and half-rewritten bytes are not. The warning row is bounded by the same 200-row detail cap as everything else there, but the exact `repointFailed` total survives that cap and keeps the final UI in a warning state even when the affected member is outside the sample.

Every planned write then states the identity it expects at its destination (`WriteInput.expectedDestinationId`). **Two layers answer that statement, and they answer two different questions** — the pair is the guarantee, not a belt-and-braces duplicate of one check.

- **Whose note stands here?** — answered by the **read-model**, and this is the authoritative one. It is the only layer that can map a path to an *identity* in every wiring, including a vault of files that carry no `notarium-id:` at all, where the medium itself states nothing; and it is the very projection the plan was settled against, so the check re-asks the plan's own premise of the model that produced it. `null` means the plan expected a free path — an occupant carrying the planned id is that plan replaying after a crash and converges (overwritten, or skipped under `skipExisting`); anyone else is a note that appeared in the meantime, and taking its identity is exactly what this refuses, terminally. It runs **before** the collision policy, which is what stops `skipExisting` from reporting a destination that changed hands as an ordinary skip.
- **Did anything change between looking and publishing?** — answered by the **engine**, on disk, inside the operation that publishes, against the single observation that becomes the compare-and-swap baseline. This one is about the race, not about ownership: there is no window between reading and writing, because there is only one read. Its reach is bounded by what the medium can say — a file with no claim in its frontmatter contradicts nothing, so this half refuses only on a contradiction and leaves ownership to the check above. And losing the swap means the expected note's BYTES moved, not that the path changed hands, so it costs one failed note rather than condemning the run: an import that had written 9 999 notes must not end terminally because the ten-thousandth raced one edit.

### Resource limits on a Markdown tree (#302)

An untrusted archive is adversarial input, so each ceiling below is a boundary a hostile ZIP would otherwise cross:

The browser-folder bridge applies the same shape before it has a ZIP to inspect: at most 100 000 entries, 64 MiB per supported member, 6 GiB across all incoming bodies and 32 MiB of path/timestamp metadata. Each decoded path and generated private comment is also limited to 65 535 UTF-8 bytes before append; ZIP's 16-bit fields would otherwise truncate modulo 65 536. These checks happen before a final staged artifact or job exists, and an abort/failure removes both `.part` and final staging names.

- **100 000 central-directory entries** (directories and noise included): the count itself is the attack surface — headers are free to author and cost a plan entry each.
- **6 GiB of expanded data**, counting EVERY regular member. Ignored attachments are part of the archive's cost even though none of their bytes are kept, and the total is metered twice: once against the declared `uncompressedSize` headers, and once against the bytes that actually arrive. The second is the one an archive cannot lie about, which is why every regular member — importable or ignored — is drained through a counting sink. Ordinary-ZIP `__MACOSX/` noise is the one class left out of the drain, and deliberately: nothing ever extracts it, so it costs no time and no space to expand, and the declared ceiling it does pay is enough to bound an archive built out of it. Browser-folder members under that name are user data, not noise, and follow the normal drain/import rules. That drain waits until the archive is known to be a TREE, and the ceiling loses nothing by it: the pass still runs before the plan is returned and therefore before the first write. What it saves is the foreign path, which never reads those members at all — a Claude export shipping a 40 MB blob ahead of its `conversations.json` used to inflate it for a run that would never look at it (267 ms → 31 ms). The walk that defers and the pass that drains select members with ONE shared predicate, and a disagreement between the two counts refuses the import rather than quietly leaving a member unmetered.
- **32 MiB of plan metadata**: the one structure that grows with the entry count. The destination root is stored ONCE (repeating it per entry is what turns 10 000 addresses into megabytes), each entry is charged before it is accumulated, and the finished sidecar is proven again.
- **a 10 000:1 compression ratio** per member — refused on the header, before a byte is decompressed (the same ceiling the backup contour uses).
- the existing **64 MiB** per Markdown member stays unchanged. An ordinary file/archive upload remains capped at **2 GiB**; a browser tree is bounded instead by the stricter member and **6 GiB aggregate** counters while it is packaged.

**They are a TREE's ceilings, and only an archive that turns out to be a tree pays them.** They are the cost of a plan, and a foreign export has no plan — before #302 the foreign walker had neither an entry counter nor an aggregate byte ceiling, and charging one to it would refuse archives that used to import. But the verdict is not known until the central directory has been walked, so a ceiling that fires cannot be raised where it fires: it is **held exactly as a structural refusal is** — an unsafe path, a destination collision — and both are thrown at the same place, once the walk has decided the archive is not a foreign export. That is also what keeps the verdict independent of the order of the central directory: the same members refuse, or import, whichever record the packer wrote first. A ceiling does do one thing a structural refusal does not — it narrows the rest of the walk, which stops metering, sampling and planning and asks only the one remaining question, whether this archive is a foreign export after all. The member the ceiling fired on is asked it too; it may be the very export that settles it.

The probe that asks that question is **not charged to the tree budget**. It has its own per-member cap — the 6 GiB ceiling the foreign path has always applied, plus a tighter 256 MiB one for the shapes it has to read whole — and exceeding that member cap makes the probe answer "not an export" rather than refuse the archive: a member too big to be a Claude export is not evidence about a vault. A separate 6 GiB aggregate bounds what all probes together may inflate; unlike a tree refusal it is raised immediately, because holding it while continuing to probe would leave the rest of the archive unmetered. And a JSON member no detector recognises is not a hole in the tree metering; it is an ordinary ignored file and drains through the counting sink with the rest.

The supported corpus this is sized for is 10 000 small Markdown files with nested folders, metadata and internal links. That claim has an executable artifact rather than an opinion behind it: `make import-bench` uses the ordinary archive seam by default, while `make import-bench SOURCE=folder` sends the same corpus through real multipart → streaming bridge → staging; both print the selected source and drive the production composition (see [dev-environment.md](dev-environment.md)). The harness requires one upload to create one durable job and asserts the totals, reproduced tree, copy identity, rewritten links — both of a note's live exact links repointed at the copies, its fenced copy of one of them still the authored bytes — and bounded result. It reports wall throughput together with process CPU time/core ratio, event-loop p99/max and parallel-reader latency, so moving work out of HTTP by burning the import loop is visible rather than counted as a win. It then cancels a second live import, once that import has provably written a note rather than merely announced its `writing` phase, and requires the notes on disk to land strictly between none and all of them: none would mean the abort never reached the write loop at all, all of them that it arrived after the last member.

A parallel reader runs beside all of that, and **what it proves is worth stating exactly, because the obvious reading is stronger than the fact**. Two things are asserted: that reads were answered INSIDE the import window — only the ones completed between the enqueue and the terminal job count, so a reader served once before the upload and then blocked for the rest of the run does not pass — and that no stretch of that window went by with none, a stretch being bounded at a third of the window. Both are shares of the run's own measurement rather than durations, because a threshold pinned to one machine is a benchmark wearing a test's clothes.

What that does **not** prove is responsiveness. A third of a window is a wide bound: an import that got slower without ever falling silent stays green, and so does one that lost the cooperative yield in its write loop. That is a deliberate trade, not an oversight — tightening the bound until it discriminates the mechanism would put a machine-dependent duration back into a gate, which is the one thing this harness is not allowed to become. Cooperativeness is watched instead through the numbers the harness prints on every run — `eventLoopMaxMs`, `parallelReadP99Ms`, `parallelReadMaxGapMs` — read against the recorded ones by a person. A regression there is a judgement somebody makes, not a red exit code.

### The plan survives the run

For a durable job the ready plan is published beside its staged upload as a sidecar (`<jobId>.import-plan`): complete bytes, fsynced, then atomically published and read back. A usable peer plan is **never clobbered**. A corrupt or incompatible old sidecar may be replaced only before writing and while the current job's lease fence is held; atomic rename alone cannot stop a reaped worker from overwriting its successor's winner. The run settles identities, claims every destination, and publishes under one claimed destination's fence before its first note write. Every later claim of that job **adopts** the published plan rather than deriving one: re-deriving is how a retry quietly decides something different from the run it is resuming. What it adopts is *checked*, not trusted — the envelope must fit the exact metadata ceiling and belong to this staged upload, and EVERY entry must carry what the settle produced: its target id, the id it expects at the destination, and whether that identity is owned or merely referenced. A plan of an older shape under the same `version: 1` is refused rather than read with blanks, because an entry with an empty target id would write a note under an identity no rewritten link names.

A missing or unreadable sidecar may be rebuilt only while the persisted job phase is one of the few that PROVE the write gate was never opened — an allowlist, not a denylist of `writing`. The difference is `done`: the handler persists that phase *before* the runner records the job as succeeded, so a crash in exactly that window reopens a fully written import at `phase='done'` — which a denylist would read as "never wrote" and let plan itself all over again. An unknown phase from a newer build is no better evidence and is refused the same way; the job then fails terminally instead of planning again over notes it may already have written. Once writing can have started, even a corrupt sidecar is terminal rather than replaceable. The sidecar shares its upload's lifetime — the row-aware sweep reclaims both together — and both ride a backup, because the job row rides one too: a restored import that could not re-read its source, or had to invent a second plan for a tree it may already be half-way through, would be a job nobody can finish. What a backup skips is the pair's half-written temps (`<jobId>.import.part`, `<jobId>.import-plan.part-*`, [backup.md](backup.md)): they exist only until their own atomic publication lands, so a copy of one is a copy of nothing.

### Who owns a destination while the import runs

A tree import plans every destination first and then writes for as long as it takes — minutes at ten thousand notes. The whole of that window is a claim: before the first write the run **reserves** its destinations, keyed by the immutable upload, and a second import that wants any of them is refused **up front** rather than discovering the collision half a tree in.

**What a claim reserves is a PATH, and only a path.** The unique index on `(space, destination_path)` is the whole exclusion — one live reservation owns a destination, stated by the database rather than settled by a race — and it is also how a single claim is *found*: a fenced write addresses one row by that key, and the reservation it belongs to is then a filter on the row the index returned, not a scan of the batch. A row does carry what the plan settled beside it — the id that path will get, the id it expected to already stand there, and whether that identity is this import's own or an existing note's merely referenced — but those three are **description**, recorded at the granularity of one archive member so a claim can be read back and attributed. Nothing proves itself against them: the run re-reads its sidecar plan, and the plan is the authority on ids. That is the same reason a claim never releases an identity — it never held one.

Three things can go wrong in that window, and each is answered by the same claim rather than by a rule of thumb:

- **A worker that was taken away keeps writing.** Every planned write happens inside an exclusion that re-proves, at that moment, that this job is still running under this very lease — and the exclusion is still held when the bytes land. A reaped worker's write is refused, not raced. A retry **adopts** the claim under a new fence, which is precisely what makes the previous run's writes stop being valid.
- **The process dies between publishing a file and recording that it did.** Nothing records it, and that is the answer rather than a gap in it: a flag written after the bytes has a crash window under it by construction, so a second flag would only move the question — which is why the table has no "did it land" column at all. The question "did the previous run publish this one?" is asked of the note itself, on disk, inside the operation that publishes the next attempt (`expectedDestinationId`, above), against the plan the retry re-read. A file the dead run left behind carries the planned id and converges; anything else is a note that appeared in the meantime and is refused. So a crash needs no reconciliation ceremony after the fact — cleanup only has to release the claim.
- **Nobody is left to clean up.** The handler returns its outcome *before* the jobs layer records it, so cleanup is not the handler's: it hangs off the durable **terminal row**, where success, terminal failure, cancel and reaper exhaustion all end up. That pass runs at **two moments, and both are needed**. The runner performs it immediately after it persists a terminal transition of its own — because a minute is a long time to hold paths nobody wants any more: the user cancels an import and starts it again, and until the claims that cancel released are closed the second run is refused its own destinations. And it runs once per maintenance tick, which is the net under the runs that ended without any such transition — a worker that was SIGKILLed, a row the reaper took. Both entries are the same pass, and it re-reads each job's status rather than trusting the caller, so one unconditional call covers every terminal shape without a second predicate to keep in step. Closing needs the job id and nothing else — no space store, no file truth, because there is no longer anything to reconcile against — so it is idempotent by construction: it closes only claims that still exist. A space purge does not wait for it at all; it deletes that space's claims itself, since a claim pointing into a deleted space would hold paths forever and keep this pass chasing a job row the purge already removed.

Within the tick the order follows from that: reap → close terminal claims → sweep staging → prune. Everything before the prune needs the terminal row, so retention runs last — and the delete itself refuses, in SQL, to remove a row a live claim still references. The ordering is a convenience; the guard is the guarantee.

SQLite and PostgreSQL hold this by opposite means and are held to one executable contract. What each excludes is the same narrow thing: the two paths that invalidate a run **from outside it** — a cancel, and the reaper deciding its worker stalled — against the run's own fenced writes. SQLite has a single writer, so that exclusion is an ordering: `cancel` and `reapStale` take the same process-owned guard that reserve, adopt, the terminal close and every fenced write hold. PostgreSQL has many, so it is the lock hierarchy — a per-job advisory (`L0j`) ahead of identity, then the claim's header and its paths. Either way an invalidation WAITS for an entered write instead of tearing it in half, and the next write cannot start because its premise is then false. `succeed`, `fail` and `release` deliberately stay outside on both drivers: a run performs those on ITSELF, so there is nothing to interleave with, and routing them through would only make a worker queue behind its own lock. The heartbeat stays outside for a sharper reason — it has to keep the lease of a slow member alive WHILE that member holds the fence, or the reaper would kill the very job that is making progress, which is also why the reaper re-checks staleness after taking the fence rather than before. And the jobs row itself is never locked across a write: the fence is the exclusion, the row read only its premise.

## What an import reports (#302)

Totals stay exact; DETAILS are bounded. A 10 000-note import must not answer with a 10 000-element result — not on the wire, not in a job row, not in the DOM — so `files`, `errors`, ignored samples and `created` each stop at 200 while the counters keep counting, and three of the four say how much they dropped (`filesOmitted`, `errorsOmitted`, `ignored.filesOmitted`). `created` is the exception and truncates silently: it exists so a single-file drop can open the note it just made, and "how many ids we did not hand you" is not a number anything asks. The collector is incremental on purpose: a terminal conflict after N writes still reports those N.

- **Non-Markdown members are reported, not dropped silently.** They are never decoded, materialised or imported; they are counted exactly, sampled boundedly, and surfaced as `Ignored N non-Markdown files (attachments are not imported yet)`. Directory records and ordinary-ZIP `__MACOSX` noise are not user files and are not counted as loss; the same path in an internal browser folder remains user data.
- **Progress is honest about what it counts.** A Markdown tree knows its member count once planning ends, so the bar goes determinate then (`done` of `total`); a foreign export never does and stays indeterminate while writing. On both paths `done` is PROCESSED work — a note, failure or explicit skip advances it, and a recognised zero-output record advances it once. Graph-memory parsing also emits a count-free heartbeat per source record so cancellation and yielding do not wait for materialized notes. The durable handler seeds its maximum from the persisted job row on every reclaim and keeps the largest processed value as the terminal `done/total`, independently of summary counters. A reclaimed foreign run explicitly clears a stale terminal total and publishes `writing` before its inventory scan; SQLite, PostgreSQL, SSE and polling therefore agree that the new attempt is indeterminate without lowering `done`. The synchronous client keeps the same maximum per run and carries it into success, partial failure and cancel. Neither carrier can therefore move progress backwards after `memory=skip`, parse-level skips, a retry or a terminal transition. `imported` remains the successful-write counter.
- **A failed import can still carry a result.** A terminal plan conflict is deterministic (a retry re-reads the same bytes and reaches the same conflict), so it fails without burning the retry budget — and carries the bounded partial summary of the work already done. The durable path puts it in `job.result`; the synchronous path puts it on the error line. The error line carries `partial` only for a failure that happened AFTER writing began. A refusal the preflight reaches — a destination collision inside the archive, frontmatter that will not serialize — is thrown with nothing written and carries no partial, because there is none. (What "nothing written" means there is no NOTES: the stream still carries the `planning` progress lines that preceded the refusal.) The Import tab shows the error AND that partial, and on remount it re-adopts the **newest terminal** import rather than falling back to an older success that would claim everything went fine.

The optional fields are additive: a result persisted before them still parses, and the web tab re-applies the cap itself rather than trusting that an older row respected one.

## Dates-as-data

The engine takes `createdAt` from the file's birthtime — a naive import would date everything "today", and the whole history would pile into the Feed in one heap. So import **threads the creation date through as data**: `WriteInput.createdAt` → the engine writes `created:` into the frontmatter AND honors it in the index (`upsertRow` prefers `created:` over birthtime; `parseNoteFile` reads it). This way a note is dated by **when the conversation happened**, and the Feed lays out the imported history by real days; round-trippable (export→import preserves the creation date).

**Where a dropped file's date comes from (#280).** For the `markdown` format the date is read from the frontmatter — `created` (ours, and Obsidian's convention) → `date` (Jekyll/Hugo/11ty) → `created_at`/`createdAt` (programmatic exports), first one that PARSES wins, and an unparseable value does not shadow the fallback. Otherwise the note is dated by **the source file's own mtime**: the browser's `File.lastModified` rides a multipart field, the route validates it and threads it through `job.params` → `runImport` → `markdownFileToNote`. Import time carries zero information about a note written in 2019; the file timestamp is the best truth available. If the source also carries an unreadable authored `created:` (for example `created: someday`), that raw line remains untouched and the resolved mtime is written as reserved `notarium-created:`; distinct keys keep the YAML valid and an explicit later date edit collapses them back to the normal `created:`. The mtime is untrusted, so `0` (the browser's "unknown") and anything in the future beyond a 5-minute clock skew are dropped. Only bare forced `markdown` uses it: an AI export dates each note from the conversation itself, and a ZIP mtime says nothing about its members.

For a browser folder, each member's `File.lastModified` has the same precedence but cannot be represented faithfully by ZIP's DOS date: it may be pre-1980, carry milliseconds or be unknown. The bridge therefore writes its validated exact epoch (or `unknown`) into the internal entry marker described above; the planner reads that marker only for the internal `folder-tree` source. A normal uploaded ZIP still uses its own extended/DOS timestamp rules and ignores comments.

`createdAt` is a **three-state authored channel** (like `tags`/`slug`): `undefined` does NOT touch the existing date (an ordinary body save does not re-stamp it), a value SETs/overwrites it. Import sends it on creation; the user edits the date deliberately from the UI (#186, the "Created" field in the editor's metadata aside) for migrations/historicity corrections. On the wire the channel is a full ISO instant. `read()` returns the resolved `createdAt` (`created:` → reserved fallback → birthtime) so the editor can prefill the field. The unreadable-author-value exception above applies only when that raw entry arrives in the same import carry; an explicit editor/API date set writes ordinary `created:` and removes the fallback. `modified` is NOT editable — it is always the real mtime. Engine: `upsertRow` UPDATE refreshes `created_at` via `COALESCE(claim, existing)` (a note without a claim does not flap on a re-stat of birthtime); the read-model resets the pinned date in the identity registry (`setCreatedAt`) and optimistically in the snapshot.

`modified` is NOT threaded through (there is no `WriteInput.modifiedAt`, and `modified:` is not written): it is always = the file's real mtime — on import this is the import time, then the real edit times. This way it does not go stale, does not "flip" on a read-model poll, and does not conflict with the #12 journal. (There was a bug: a written `modified:` was honored by the engine in the index → on the next poll a note's `modifiedAt` jumped to the conversation date and reverted edits — removed by this decision.)

## Idempotency (dedup on re-import)

Source-addressable foreign records have a versioned locator <a id="file-names"></a>: `v1:claude:conversation:<base64url(uuid)>`, `v1:claude:project-prompt:<base64url(projectUuid)>`, `v1:claude:project-doc:<base64url(projectUuid)>:<base64url(docUuid)>`, `v1:claude:design-chat:<base64url(uuid)>`, or `v1:chatgpt:conversation:<base64url(conversation_id|id)>`. Claude project placement uses the non-note key `v1:claude:project:<base64url(projectUuid)>`. IDs are trimmed durable scalars; an absent id is a visible per-record failure. Claude memory and MCP memory-json deliberately stay on their existing path-based branch.

The full locator is persisted as reserved scalar `notarium-source`. It is logical file state: CAS, history, live restore, strict restore, trash restore and export keep it, while `StorageOwnerKey` remains limited to storage ownership. Ordinary REST/MCP note shapes and their `frontmatter` projection omit it. A capability-thin store may return only the separate typed locator; the read-model's exact-state fallback validates that projection and restores the reserved field before deriving CAS/history state. Fresh Markdown/public/inline metadata cannot mint the key; an ordinary edit carries an existing live locator, and a direct external file is indexed as a claim only when its spelling is canonical. The derived index stores it in nullable `source_locator`; the additive migration preserves rowids/FTS/vectors and does not scan old rows merely because the column appeared.

Paths are a portable representation, not identity. The readable part uses current Unicode-aware `slugify`; a 96-bit `pathHash(locator)` suffix is budgeted before clipping. A Claude project directory hashes its placement locator and is shared by prompt, docs and project-bound design chats. Conversation and design-chat basenames hash the note locator; a project doc hashes its own locator. `CON`, `NUL`, long UTF-8 names and CJK remain portable and distinct. The parser also carries the exact pre-source-locator relative directory/basename, but only as a predecessor fence — never as a destination fallback.

Before foreign streaming begins, the host forces a checkpoint and freezes one inventory of locator owners and exact paths. One owner is updated by `originalId + versionToken + sourceLocator + preservePath`, so a user move survives re-import; `skipExisting` skips by locator. A fresh locator creates at the canonical path only when that path is free and no source-less legacy predecessor occupies its old path. Such a predecessor is a visible refusal: it is neither guessed as the owner nor left beside a new sibling. A different source-tagged legacy occupant does not claim this source.

The read-model claims the full locator as an opaque single-process mutation resource, then re-checks its live owner plus canonical and legacy paths under that lease. The locator resource is independent of the mutable title/path representation: parallel fresh creates of one source serialize even if their exports carry different display names. The winner leaves the follower a safe per-record conflict; a later independent retry sees its locator and converges. A sticky `seenLocators` reservation is taken before the first write await and survives uncertain failures, so a duplicate locator later in the same stream never overwrites or merges the first record. The confirmed locator/path maps advance only after a write returns an authoritative id and path.

## Cooperative responsiveness on large imports (#192)

The engine is a single process with a single event loop, shared across all spaces and users of the instance. Without countermeasures, a mass import (write-loop + embedding backfill + graph enrich) monopolizes the loop and the CPU → everyone else's search, navigation, and SSE slow down. A "slow import" is itself acceptable; what is not acceptable is that it **steals responsiveness from interactive requests**. So import runs in **bulk mode**, where the background work cooperatively yields to the interactive path (the "yield+throttle in the current HTTP model" policy; the durable/worker offload is orthogonal, #191/#105):

- **Cooperative yielding in the write-loop.** After writing each note, the import yields to the macrotask phase (`setImmediate`) so the event loop can service an incoming request rather than piling them up behind the whole stream. `node:sqlite` is synchronous — without this, thousands of writes in a row hold the loop.
- **A bulk bracket on the read-model** (`CachedStore.beginBulk`/`endBulk`, wrapping the whole import): for the duration of the stream (1) the per-create flush of the identity registry into the meta-DB is **batched** (one `claimMany` per `settle`/end instead of one transaction per note — which is both a cost and a blocker), (2) the background **embedding is paused** (the engine's `suspendBackground`/`resumeBackground` — enqueued rowids accumulate and drain afterwards with yielding; nothing is lost, the boot backfill is a backstop), (3) `changed` events are **coalesced** into one summary broadcast (~300ms) instead of a per-note fan-out to all of the space's SSE subscribers (a refetch storm on other people's tabs), (4) the redundant **delta-poll is paused** (write-through keeps the snapshot alive anyway; one catch-up poll afterwards), (5) the **graph enrich is not recomputed** on every burst — exactly one pass after the import.
- **enrich does not monopolize.** The layout of a large graph yields after each tick (a 3k-node force-tick is ~90ms — that is the grain of the interleaving), so the background does not cause multi-second freezes. An accompanying **structural fix O(N²)→O(N)**: `applyDelta` builds the link-index ONCE per delta and re-resolves ghosts once (previously `patchNoteEdges` built a full index for EVERY note → a catch-up on 3k notes = ~48s of synchronous freeze). It fixes the scaling of any large reconcile, not just import.

Measured (test bench, embed off, 3000 notes, a parallel `/search` every 100ms): the interactive p99 during import **6987ms → 220ms**, the worst continuous event-loop block **~48s → 364ms**, the median ~unchanged (~20ms). In production with embed on, bulk mode removes the embedding's contention for CPU/sqlite for the duration of the stream (without it, importing 1000 notes itself stretched out to minutes).

## Deliberate boundaries

- **The durable offload is done (#191):** import is by default a durable job (above), off-request: true background ("closed the tab"), surviving a server restart, live progress with phases, cancel, reconnect. The synchronous single-request path (bounded memory, a heartbeat against the idle timeout) remains ONLY as the none-mode fallback. What is deliberately NOT in even the durable version: resuming the **upload itself** (the bytes flow through a single connection — an interrupted 600MB upload breaks; durable begins AFTER the 202), pause/resume (cancel only), an ETA (a Markdown tree does yield a % once planning has counted its members, but how long the rest will take is still not projected), moving embedding into the job (indexing in the background, #81/#197). Peak memory under a steady write stream (GC headroom + sqlite buffers, ~1.7 GB on the extreme shape of 1000×640 KB) is inherent to writing that volume quickly.
- **Bulk mode — deliberate caveats:** during an import (a) the per-create flush of the identity registry is deferred off the hot path, but an id is made durable in the meta-DB BEFORE each coalesced `changed` broadcast (`BulkController.broadcast`: flush→dispatch) — so the id resolves by the moment the client can even learn about the note and click it; no resolveNote-404 window; (b) an EXTERNAL edit of this space (another client) is observed only after the end of the import — rare, the import takes priority; (c) the graph/feed are live again moments after the end of the import (SWR serves the stale-enriched shape within the window).
- memory-json destination — the user's choice (`memory=folder|space|skip`); the default is `folder` (visible user-doc). `space` puts it into the SPACE's agent-mount (`.notarium/memory`) — there is no per-space memory browser UI there (it is visible to the agent through recall); import into the GLOBAL personal domain (Agents>Memory, #13) is a separate future integration.
- Existing source-less foreign imports are not migrated, backfilled, moved or heuristically matched. Re-import that meets their exact legacy predecessor fails closed; the working corpus remains untouched.
- Source-aware exclusion is process-local, matching the self-host single-writer topology. An external filesystem writer can still race the multi-path predecessor proof; closing that resource-authority boundary is separate work.
- DoS hardening against untrusted upload: a per-member size cap (a zip bomb) + a private temp folder (mkdtemp 0700) are done; the durable staged upload lives under `<DATA_DIR>/jobs/imports` and is swept row-aware (terminal/orphan) + purge/removeSpace. A rate limit/quota on repeated uploads and moving staging to object storage are future work (#70).
- Binary attachments of conversations: the `extracted_content` text is embedded into the body; the binaries themselves are not imported (the same seam as export — when the `attachment` class lands).
