# Durable job layer (#105)

A meta-DB-backed queue for long or heavy work that must outlive a single HTTP request and a server restart. It is a system mechanism, not an export feature: the first consumer is async export (#17) and the second is durable import (#191); the layer is generic over `kind` and is also the home for trash purge/retention (#79), audit-log export (#80) and a future migration of re-embedding (#81) off its in-process queue.

## Why it exists

Before #105 every background activity was ad-hoc and in-process: the per-note journal chain, the embedding `Set<rowid>` loop, the read-model poll/debounce. That pattern — derive the work from state, spin it in the process, self-heal on restart — is enough for fast, derivable work but not for an operation that takes minutes, produces an artifact, and must survive a dropped connection or a redeploy. Synchronous streaming export (#17) is the symptom: it holds a worker for the whole archive, has no progress and no resume, and a disconnect means downloading from scratch.

## Model

One `jobs` table in the meta-DB carries its `kind`, `status` (`pending` → `running` → `succeeded`/`failed`/`canceled`), the enqueuing `principal`, kind-specific `params`/`result` JSON, progress counters, retry bookkeeping (`attempts`/`max_attempts`/`run_at`), a heartbeat (`locked_at`/`locked_by`), and the produced artifact pointer (`artifact_ref`/`artifact_bytes`/`artifact_name`/`expires_at`). All timestamps are ISO text (the table-wide convention); `artifact_bytes` is `BIGINT` on Postgres (a GB archive overflows `int4`) read back through `Number()`.

The runner (`apps/server/consumers/jobRunner`) is one worker per process. It claims work, dispatches by `kind` to a handler, heartbeats while running, and on completion records success or schedules a retry. A maintenance tick reaps stalled jobs, closes the claims of jobs that have ended, GCs expired artifacts, sweeps staging and prunes old terminal rows — **in that order**, because everything before the prune reads the terminal row it removes. Retention runs last, and refuses in SQL to delete a row a live import claim still references (#302): a consumer whose cleanup depends on that row is protected by the delete itself, not by the order alone.

A consumer's terminal cleanup runs at **two** moments, not only on that tick (#302). The runner calls it immediately after it persists a terminal transition — succeed, terminal fail, retry exhaustion, or a cancel it observed — because the tick is a minute wide and a resource held for a minute after the user asked for it back is a bug the user can see: the cancelled import's destinations stay claimed, and the retry they cancelled it for is refused. The tick call remains the **net** under the runs that never reached such a transition, a SIGKILLed worker or a row the reaper took. Both entries are the same idempotent pass over terminal rows and it re-reads each job's status itself, so one unconditional call after every transition covers all of them without a second predicate to keep in step.

## Single-flight, the hard part

The claim is the one place a job can be double-run, so it is atomic and branches by driver. On Postgres (the HA / multi-instance case) the claim is a single autocommit `UPDATE … WHERE id = (SELECT id … FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *`: the subquery row-locks one runnable job and the outer update flips it to `running`, all committed at once, so the lock is never held past the claim and concurrent workers skip each other's locked rows — one job, one worker. On SQLite (the single-process self-host case) `node:sqlite` is fully synchronous, so the same `UPDATE … RETURNING` is atomic by construction; there is exactly one writer and no `SKIP LOCKED` is needed. SQLite is never run as a multi-instance HA queue — that is outside the deployment shapes, and the prior-art (River's experimental SQLite backend) confirms it is the wrong tool for it.

The claim stamps a **per-run lease token** (not a constant worker id) into `locked_by`, and every subsequent write — heartbeat, and the terminal `succeed`/`fail`/`release` — is guarded by `locked_by = <token> AND status = 'running'`. This closes the one gap the claim alone leaves: a job reaped (its lock went stale) and re-claimed under a fresh token while its original run is still alive. The original run's next heartbeat no longer matches the row, so it aborts instead of double-running; and its terminal write no-ops instead of overwriting the new owner's state or a landed cancel. So the invariant is not just "one claim, one worker" but "only the current lease holder can advance the row."

This design is grounded in the phase-0 prior-art spike (graphile-worker / pg-boss / River / Oban; the export-artifact pattern of GitHub, Google Takeout, GitLab). The conclusions: build it over our own meta-DB rather than depend on a Postgres-only library or a Redis broker; poll for correctness on both drivers and treat `LISTEN/NOTIFY` as a future latency optimisation; promise at-least-once with idempotent handlers, never exactly-once.

## Delivery and recovery

Delivery is poll plus an in-process `wake()` fired at enqueue — the enqueuer is in the same process, so a job starts within milliseconds without waiting for the poll tick; the poll is the correctness baseline that also picks up jobs another instance enqueued and jobs left behind by a crash. Cross-instance push (`LISTEN/NOTIFY` on Postgres) is a latency optimisation the layer is shaped for but does not yet need — export runs for minutes.

Semantics are at-least-once: a worker that dies after doing the work but before recording success will re-run the job, so handlers are idempotent (the export handler names its artifact from the job id and publishes it by an atomic rename, so a re-run overwrites rather than piling up; the import handler writes every note on a deterministic source-id-keyed path, so a re-run overwrites the same files). Retries are for TRANSIENT faults — a handler that hits a deterministic bad-input failure (an import of an unrecognised upload) throws a `TerminalJobError`, and the runner fails the job at once with no backoff/retry, so the user sees the real error now instead of after N pointless attempts. A heartbeat refreshes `locked_at`; the reaper reopens jobs whose heartbeat went stale past `staleAfterMs` (a SIGKILL'd worker) — retries left → back to `pending`, exhausted → `failed`. Retries use exponential backoff with jitter. Cancel is cooperative: `cancel()` flips the row, and the running worker notices on its next heartbeat (it returns false) and aborts the in-flight handler — so cancellation works across instances, bounded by the heartbeat interval; because the success write is lease-guarded, a cancel that lands in the final window is honoured, not overwritten by a late `succeed`. On a graceful shutdown the runner aborts in-flight handlers and releases their jobs back to `pending` — refunding the attempt the claim consumed, so a long job crossing rolling redeploys keeps its full retry budget for genuine failures — and the restart or a peer resumes them immediately instead of waiting for the reaper.

## Artifacts

A job that produces a file writes it to the artifact store (`libs/artifactStore`), not back into the user's notes — an artifact is a derived class (P11): regenerable, app-data, GC'd by TTL, never replicated. The seam has one filesystem implementation today (`<DATA_DIR>/jobs`, derived in code from the single data root — [canon](architecture.md#data-root) — and outside any notes dir; `JOBS_DATA_DIR` overrides it onto another disk, but is never required); object storage with pre-signed URLs (the #70 seam) is the cloud upgrade, not built for Beta. The artifact's `ref` is store-relative and every op refuses one that escapes the root, so an untrusted ref can neither read nor clobber outside the tree. The handler writes to a **per-run temp part** and publishes it by an atomic rename to the final `ref` on success — so a concurrent re-run of the same job (a reaped-then-reclaimed lease) never interleave-corrupts a published archive, and a failed/aborted run removes only its own temp.

GC deletes the file once `expires_at` passes (TTL default 7 days, GitHub-ish) and clears the pointer only after the delete succeeds (a failed unlink leaves the pointer so a later tick retries — never orphaning the file), keeping the row as history; terminal rows are pruned after a longer retention. A space purge (#110) drops its job rows **and** sweeps the space's artifact subtree (`<JOBS_DATA_DIR>/<space>/`) directly in the composition root's `onPurge`: once the rows are gone the row-driven TTL GC can no longer reach the files, so purge owns that cleanup itself. Because a temp part is never referenced by a row, the maintenance tick also sweeps stale `*.part` files by age (the leftovers of a SIGKILL between a run's temp open and its rename) — the one artifact class the row-driven GC cannot see.

## Input staging (#191)

An artifact is an OUTPUT (an export's ZIP); a durable import needs the mirror — a durable INPUT. The uploaded export must outlive the request that received it so a re-claimed import job can re-read its source across a restart, so `POST /import` streams the upload to the **import staging store** (`libs/importStaging`, a subtree of `JOBS_DATA_DIR`, same filesystem-under-a-root shape and traversal guard as the artifact store) BEFORE it enqueues the job (`params.uploadRef`). Stage-then-enqueue: the row becomes claimable only once the file is fully on disk, so the runner never claims a job whose source is half-written. Cleanup is ROW-AWARE, not TTL: a staged upload lives exactly as long as its job is unfinished. The handler never removes it (a retry / reap-reclaim needs it); the maintenance tick's `onMaintenance` hook runs `sweepOrphans`, which drops a staged file whose job is terminal or gone (a crash before enqueue) — with an age grace over the µs window between staging a file and its enqueue row landing, so a live-but-slow import is never swept out from under itself. A space purge sweeps the staging subtree too.

A durable import may publish a second staged artifact beside its upload: its **plan** (#302, `<jobId>.import-plan`). A Markdown-tree import decides every destination and identity before it writes anything, and a re-claimed job must replay that decision rather than make a new one. The plan is written whole and fsynced; a usable peer plan is never clobbered, while a corrupt or incompatible pre-write sidecar may be atomically replaced only under the current job's lease fence. The run claims its destinations first, publishes under one claimed path's fence, reads the winner back, and only then writes notes. Every later claim adopts that winner. It shares the upload's row-aware lifetime (both are swept together once the job is terminal or gone), and its per-run temps are age-swept like an in-progress upload. Those temps are also the only part of the pair a backup skips: the PUBLISHED sidecar rides one exactly as the staged upload does, because the job row rides one too — an import restored without its source, or forced to re-derive a plan for notes it may already have written, would be a job nobody can finish. A missing or unreadable plan may be rebuilt only while the persisted `phase` is one of the few that PROVE the write gate never opened — an allowlist rather than a denylist of `writing`, because `done` is persisted before the runner records success and a crash in that window would otherwise let a fully written import plan itself again. Any other phase fails the job terminally instead of re-planning over notes it may already have written.

## A terminal failure may carry a result (#302)

`jobs.fail` is normally an error and nothing else. An import is the exception: a terminal plan conflict after N notes were written is deterministic (a retry re-reads the same bytes and reaches the same conflict), so it fails without retry — and the N notes it did write are real. Such a failure persists a bounded partial `ImportSummary` into the existing `result` column, so the client can show the error AND what happened. No schema migration is involved (`result` already exists), a RETRYABLE failure publishes none (there is no outcome yet, only an attempt), and an old row without one still parses.

## Capability degradation

The layer needs a meta-DB (the table lives there). A none-mode host (no meta-DB) has no runner and no async routes; the async export endpoints 404 and the client falls back to the synchronous streaming export (#17) — honest capability degradation, not a hard dependency, the same discipline as the rest of the stack.

## Wiring

The composition root (`apps/server/server.ts`) builds the artifact store, the import staging store and the runner when a meta-DB is present, wires the export AND import handlers (each resolving its job's space store through the `SpaceManager`, so a job reuses the exact same warm read-model), pushes progress out the per-space SSE bus (`auth.notifyJobChanged` → the named `job` event), hangs the staging orphan sweep off the runner's `onMaintenance` hook (one timer, not two), starts the runner once spaces are recorded, and stops it before the stores are torn down. The e2e fake wires the same real runner over an in-memory SQLite jobs facet, a tmp artifact store and a tmp staging store, so both the async export and durable import paths are exercised by production code, not a stub.
