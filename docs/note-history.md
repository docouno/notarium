# Note history: revision journal (#12) <a id="model"></a>

Versioning lives at the application level: an append-only revision journal in a second meta-DB table (the spike #9 decision — not a git layer over the catalog). The file remains the source of truth (P1); the journal accumulates states that passed through Notarium or were spotted by delta-sync, and that is its honest completeness boundary: the granularity of external revisions = the polling frequency (#61), edits between polls collapse into a single observed state.

## Model

A revision = a full snapshot of the note's state: `title` + `tags` + the custom `slug` + the normalized body (in the form `read()` returns it — the same form that versionToken hashes, so restore honestly passes through the CAS path #50). `slug` is a separate column (#124), not part of the body: the body is normalized WITHOUT frontmatter, so a custom `slug:` (#100 phase 1) would survive in the journal only as a structural field — otherwise restore (#79) would roll the note back to the `slug(title)` default and incoming `[[old-slug]]` links would re-ghost (aliases have a journal shadow — DISTINCT titles — the slug had none). `null` = no recorded custom slug (including pre-#124 rows — the column didn't exist then). On null, restore does not resurrect a custom slug: undelete from the trash (the note is recreated) yields the title default, whereas rolling back a live note LEAVES its current slug untouched (a rollback doesn't silently erase the slug — it isn't visible in the timeline diff). In addition, a revision carries the `charsAdded`/`charsRemoved` counters — the per-character cost of the edit against the chain-parent, computed once at append time (a word diff that accounts for whitespace, capped at 1 MB of total input → an honest null); timeline list queries never diff bodies. Bodies live in the content-addressed `revision_blobs` table keyed by sha-256 (storage addressing needs a real hash; the fnv64 of the version token does not qualify): restore round-trips, agent edit cycles, and identical notes don't spawn copies, and future retention/compaction operates on references. We don't store diffs — the derived is recoverable (P2).

The journal key is the internal note-id (P7), not the path: history survives move/rename. The `space` column has been there from day one (#16: a per-space audit falls out for free), as has `principal`: `ui` today, `agent:<token>` via gateway #21, `null` for external states — there is no one to sign them.

`kind`: `write` (a save through us) | `external` (a state spotted by delta-sync, or a pre-edit baseline) | `restore` (a rollback; `source_rev` stores the provenance) | `delete` (a tombstone with the last known hash — groundwork for undelete from the journal) | `merge` (reserved: the schema already carries both sides of a conflict, `base_rev`+`their_rev`, plus attribution — a manifest requirement; the merge flow itself is a future ladder P3/P6, not here).

The chain: `base_rev` = the note's latest revision at the moment of writing. The first journaled edit of an existing note first records the found state as a baseline `external` revision (the CAS verify-read is holding the body in hand anyway) — even the first edit has a "before".

`entry_role`: `origin` | `baseline` | `change` (#327) — WHAT the entry is in the note's life, decided by the writer at append and never inferred on read. `origin` = the note appeared through us; `baseline` = a synthetic pre-edit state or the first sighting of a note that already existed outside (real history, but not activity — counting it would double a pre-existing note's first edit); `change` = every later state. Before it, four consumers derived the same thing from `kind = 'external' AND base_rev IS NULL`, and quarantine (below) broke that approximation outright: with a contaminated past, a note's next ordinary edit has no trusted parent either, so it read as a first sighting and vanished from every Activity surface. The writer asks `hasAnyFor` — trusted AND quarantined — exactly once in a note's life, when there is no trusted latest at all. Quarantine does not change the role: it is a structural position, like `kind` and `createdAt`, not payload, so a gap keeps it and a contaminated baseline is still suppressed from `created`/`edited` while emitting as `unavailable`. Migration `0005` backfills the axis; rows written by an older process during a rolling upgrade carry the SQL default `change` permanently, which is accepted — see [meta-db](meta-db.md).

`integrity`: `trusted` | `quarantined` (#327). A cross-space id collision does not only mis-address rows, it CONTAMINATES chains: a revision's `base_rev`/`their_rev`/`source_rev` could point across a space boundary, so everything downstream of such a link was diffed, chained and attributed against state that never belonged to this note. Those rows are `quarantined` and served as **gaps**: the revision id, note, space, `kind` and time survive — which is what keeps cursors, totals, pages and session linkage exact — and everything that could attribute or reconstruct the state is withheld, with an additive `unavailableReason` on the wire. Nothing is invented in its place: no neutral author, no reconstructed parent, no alias. The taint belongs to the DEPENDENT row, never to a clean ancestor, and it flows downstream through EVERY space: an Alpha → Beta → Alpha chain quarantines the Beta row and the late Alpha row while the early clean Alpha row stays the trusted operational latest. Note-addressed reads are space-scoped for the same reason — the journal is shared across spaces, and a contaminated chain must not be readable through a sibling.

A gap is never operational state: `latestFor`/`latestForMany`, the trash collapse, `latestTimestamps` and the alias backfill all read trusted rows only, so a gap is never a chain parent, a tombstone, a restore source or a historical name. It IS history all the same — `hasAnyFor` counts it, so the write path does not invent a fresh "baseline" over a note whose past it cannot read. Sanitizing the row mapper is not enough on its own: every query classifies and filters on EFFECTIVE values (`revisionProjection`), because reading a raw `class` or `principal` to decide whether to SHOW a gap would leak exactly the metadata the gap withholds.

## How it's written

The journal is a core service (`services/revisionJournal`), and the hooks live in CachedStore (a single piece of code both over the notarium engine and over InMemoryStore in the e2e fake). The write is fire-and-forget with a per-note queue: the journal never fails a save; a lost append degrades history, not the note. Dedup by (sha-256, title, slug, tags) against the latest revision suppresses no-op saves and the echo of our own write coming back from the delta (reindex returns everything we write); the slug is in the key (#124), so an edit of ONLY the slug (for example, an external clear) is journaled too. The slug is mutable, so it is carried forward explicitly (like class/tags): `undefined` in the record = "not touched, inherit the previous", `null` = an explicit reset to the default, a string = a new custom slug. A delta upsert without a body is read in by a background read lane; only a read failure leaves a marker revision with `content_hash: null` — an explicit gap instead of a silent one. An external delete is journaled only after the frontmatter sweep: an external move (remove+add) resurrects the id and does NOT give birth to a false tombstone.

The write is fire-and-forget, but revision reads are read-after-write consistent (#238): before listing, `revisions(noteId)` drains the queue of EXACTLY this note (`journal.drain(noteId)`), so the provenance in `get_note`, the author of the memory category, and the timeline always see the latest record that has already returned — a human UI save is not surfaced as an agent edit even under cross-file parallel load. Set-oriented provenance surfaces use `latestForMany(space, noteIds)`: the journal drains exactly the requested note queues, then each persistence driver returns the newest row per note in one batch query (missing ids are omitted), never an N+1 loop. The hot write path is not touched by this (the save doesn't wait on the journal), and reads don't gate unrelated notes: draining an empty queue is O(1). Synchronicity is guaranteed by the fact that `journal.record` puts the append into the per-note chain SYNCHRONOUSLY, before returning from `write()` (that is, before the 200 response) — which means a read-time drain always catches this record.

Persistence is a meta-DB facet (`packages/server/src/services/metaDb`) over the shared checksummed SQLite/PostgreSQL schema specified in [meta-db.md](meta-db.md). Without meta-DB the journal runs over the in-memory driver — history for the lifetime of the process, the same honest degradation as identity (#51). In PostgreSQL the journal is the bottom of a wider lock hierarchy whose ONE normative statement is `packages/server/src/services/metaDb/drivers/pg/lockOrder.ts` — identity, then the reference facets, then the revision levels; this paragraph is a restatement of its tail, and the module wins on any disagreement (#327). Within that tail, append and purge take transaction-scoped advisory locks in a stable space-then-note-then-blob order (note purges start at the narrower note level): append shares the space lock with independent writes, while whole-space purge takes it exclusively before enumerating rows. High-cardinality note/blob keys map into a fixed set of sorted lock stripes, so a large purge has bounded lock cardinality. Replicas therefore cannot garbage-collect a shared CAS body while another replica is attaching a revision to it, without serializing all journal traffic in a space or exhausting the PostgreSQL lock table. A successful irreversible purge also leaves only a compact note/space fence behind; a delayed fire-and-forget append that lost the lock order is rejected instead of recreating history after deletion. **The note fence is scoped to the space that purged** (#327): note ids are globally unique now, but the journal is shared, and a fence keyed by id alone let one space's trash-emptying permanently silence a colliding id in another. Legacy fences written before that scoping carry an empty space and stay global — a purge already decided is not re-opened by a migration. During a rolling deployment the database insert trigger brings a writer without application-level revision locks into the same lock/fence gate, while a statement trigger rejects a purge writer that has not declared the fenced purge protocol. Existing replicas may keep serving ordinary appends; an unsafe irreversible purge is rejected and retried on a current replica.

## Wire and UI

The handles: `GET /api/note/revisions?id&offset&limit` (a window + an honest total — contract headroom, the UI loads 50 at a time), `GET /api/note/revision?id&revisionId` (the body; a revision is addressable only through its own note), `POST /api/note/restore {id, revisionId, versionToken}` — the server takes the body from the journal itself (the client cannot substitute content under a `restore` record) and writes through CAS: a stale token = the same 409 with a live note as on a save. The `createdAt` of revisions is a full ISO: the journal is the source of honest timestamps; since #54 the read-model derives the exact `modifiedAt` of notes from it (a bulk `latestTimestamps` at boot + a bump on a non-deduped external revision). A host without a journal (a bare engine without a read-model) answers 404 `revisions_unavailable` — capability honesty (`capabilities.revisions`).

The UI is a VSCode-style pair of panels whose state is held by `DocumentLayout` (both panels are its children, modeled on the edit-overlay): the **History** tab in the read-mode aside (next to Local graph) hosts `HistoryTimeline` — a timeline spanning the whole aside (the version name `vN` = the positional `total − index`, with a `name` seam for a future rename; who + the `+N −M` counters; the date on the right; rows fold on a narrow aside via a container query). Selecting a revision replaces the reader in the main column with `RevisionView`: a `core/StickyBar` bar (blur, the topbar's rhythm) with a Changes/Content toggle (`Segmented`) on the left and actions on the right — `Restore this version` (warning) / `Back to current` (primary); on the newest revision, instead of restore, a "This is the current version" marker. The diff is line-based: a gutter with the line numbers of the new state, changed lines marked only in the gutter (an accent stripe + number), and inside — word-level ins/del accounting for whitespace (`diffWordsWithSpace` — a pure-whitespace edit must be visible, since the counters counted it); a removed line break is shown as an inline glyph so the numbering doesn't lie; the logic is a pure `buildDiffRows`. The comparison base is the chain-parent (`base_rev`), not the adjacent row in the window. The restore row names its source "Restored from vN" (`source_rev`). Exits back to the current version: the button in the bar, Escape, a repeat click on the revision, leaving the tab/note/into the editor; in view mode the topbar's document actions (Edit, the kebab) are hidden — the bar owns the mode's actions. Both widgets are props-driven, and transport goes through a source port from the host (boundaries don't let widgets into services). Restore takes a fresh token immediately before writing, and core answers a restore only after the journal append (`journal.drain()` — an ordinary save stays fire-and-forget): the client's timeline refetch is guaranteed to see the "Restored" row, with no race against SSE. An SSE `changed` on the open note refreshes the timeline.

## Deliberate boundaries

- Retention: we keep everything; a manual purge through the trash (#79) erases the note's history + GC of blobs. Scheduled auto-retention is behind the durable job layer (#105).
- Timeline granularity in the UI: series of quick saves don't collapse visually (in the journal — all of them); a decision to be made based on actual usage.
- Delete does a read-before-delete (#79): the tombstone carries the final body (a blob in CAS) so the trash can resurrect the exact last state even for a note never once saved through us; a read failure degrades honestly — the tombstone stores the last known hash (or null = honest gap, not recoverable). The delete append is now awaited, not fire-and-forget: the tombstone = a record of the trash, and it must be visible before the 'changed' emit.
- The undelete flow exists (#79): the trash is a view over the journal (a note's latest revision = delete), restore resurrects from CAS while preserving the note-id, purge erases the rows + GC of blobs. The canon is docs/trash.md.
