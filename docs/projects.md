# Projects — model, identity, addressing

Canon on projects (#13, design research 2026-06-17). A project is the unit of work organization WITHIN a space (the space boundary is a separate canon, [docs/spaces.md](spaces.md)). This decision **refines #74-F3** (project as a lightweight optional entity instead of "not an entity"; the ADR amendment is in the data-model spike #74). The research rationale (industry + candidate models + folder-identity) is in the project/space/memory-model research behind #13.

> **Relation to the research (override).** This canon DELIBERATELY overrides the winner of the research synthesis (radical-simplify: project=path, no entity/registry). The `.notariummeta` marker answers the honest price of the synthesis (a durable handle that survives an EXTERNAL folder rename, which a pure address-split does not give); the fear "registry = #74-F1 anti-pattern" is removed by the registry being keyed on a stable `id` (not on the path), the `id` being NEVER used for authz (the marker is an untrusted claim, registry-wins-to-heal), and the marker being a sibling dotfile outside the reserved `.notarium/` namespace #78. There is no pre-MVP compat tax; the industry (GitLab/Jira/Linear) = an entity.

## Why (root of the defect)

At the outbound MCP edge (#21) the word "project" carried TWO ontologies at once: the isolation boundary (`space`) and the unit of work organization. `get_my_projects` returned whole spaces (`ProjectSlug = SpaceSlug`), the agent called spaces projects and could not scope into a real project inside a space. The root is the conflation of the isolation boundary with the unit of work. The fix is to split them into two different entities with two different addresses, rather than one overloaded term.

## Model

- **Space** — the isolation and security boundary (its own index/graph/search/tree/journal, an immutable slug, the membership anchor #10). An internal term, NOT exposed outward to the agent. Created at the host level. Unchanged (#16). One space holds many projects.
- **Project** — a LIGHTWEIGHT OPTIONAL entity: a marked folder subtree inside a space, with a stable identity and metadata. NOT a heavy-normalized entity, NOT a mandatory structure (content can live outside projects — a folder without a marker is just a folder).
- **Folder** — an ordinary tree node. It becomes a project when it receives a marker (an explicit human act). One project ↔ one subtree.
- **Memory** — the `agent-memory` class (#78), orthogonal to projects/spaces. Two axes: about the user (personal domain) and about the project (in the project's space). See "Memory".

`project` is now a real addressable unit; spaces stop being called "project" outward (inverting to "workspace" is not needed — real projects have appeared).

## Personal domain as a working space (#13, 2026-06-20)

The personal domain (`users.personal_space`, #21/#13) is a **full-fledged working space** that ALSO stores personal (about-user) memory and the profile. A solo user does not need to create a separate space to start working: in the personal one they can immediately mark folders/root as projects, write into them, and manage their about-project memory. This closes onboarding (even without separate spaces the agent easily saves notes into a marked project/root of the personal domain).

- **The personal space is the only landing (#99).** There is no more host-global "default" space (the legacy concept was removed): after registration a user has exactly one space — their personal one, no imposed `main`. `/` lands in `me.personalSpace`, otherwise in the first readable one from `/api/spaces`. `/api/config` returns only `capabilities` (the `defaultSpace` field is removed from the wire — the client knows the landing from `me` + `/api/spaces`).
- **Invariant 1 — the personal space is mandatory for every user, not lazily.** It is minted at EVERY account-issuance point: `setup` (owner), `accept-invite` (invitee) — eager, reliable on a mintable host; the lazy mint on the agent's first request remains a degradation safety net. Personal **ability authoring** admits the credential before using that net: an unrestricted human/write agent continues in the same request with the newly asserted owner grant, while a PAT/OAuth token narrowed to existing spaces is refused without minting an ability home outside its reach. Exceptions: the admin-CLI `createAdmin` (a recovery tool without access to SpaceManager — the lazy net) and hosts whose engine does not own namespaces (operator-static). Such a host may degrade ordinary Personal content to a readable Space, but it cannot safely do that for abilities: Personal and explicit Space packages share one physical root and have different runtime reach. Without a live pointer, Personal ability install is therefore advertised and returned as capability-unavailable before publication; no synthetic pointer/grant or ambiguous package is written.
- **Invariant 2 — the personal space is undeletable.** `SpaceManager.remove()` refuses if the slug is someone's personal (the `isPersonalSpace` predicate from auth). There is no space-deletion API yet — the guard is forward-looking for a future #69 delete flow.
- **The only difference from an ordinary space is the ban on invites.** You CANNOT add a second member to the personal domain: another principal with `space:read` would see the owner's private about-user memory and personal notes. The ban is enforced on the backend (`PUT /api/s/<slug>/members/<username>` → 403 if `isPersonalSpace`), not only in the UI (the Members tab is hidden in the personal domain's Management).
- **Projects in the personal one — as everywhere.** `markFolderAsProject` is uniform: the root (`folderPath:''`) and nested folders — one code path, no personal-specific behavior. The boot-scan scans the personal domain on par with the rest (markers are reconciled). `POST/GET/DELETE /api/s/<slug>/projects` and `…/projects/<id>/memory` work in the personal one without refusal.
- **Visibility in MCP.** `get_my_projects`/`whoami`/`start_session` list the marked projects in the personal domain (handle `(personal-slug, slug)`) — these are the principal's own projects, addressed like any other. The personal domain itself AS a space is not listed (it is implied from the PAT). About-user memory is still retrieved by a hint-less recall / the profile, lives in `.notarium/memory/` (subdir='', hidden from the index) — projects do not touch it.
- **UI.** The personal one is shown in the switcher as a separate item (a user glyph, outside `visibleSpaces`); its Management is visible with the single Projects tab (Members hidden).
- **History.** The former invariant "the personal domain NEVER has a row in `projects`" (#13 I0c) was reversed 2026-06-20 — it reflected treating the personal one as a "memory domain, not a workspace"; the product model was refined: personal = working space + memory, minus invites.

## Project identity — the marker file (pattern #51, lifted note→folder)

The central problem: if the project path is stored only in the meta-DB, an external folder move (git, file manager, another client) breaks the pointer. Notarium is file-first, external moves are real. The solution is to anchor identity IN THE FOLDER, exactly as #51 anchors a note's identity in its frontmatter.

- **The `.notariummeta` marker** — a structured file (JSON) inside the project folder. It stores the stable `id` (+ portable user fields). Identity rides with the folder on any move — ours OR external. The dot name is mandatory: `safeRelPath` fail-closes dot segments (the marker is unreachable by ordinary note/folder `/api/*` — engine-managed only), and `localFs.scan` skips dotfiles AND non-`.md` files (the marker is doubly excluded from the index #81, never a note). The marker CANNOT be `.md` (otherwise it would be indexed and stamped with a notarium-id). The marker is a **sibling dotfile at the folder root** (`<folder>/.notariummeta`), NOT under the `.notarium/` mount #78 → there is no namespace collision. An empty marked project is **invisible to the note index** (the marker is hidden from the scan), but visible in the tree via the **directory channel** (#97, below).

**Folders are first-class, directories are durable (#97 "never-prune").** The engine NO LONGER prunes emptied directories (`pruneUp` was removed): a folder is a self-standing organization primitive (file-first, like Obsidian), living until it is explicitly deleted. Therefore an empty project is held not by "a marker against rmdir" but by the engine simply not deleting directories. The tree is built not only from note paths: the **directory channel** (`KnowledgeStore.listDirs()` — a separate FS walk, dot-folders skipped, NOT mixed into the note `FileStat[]` → the invariant "index = notes only" #78 is intact) gives the server the real folders from disk. The server merges `listDirs() ∪ registry-project-paths` into the tree skeleton (`treeSummary`/`treeChildren`) → the tree is **server-authoritative**: empty projects AND neutral empty folders come in the skeleton, the client-side `withProjectFolders` crutch was removed (this eliminated the class of "two channels" — the duplicate on rename, P.2). A neutral empty folder ("New folder", `POST /api/s/<slug>/folders` → `makeDir`) is an ordinary directory without a marker: it has no identity, does not show up in `get_my_projects`. Deleting a folder — `DELETE /api/s/<slug>/folders` (`removeDir`: it removes notes with journaling + the subtree + markers in one act). Moving an empty project/folder no longer fails with `folder not found`: the engine asks disk for existence (`dirExists`), not the note index (P.3).
- **The derived `projects` registry in the meta-DB** — a cache (a sibling of the `spaces` table and the identity registry #51): `{id, space, path, slug, displayName, status, …}`. Rebuilt by a marker scan. **Per-request reads hit the cache, the marker on disk is NOT read on every request** (as in #51: frontmatter is not parsed on every lookup — the in-memory `identityRegistry` serves it). **The row key is the stable `id`, NEVER the path** (otherwise #74-F1 path-as-identity returns); `path` is a derived field of the id-row (the registry remembers which path owns the id — this is exactly what dedups a copy: registry-known-path = the original). Losing the `projects` table = a lossless rebuild by a marker scan (the #51 guarantee of soft degradation). Reading the registry and `get_my_projects` is scoped by space membership — the same anti-enumeration 404 as `/api/spaces` (#16): we do not reveal the names of projects in others' spaces.
- **Truth/derived split:** the marker is the source of truth for `id` and portable user fields; **on divergence the marker wins ONLY when its `id` is free or tombstoned** (external move → re-adopt); for a live-owned duplicate (a copy) the registry/owner wins, the marker's claim is parked until it is overwritten through us (exactly the registry's own claim algebra, #51: `adopted` vs `duplicate` — for notes that decision is now global, see [identity](core.md#identity)). The registry is a derived cache + operational fields (`path`, `space`, `lastSeen`). On a **change through us** — write-through (marker + cache immediately, the cache is always fresh). On an **external edit** — the cache is eventual-consistent until the next scan (model P2, the same as for notes; there is no watcher).
- **Reconciliation (I3 — implemented):** an internal move (#94) carries the marker with the folder automatically (a single `fs.rename` of the whole directory) + a write-through `projects.renamePrefix(space, old, new)` updates the `path` of every project row IN/UNDER the moved folder (a space-scoped prefix-UPDATE, `id`/`slug` immutable; best-effort — a successful move does not fail over a registry blip, it heals on the next boot). External changes (move/copy/delete past us) converge on the **boot reconcile** — cadence = **boot only + write-through on our moves** (model P2, eventual-until-scan, as for notes; there is NO periodic timer, we do NOT piggyback on the engine's note-scan — the marker scan lives in the server layer as a separate node:fs walk, the engine is untouched, the I0c decision). marker-hits = a **SEPARATE typed channel** (`{hits, complete}`), NEVER mixed into the note `FileStat[]` → the note index still does not see the marker (invariant; R2 is not entitled to merge the channels).
- **Gotchas (the marker = an untrusted claim, #51-idClaim; free/tombstoned `id` → re-adopt fail-open as in #51, contested/broken → fail-closed re-mint):** a folder copy → a duplicate `id` (registry-known-path = the original holds the id; the copy is dedup'd in the output — there is no row). **Re-minting a copy (Fork B) — on the FIRST write of ours that changes it; in I3 the real (reachable) trigger is ONE — an explicit marking of the copy (`POST /projects` → `markFolderAsProject` detects the owned-id → a fresh id+slug).** The other speculative triggers (`create_note` into the copy's subtree / moving the copy) are UNREACHABLE: the copy has no row → no handle → the agent does not address it, `/move-folder` edits only existing rows. `id` is form-validated before it is trusted (a NEW rule of the marker layer — #51-`idClaim` checks only for a non-empty string, here it is stricter); a deleted/broken/git-conflict marker → we treat the folder as unmarked, fail-closed re-mint (registry-wins-to-heal); **a readable-but-broken marker SUPPRESSES prune in the reconcile** (broken ≠ absent — otherwise one garbled byte would wipe a live row); nested markers → nearest-ancestor-wins for a note's derived project. `id` is NEVER used for authz (the space's arbiter is the registry + grants #10, not a file claim).

## Marker fields

Only **`id`** is mandatory (the stable portable identity). Everything else is optional, the parser is tolerant of unknown keys → new fields are additive, migrating old markers is not needed; the cache schema is extended in parallel.

- **v1:** `id` (mandatory) + `slug` (Fork A — our write-through always writes it, the durable handle rides with the folder) + `displayName`.
- **The first additive extensions:** `status` (active/archived — the archive lifecycle), `color`, description.

## Addressing

- **Handle = `(space, slug)`** — the GitLab `group/project` model. `slug` is unique WITHIN a space (uniqueness is enforced on marking a folder / writing the marker, R2); same-naming across spaces is resolved by the `space` field. Globally unique is the stable `id` (also the registry key). **`slug` is mutable (#100 phase 2)** — renaming retires the old slug into the project's alias history (a field in the marker + the registry's `aliases` column), and `space/<old-slug>` keeps resolving (id-first → current → alias, exactly the note model #100 phase 0/phase 1). The handle's durable promise is now held NOT by freezing the slug but by the alias resolve: renaming is safe (agent/AGENTS.md links do not break). Resolve `resolveProject`: the current slug is tried FIRST (`getByHandle`/`findBySlug`), on a miss — an alias pass (a registry scan, scoped to reachable spaces); **the collision rule current > alias** — a live current slug is never shadowed by someone's stale alias. The emitted form of the root still collapses to `<space>` (the root slug is not renamed here — it is the space slug, #100 phase 4).
- **The root project (path `''`) — the handle COLLAPSES to `<space>`** (#13 2026-06-20): the root project owns the whole space, and `<space>/<space>` (e.g. `main/main`) reads as redundant — the space slug already addresses it unambiguously. Therefore the EMITTED form (get_my_projects/whoami/start_session/three-state/UI) for the root = just `<space>` (`main`, not `main/main`; `root`, not `root/personal`). The full form `<space>/<slug>` STILL resolves (back-compat) — the resolver of a bare token equal to a reachable space with a marked root returns the root project (dedup with a slug match; a real collision with a same-named project of another space → the same ambiguous error). One builder `projectHandleOf` (server) = the single chokepoint for MCP and REST → the UI and the agent see ONE form. The collapse concerns only the handle; the `slug` in the registry/marker remains (for example `main`), `path=''` is the marker of the root.
- **`get_my_projects`** — a flat list of projects REACHABLE to the principal (filtered by space membership, as `/api/spaces`; anti-enumeration 404 — we do not reveal others'), **including projects marked in the personal domain** (a solo user works there, #13 2026-06-20). Each carries `space` as a disambiguator field. The agent addresses by the handle `(space, slug)`; the system resolves it to the stable `id`. The personal domain is not listed AS a space (it is implied from the PAT) — but projects marked in it are addressed by the handle `(personal-slug, slug)` like any other (the personal-slug in the handle is the principal's own slug, not a cross-principal leak).
- **Write:** the agent passes a project handle plus either a project-relative folder or an exact space-relative folder copied from `list_notes`; the server resolves both to `<space-root>/<project-path>/<relpath>` (`safeRelPath` remains an internal barrier). For a non-root project only, a two-segment prefix that the existing project resolver maps back to the selected project id is reserved: it is a likely duplicated handle and is rejected before dedup/write. Current names, resolvable project/space aliases, shadowing and ambiguity therefore follow the one handle resolver. Root projects skip this classifier because the two folder grammars collapse there. The handle only disambiguates the SPACE — the operation still sits on a **space-scoped route** (`/api/s/<slug>/…`); there is NO space-free project route (#16: "a route without a space does not exist"). The agent does NOT choose the space/class (poka-yoke).
- **Membership = scope, not access:** residing under a project folder determines ONLY the scope/derivation; the access decision stays `space_member` (#10), the project does NOT become a boundary.
- **Collision of same-named projects in different spaces:** two different entities (different `id`s), disambiguated by the `space` field (like a GitLab full-path). There is no collision in the UI in the steady state — the section shows the current space's projects, and within a space the `slug` is unique (enforced on marking). _(A transient window: a folder copy before re-mint carries a duplicate `id`+`slug`; the handle resolve and the `get_my_projects` dedup sort it out by registry-known-path until it heals — `lastSeen` is an operational marker, not a tiebreaker; details in §Reconcile.)_

## Lifecycle

- **Creation** — a HUMAN act (`POST /api/s/<slug>/projects` → writes the marker + the registry row; the UI "mark folder as project" / "New project" calls it). **Creating a space AUTO-MARKS its root as a project** (#97/P.5, 2026-06-20 — a reversal of the Q3 revision): the first-provision hook (`SpaceManager.onProvision`) marks `folderPath:''` EXACTLY ONCE — on the first registration of the space's row in the registry (a space mint OR the first-ever boot of a config space), NOT on a restart/recovery, so a later manual unmark is respected (on the next boot the root is NOT re-marked). ALL spaces are marked, **including the personal domain** (a solo user works in it — the auto-mark closes agent onboarding: there is always an addressable root project, `create_note(project:<space>)` works right away without manual marking). Honest-degradation: without a registry/marker-storage the hook is a no-op. **Impact on F3:** every note of a new space resolves to the root project (`project?`=`<space>` instead of "free"), BUT memory is NOT affected (about-user/about-project are derived from the mount `.notarium/memory/`, not nearest-ancestor) — only the cosmetics of the three-state user-doc change, the fundamental memory mechanics are intact. The agent does NOT create containers (it mirrors #16; Claude Code: the agent owns the content, the human — where it goes). The agent may write into an existing project; a write into an unknown project fails with a hint.
- **Directory ownership.** `New project` (`create:true`) materializes the fresh user-visible folder through the space store's ordinary `makeDir` mutation before publishing the project marker and registry row. This is the same directory channel as `New folder`, so the live read-model sees an empty project immediately and its first `index.md` can be saved without a restart/reconcile. `MarkerStore` is metadata-only: every marker write requires an existing directory and can never create or resurrect one. If marker/registry publication fails after `makeDir`, the residue is at most an ordinary empty folder, never a marker-only ghost.
- **Move** — we move the subtree; `id`/`slug` are stable (in the marker); the path in the registry is updated (a move does NOT rename the slug). **Rename (#100 phase 2)** — `PATCH /api/s/<slug>/projects/<id>` changes the `slug` and/or `displayName`; the old slug goes into alias history (the handle does not break — alias resolve). `displayName` is mutable including via re-mark.
- **Archive** — `status: archived` (the project stays addressable, drops out of the default-active lists) OR a move into `archive/`. The default exit (archive-not-delete).
- **Delete** — there is no agent delete of a CONTAINER (folder/project); **note delete → trash appeared in #102 phase 3** (the `delete_note` tool, the `note:delete` action, reversible via #79 — purge/restore stay with the human). Container reorg by the agent appeared in #102 phase 6 (move/rename, NOT delete): `move_folder`/`rename_folder` (a folder by `path`, `space:write`) and `rename_project` (a project handle/name, O(1) alias-write #100 phase 2) — the agent still has no destructive container-delete. A HUMAN deletes a folder via `DELETE /api/s/<slug>/folders` (#97 — notes are journaled, the subtree+markers are removed). An empty marked project = a legal state (a directory is durable, never-prune; the reversal of "no empty projects" is a consequence of the optional entity).
- **Sprawl control** — we gate the boundary (a space — host-only), not a predicate; the human owns containers; archive-not-delete. Rate-limit/guarded-agent-create are reserved (not v1).

## Memory (two axes)

- **About the user** — the `agent-memory` class in the **personal domain**, lives in the ONE personal space, not tied to the working one (the same regardless of which space you look at; NOT injected into every space). Shipped (#13 UI: Settings → Profile, Agents → Memory). `remember_about_user` writes here (poka-yoke).
- **About the project** — the `agent-memory` class, a physical **subdirectory inside the agent-mount** (`.notarium/memory/<project-id>/`, eager/lazy-per-subdirectory in the spirit of Letta-MemFS, #78) — **NOT a new index axis** (there is one index per space, the `class` column does not change, F2 "not an index-per-class" is intact) and NOT by residence under the notes folder (the class is derived from the dot-mount #78; residence under a user-visible folder gives `user-doc`). This is an agent-owned dot-namespace subdirectory, **not user folders** — the invariant "a flat agent-owned set" (#74 §7) is not violated (the layout is inside the mount, not a user reorganization). It introduces no new isolation axis. **Writing — in #13** (the `remember_about_project` tool, a direct write into the project's subdirectory). **READ-authz:** about-project READ — **space-membership-scoped** (#10, `/api/s/<slug>/projects/<id>/memory` — the project segment is mandatory, see §REST), NOT self:read (that is the about-user path `/api/me/memory`); the symmetry with `remember_about_user` is only in the write ergonomics, it breaks on read/authz. **Implemented (#13 I5):** the about-project READ axis — the endpoint `GET /api/s/<slug>/projects/<id>/memory` (§REST, a mirror of `/api/me/memory` via `listMemoryCategories(store, project.id)`) + the web-api binding `projectMemoryGet`. The shipped Memory explorer lives in the left sidebar: Personal is the stable first axis, active projects follow alphabetically, categories link to the standard note reader, and active-space SSE refreshes the project axes. The `consolidate` skill (reflection) is separate, not #13.
- **Audit ordering (#314).** The explorer has one global persisted order for Files, Favorites and both Memory axes. Memory REST defaults remain newest-write-first for old callers; `sort`/`dir` opt into the display order, and `order=eager` remains the context-constructor contract rather than a display mode.

**recall (agentRecall read).** **A project handle = a PURE project scope** (#13 I2, approved 2026-06-18 — it overrides the former "about-user memory always fans out"): resolve handle → the user-docs of the project's SUBTREE (`pathPrefix=project.path`) + the about-project memory of the subdirectory `.notarium/memory/<id>/`, and NOTHING from the personal domain. About-user memory is retrieved by a **recall WITHOUT a handle** (a fan-out over all reachable spaces, INCLUDING the personal one — the personal domain = its personal space `users.personal_space`, is in the accessible-set → **within-principal access**, #16: cross-space is permitted WITHIN one principal's set, not crossing the boundary) OR from the `start_session` profile. The reason for the pure scope: a project handle is a lens ONTO the project; mixing private personal notes/memory into the project context is unnecessary, and memory about the user is always in context anyway via the profile / hint-less recall.

## Init-context curation (#165) <a id="init-context-curation"></a>

The **Agents → Context** section — the constructor of what the agent sees when it starts working (`start_session`). Its base Personal/Project pin axes are file-first; reusable cross-space and role presets are user curation in the meta-DB and therefore degrade honestly when that capability is absent:

- **Pins (`always-load`).** Relevance = membership in the `always-load` tag (a boolean, not ordering), on TWO axes: personal (a reserved profile note + a scan of the personal domain → `profile.alwaysLoad`, always loaded; `pins[]` remains an editable list of user-doc pins) and **project** (a scan of the project subtree → `start_session(project).project.alwaysLoad`, loaded when working in the project). Pins are normally manual. The one lifecycle default is the exact project folder page: if `<project>/index.md` exists when the folder first becomes an active project, or is first saved while that project is active, that ordinary note receives the same-space tag. Marking never creates a missing page. Manual Unpin survives body edits and repeated idempotent marks; `unmark → mark` is a new lifecycle and pins an existing page again. A pin is bound to the note's PLACE: personal domain → the profile, the subtree of a marked project → the project bundle; a note outside both is pinned into nowhere (the action is hidden). The shared curation helpers (`weighAlwaysLoad` + `curatePersonalScope`/`curateProjectScope`, `server/.../spaces/agentContext.ts`) — for the MCP `start_session` (`curateAgentContext`) and the REST preview, so the human sees EXACTLY what the agent loads. The existing subtree rule remains: a folder-page pin loads that `index.md` note, not the folder contents.
- **Auto-pin failure boundary.** The page write / project mark is the primary lifecycle mutation; its auto-pin is a post-primary best-effort tag delta. If that delta fails, the server logs it and keeps the successful primary response instead of pretending the page/project failed or rolling it back. Repeating an idempotent mark does not retry the default; `unmark → mark` creates the next transition that may pin the existing page.
- **Memory mute (opt-out).** Memory is loaded by default; the human selectively MUTES a category — `muted: true` (the typed frontmatter channel `WriteInput.muted`, symmetric to `summary`; the engine writes/reads, the fake mirrors, the normalizer `isMutedFlag` reconciles the string `'true'` of the real engine and the boolean of the fake). **Mute silences memory on all AUTO-push surfaces where it reaches the agent BY ITSELF, without an explicit request (#207), not only in the eager profile.** These are: the personal eager profile (`curateAgentContext` excludes `muted` from the budget → `profile.memory` carries only loaded); `recall` (core: muted agent-memory is skipped in the bundle assembly — both personal and project, since project memory is NOT loaded eager, it is recall-on-demand); `start_session(project).knownValues.categories` (`buildKnownValues` filters `muted`). **A deliberate exception — the explicit pull channel `search`:** it indexes agent-memory precisely for dedup ("search before write", #102) and therefore does NOT filter muted — otherwise the agent would not find the muted category and would recreate a duplicate. The REST audit sees it the same way (`/api/me/memory`/`…/projects/<id>/memory` carry the `muted` flag) — the human finds and restores it. Not deletion — muting: the auto-context is clean, the explicit search/audit are honest.

**REST (the web goes not via MCP).** A read-model preview that does not call the MCP delta persistence at all: `GET /api/me/agent-context` (the personal scope) + `GET /api/s/<slug>/projects/<id>/agent-context` (the project scope + a read-only auto-index noteCount/folderCount, anti-enum 404 like the memory-twin). **ONE token budget per SCOPE, not per channel (#208):** the personal response carries `pins[]` AND `memory[]`, each with a server-derived `loaded` (pins are loaded first, then memory — a strict-prefix of what fits in `PERSONAL_TOKEN_BUDGET` `P`), plus `loadedTokens`/`budgetTokens`. The project response carries ONE budget `PROJECT_TOKEN_BUDGET` `Q`: first the project `pins[]` (the specific scope outweighs the general one), then **the personal background is embedded** into the remainder of `Q` — the `personal` block = the same `pins`+`memory`, but `loaded` is recomputed against `Q − projectLoaded` (in a tight project the personal one is squeezed harder); `projectLoadedTokens`/`loadedTokens`/`budgetTokens`. So `loaded ≤ budget` ALWAYS → the gauge will not show "budget free, but something trimmed". The curation (`curatePersonalScope`/`curateProjectScope`) is one async strict-prefix scan shared with `curateAgentContext`: set refs are resolved only as the scan reaches them, stop after the first token overflow or either safety cap, and never resume in a more general layer. Therefore the control panel == the agent's real load without a speculative full-set walk or client re-derivation. The measure per element: a pin = the BODY (`estimateTokens`), memory = the SUMMARY (`MemoryCategory.tokens`). An accessible carrier that is a folder page — a VISIBLE `user-doc` named `index.md`, not a hidden-class note that merely carries the name — is marked only in REST as `folderPage:true`, including when a loose pin or context-set item wins dedup; `start_session` keeps the unchanged `{noteId,title}` references. **Project memory is outside the eager budget Q (recall-on-demand, #207):** its nature is large pinpoint knowledge on a topic, not "always load"; if you want a specific project fact always → pin a note. The audit of project memory is still `…/projects/<id>/memory` (off-budget). `budgetTokens` — an echo of the server config (one source, the UI does not hard-code numbers; a per-project override — phase 2). The write channels are id-addressed (`note:write`): `PUT /api/note/pin` applies an exact tag delta under the note's mutation fence; `PUT /api/note/mute` remains the narrow whole-note meta edit. **A conscious MVP caveat:** the preview is under the CURRENT user, not under a specific PAT (#165 G); editable budgets P/Q (a balance for large/small models) → phase 2.

**Effective role layer (#308).** An optional owned role adds a third, most-specific context layer: `Role → Project → Personal` under the same `Q`, or `Role → Personal` under the same `P`. A role has no separate budget and carries no memory/delta/index channels; its preset is only pins, context sets, and their order. The strict-prefix scan and note-id dedup run once across all layers, so a role note wins over the same note in base context and a heavy role can squeeze later Project/Personal entries. Both preview endpoints accept `?role=<locator>` — the same opaque exact ability locator the Abilities routes use, never a name — return the bounded owned `roles[]` of the scopes in play, and include `role` **only when the agent would load that role here**, which is also the only case its layer is weighed into the budget. Because the locator already names one exact placement, nothing is re-resolved by precedence.

**Two doors, because a locator is asked two different questions.** "Which role does this address name, and may I configure it" is a question about the SPACE: a member who switched a shared role off for themselves still edits its shared context. "Does the agent load it here, and what does that cost" is a question about this reader, standing here, now. One response answering both is wrong whichever way it leans — answer identity only when the role is effective and the page that configures a shared role tells its own member the role does not exist; answer it always and the layer of a role the agent never loads is charged to the session budget, displacing a pin that IS loaded and reporting that pin as trimmed. So the preview above goes on mirroring the agent exactly, and identity is answered by `GET /api/me/agent-roles/<locator>/context` — `self:read`, optional `?project=<id>` (gated by `space:read` on that project's space, with the same 404 for an unknown id as for an unreadable one — the anti-enumeration rule the project preview keeps). It returns the role, its own editable layer, `active`, and when inactive a `inactive` reason of `disabled` (the viewer's own Enable/Disable bit), `out-of-reach` (this scope does not reach that placement, or a Space role is narrowed away from this project) or `unhealthy` (attachments that no longer resolve, which resume refuses). It makes **no budget claim at all**, and that is enforced by the wire shape rather than promised in prose: its pin rows carry no `loaded` and its role carries no `loadedTokens`. All three reasons leave the role EDITABLE; the client returns to the base context only on a 404, and shows the reason otherwise. `start_session` and `use_role` use that same placement and expose its loaded refs in `activeRole.context`/`context`, including on session resume. Late `use_role` also returns an authoritative replacement for the base profile/project slice from the earlier bootstrap, so role-first evictions are explicit and the caller does not append a second P/Q allowance.

### Context sets (#209) — reusable cross-space bundles

The `always-load` tag binds a pin to the note's PLACE (§above). #209 removes this restriction with TWO siblings, both reusing one cross-space mechanism (a `{space,noteId}` reference + honest per-reader degradation + a single scope budget):
- **A context set** — a NAMED reusable collection of references, attachable to a scope. Case: you assembled "Frontend conventions" from notes of the shared space `conventions`, attached it to projects in another space — both sessions get the notes; you edit the set in one place — it updated everywhere.
- **A cross-space loose pin** — ONE note pinned directly into a scope from another space (a set of one, without a name). Case: the space `conventions` is separate, a big project is in another space — you pin a specific convention right into the project's context, without a set wrapper.

The `always-load` tag remains for a same-space pin (a note in the scope's space); a loose pin / set — for cross-space (all coexist, dedup by noteId).

- **Ownership = a space.** A set LIVES in its home space; membership there = visibility/editing (reusing `space:read`/`space:write`). A personal set is attachable only to its owner's Personal scope or Personal role; a shared set — to Personal, Project, or any shared Space/Project role. The rule **ownership ≥ attachment**: a personal set cannot attach to a shared project/role — else `400`.
- **Storage = the meta-DB (NOT frontmatter — the first non-file-first axis of the constructor).** THREE reusable facets. `context_set_attachments`, `context_scope_pins`, and `context_order` accept `target_kind:personal|project|role`. Personal/Project targets use stable spaceId/projectId. A role target deterministically encodes its exact owned placement `(scope, stable owner id, immutable package id)`, so same-name Personal/Space/Project forks never share a preset, a rename never moves one, and role body/preset resolution cannot drift. Placement is part of that key, which is why promoting a project version to the Space base MOVES the rows instead of assuming they follow the package. The reference `{space,noteId}` remains authoritative by `noteId`. `purgeSpace` drops sets homed-here + facets whose `target_space` is purged. A dead reference degrades on resolve; a meta-DB-less host keeps the role instructions but has an empty preset.
- **Resolution = bounded curation + honest degradation.** `weighScopeContextSets` now returns raw membership plus one access reader; it does not open item bodies. `curatePersonalScope`/`curateProjectScope` build the single Role → Project → Personal group order first and resolve set refs sequentially inside that strict prefix. The first token overflow is the only extra known row; `SCOPE_ITEM_CAP` separately bounds successful survivors and total set-ref attempts. Any budget/item/resolve stop is hard: later pins, sets and memory stay unloaded. Per-reader access loss remains a neutral gap. Internal sets retain raw `itemsTotal`, processed `itemsLoaded`, first missing `itemsCursor`, `sourceIndex`, and explicit `trimmed`; dedup is still by authoritative note id and a losing raw ref counts loaded when its winner loaded elsewhere. The role identity editor is deliberately separate and keeps its historical full, unbudgeted layer.

Presentation belongs to `GET /api/s/<slug>/context-sets/<id>/items?offset&limit`, which slices raw membership first and then resolves at most that page; inaccessible/deleted rows retain `sourceIndex`/`noteId` and nullable title/space. Its caller-supplied space is a non-authoritative compatibility hint; production resolves the requested ids with bounded exact `IN`/`ANY` identity batches (never a whole-space inventory or 1000 prepared point statements), then access-checks each row, while persistence revalidates explicit settlement lineage transactionally. The route compacts the validated request directly into candidates/failures, persistence reuses original refs after canonical-id validation, and an event-loop boundary separates the transaction from wire projection/serialization. The existing single-add/remove/reorder, attachment and role-preset doors remain. Personal roles use `self:manage`; Space/Project winners additionally require `space:write`. Selecting a role never expands rights.
- **Order = load priority (#210).** `context_order` remains an overlay over heterogeneous pin/set membership, atomically replaced with dense ranks; an absent rank self-heals to the default tail. Each Role/Project/Personal layer keeps its own order, while the layers themselves are fixed by specificity (`Role → Project → Personal`) and cannot be interleaved. Within a layer, DnD order is budget priority. Items inside a set retain their shared set order. The base Personal/Project order endpoints and home-space set-item reorder remain unchanged; the role endpoint above writes the same facet.

### The address primitive `ProjectHandle`

`ProjectSlug = SpaceSlug` IS ABOLISHED (it was a separate primitive before #13; outward it is now `ProjectHandle`). The new primitive `ProjectHandle` — a handle string of the form `"<space-slug>/<project-slug>"` (full-path, the GitLab `group/project` model) OR a bare `"<project-slug>"` (allowed when the slug is unambiguous in the principal's reachable set). The segments are separated by `/`; the slug translit (#69) guarantees the absence of `/` inside a segment → parsing is safe. **Resolution on the server:** full-path → a direct `(space, slug)`; a bare slug → a search for the single project with this slug over the reachable spaces — on a collision a guiding error ("ambiguous project 'billing'; use 'space/billing'"), on absence/no-access — 404-semantics (anti-enumeration). **A bare token equal to a reachable SPACE with a marked root resolves to the root project** (#13 2026-06-20 — the root handle is collapsed to `<space>`): the candidates = slug matches ∪ the space root (dedup by id), >1 → the same ambiguous error. The emitted form of the root = `<space>`, but the full `<space>/<slug>` also resolves (back-compat). The resolve always ends with the stable `id` (the registry key) + a space-scoped route (`/api/s/<slug>/…`; there is NO space-free project route — #16). `get_my_projects` returns a READY `handle` — the agent copies it verbatim, does not construct strings (poka-yoke); the output `project?` on hits = the same `handle` (round-trip).

### The projects/folders registry in the meta-DB <a id="projects-folders-registry"></a>

The single `folders` table carries both projects and lazy ordinary-folder
identity. **A project = a row `type='project'`; an ordinary renamed folder gets
a lazy identity as `type='folder'`** (id + path history, without a project
handle or memory). The meta-DB exposes two typed accessors over it: `projects`
(filtered to projects) and `folders` (folder identity plus cross-type aliases).
`UNIQUE(space,slug)` is partial to projects; `UNIQUE(space,path)` is global.
`renamePrefix` moves both types. Marking a folder that already has identity
adopts that id and carries its path history forward. See drag-and-drop.md §8.6.

A derived cache (a sibling of `spaces`/`note_identity`); **the key = the stable `id`, NEVER the path** (otherwise #74-F1 path-as-identity). Per-request reads hit the cache, the marker is read ONLY on the scan (the #51 pattern). Losing the table = a lossless rebuild by a marker scan (P2 degradation).

```sql
CREATE TABLE folders (
  id TEXT PRIMARY KEY,
  space TEXT NOT NULL,
  path TEXT NOT NULL,
  slug TEXT NOT NULL,
  display_name TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'active',
  last_seen TEXT NOT NULL,
  created_at TEXT NOT NULL,
  aliases TEXT,
  type TEXT NOT NULL DEFAULT 'project',
  path_aliases TEXT
);
CREATE UNIQUE INDEX idx_folders_space_slug
  ON folders(space, slug) WHERE type = 'project';
CREATE UNIQUE INDEX idx_folders_space_path ON folders(space, path);
```

Both dialects use this shape. `created_at` is the first registry upsert, not
folder ctime; `last_seen` is refreshed by confirming scans. The personal domain
may contain project rows: projects there are first-class working projects.
Project queries filter `type='project'` and never exclude the personal space.
Minting writes the unique slug into the marker; handle resolution is membership
scoped, and note→project derivation selects the nearest project ancestor by
`(space,path)`.

> **Resolved model:** #13 made a project a stored `folders`-registry entity rather
> than a transient field on a note. Folder identity travels in its marker while a
> move remains space-scoped; gateway project listing reads the registry rather
> than projecting spaces as projects.

### Reconcile + the row lifecycle (Fork B = lazy; I3 IMPLEMENTED, cadence boot-only — 2026-06-18)

The marker-aware scan = net-new, **a separate server-layer node:fs walk** (does NOT piggyback on the engine's note-scan — the engine does not know about markers, the I0c decision; not a "shared walk"), **a separate typed channel `{hits, complete}`** (NOT mixed into the note `FileStat[]` — the invariant against index-poisoning). Cadence — **boot only + write-through on our moves** (model P2, eventual-until-scan; there is no periodic timer). Diff by `id`, per-space:

- **Internal move (#94):** carries the marker with the folder (`fs.rename` of the whole directory) + a write-through `projects.renamePrefix(space, old, new)` — a space-scoped prefix-UPDATE: it renames the row of the folder ITSELF AND of all nested project rows (`path = new || tail`, the offset via SQL `length()` = char-count, astral-safe; a boundary check so that `demo` does not catch `demofoo`); `id`/`slug` do not change under a move (the slug is renamed by a separate `PATCH`, #100 phase 2). Best-effort (catch+log): a successful move on disk+index does NOT fail over a registry blip, it heals on the next boot. (NOT an id-keyed single-row UPDATE and WITHOUT a staleness-guard — the actual form is a prefix-UPDATE.)
- **External MOVE** (the id-row exists, its `path` no longer carries the marker, the marker surfaced at a new path in the SAME space): an upsert by id → `path` is updated — re-adopt, fail-open as #51 tombstone.
- **A COPY in the SAME space** (the id-row exists, its `path` STILL carries the marker, and a SECOND path claims the same id): registry-known-path = the original holds the id; the copy = `duplicate`, the row is NOT inserted, it is dedup'd by registry-known-path (`last_seen` — an operational marker, not a tiebreaker). **Before re-mint** the notes are physically in the copy: their `filePath` is not under a registry row → the output `project?` absent (free notes), `space?` = the copy's space; nearest-ancestor does NOT match on the original — except when the copy is nested under another marked project (then that ancestor matches).
- **A COPY into ANOTHER space** (the same id-marker surfaced in a space different from the owner space): the row **NEVER migrates across the boundary** (#16) — the copy is row-less, the owner space holds the project. (`id` = PK → the row lives in exactly one space; the boot resolver checks the owner space-scoped, otherwise a cross-space claim would steal the row and it would ping-pong between spaces on every restart.) A true cross-space MOVE converges in ≤2 boots (the source space prunes, the destination space adopts the freed id).
- **PRUNE of an orphaned row** (the marker disappeared from outside — the folder/marker was deleted past us): on the boot reconcile a row whose `id` is not among the space's live markers is **deleted**. GUARD: only when the space scan is `complete` (fully readable — a partial scan = a lower bound, does not prune) AND all markers parsed (`parseOk` — a readable-but-broken marker hides an unknown id, the prune is suppressed; broken ≠ absent). A copy (a duplicate id) does NOT trigger the prune of the original (the original's id is among the live ones).
- **id free/broken/conflict** → the folder is treated as unmarked (fail-closed), there is no row until re-mint.
- **Re-mint of a copy (Fork B):** the FS scan does NOT mutate (it only dedups the output — no git-diff noise on a committed marker). The real reachable trigger in I3 = **an explicit marking of the copy** (`POST /projects`→`markFolderAsProject` detects the owned-id → a fresh `id`+`slug`, a suffix until uniqueness). `create_note`/moving the copy are UNREACHABLE (the copy has no handle). Mirrors #51's claim algebra.
- **Archive:** `status='archived'` (addressable, drops out of default-active) or a move into `archive/`. The handle resolve does NOT filter by `status` (an archived one is addressable); a write into an archived one is ALLOWED (archive = a list filter, not a write-lock); within-space the `slug` is unique regardless of `status` → there is no active-vs-archived collision on a bare resolve. **Delete:** not agent-side (C1); an empty marked project is legal (a directory is durable — #97 never-prune, the engine does not prune emptied folders).

### The `.notariummeta` marker — schema + parser (pin)

The format — **JSON** (a structural, tolerant machine-managed dotfile; not `.md` → not indexed / not stamped with a notarium-id; a dot name → unreachable by `safeRelPath`, excluded from `localFs.scan`). A sibling at the folder root (`<folder>/.notariummeta`), NOT under the `.notarium/` mount #78 (there is no namespace collision).

```jsonc
{
  "id": "Ab3xK9_qZ2mN",      // MANDATORY. 12 chars [A-Za-z0-9_-] (the freshNoteId scheme #51)
  "slug": "billing",          // opt. in the schema, but we ALWAYS write it (Fork A, 2026-06-18)
  "displayName": "Billing",  // opt. (v1)
  "status": "active",         // opt., additive (active | archived)
  "color": "#7c3aed"          // opt., additive
}
```
**`slug` in the marker (Fork A, approved 2026-06-18).** The slug rides IN the marker together with `id` — the durable handle `space/slug` then survives an external re-clone into an EMPTY meta-DB WITHOUT LOSS (rather than only a re-derive from displayName, which drifts on a rename or a collision-suffix — exactly the scenario for which the marker exists, R0b). The registry remains the arbiter of uniqueness: a slug collision is suffixed `-2/-3` in the registry on the MINT (registry-wins, as with a contested id); an explicit rename rejects a collision (409, does not suffix silently — #100 phase 2). The slug is optional in the SCHEMA (our write-through always writes it; a handwritten marker without a slug → it is derived). **The slug is mutable (#100 phase 2):** a rename writes the new slug into the marker + retires the old one into the marker's `aliases` field (the same Fork-A logic — the alias history rides with the folder, survives a re-clone). This closes the tension "loss of the table = a lossless rebuild" (projects.md §Identity): now it is honestly lossless, including the alias history. **The `aliases` parser:** an array of slug-form strings (like `slug`, invalid/duplicate ones are dropped); absent in pre-phase 2 markers (no migration needed — the field is additive). **boot reconcile:** the marker is the truth of slug+aliases (the slug is mutable → the marker-slug WINS over the registry row's old slug; the displaced registry slug is poured into aliases — heals an external edit of the marker).
**The parser:** tolerant of unknown keys (additive evolution — migrating old markers is not needed, the cache schema is extended in parallel); `id` is form-validated (a NEW rule of the marker layer — stricter than #51-`idClaim`, which only checks for non-emptiness); an invalid `slug` is DROPPED (re-derived, not trusted blindly); a broken JSON / no id / an invalid id → the folder is unmarked, fail-closed re-mint on the next project write through us. **Writing the marker — ONLY through a dedicated host-marker-owner** (`markerStore` over localFs, NOT the safeRelPath note routes; it writes the sibling dotfile past the note `write()` → no index, no journal, no identity — the marker is dot-named + non-`.md`, `localFs.scan` does not see it) + a mount-boundary guard (a replica of the class-poisoning-guard; a ban on ANY dot segment in folderPath → `.notarium/*` is unreachable). The marker scan — a **separate typed channel** (`MarkerHit[]`), a node:fs-walk of the host, skips dot directories.

**`MarkerStore.available()` answers for WRITES, and it is a runtime fact, not just a path one.** A marker is published into an *existing* folder through that folder's open directory inode, addressed as `/proc/self/fd/<fd>` — that is what stops a temp or a journal path from being rebound into a replacement folder when the public pathname is renamed mid-write. So the capability needs a local notes dir AND Linux AND a `/proc/self/fd` that actually re-enters the fd it names; the *existence* of the `/proc/self/fd` directory proves nothing, since a container can carry it without the dynamic per-fd entries. The store settles this once, at construction, by opening a directory fd and demanding that `dev`+`ino` match through both routes; any error, mismatch or missing entry fails closed.

**The host anchor is one of two prerequisites, and `available()` answers for both.** The other is storage: composition hands the store a factory that builds the file view a marker write needs — the current bytes plus a content compare-and-set — and a deployment whose adapter declares no `conditionalFileMutation` hands over nothing. `available()` is false when *either* is missing, and `write` refuses on the same two facts before it resolves a root or opens a folder. The factory is called per write, on the `/proc/self/fd/<fd>` of the directory just opened, never on the public pathname: a prebuilt bundle could not exist, because the root only comes into being once the fd does. This capability is otherwise **independent of the engine's atomic directory no-replace** ([note model](note-model.md#create-collisions)): the marker rides file CAS through the anchor, not `renameat2` on a directory, and neither implies the other.

Where the anchor is absent, marker-backed **writes** are honestly off: `available()` is false, so marking a folder as a project, renaming one and the space auto-mark refuse before touching the registry, and `write` itself throws `ENOTSUP` before it resolves a root or opens anything. Of those three only the first two are routes a client can hear from; the space auto-mark is a first-provision hook that simply skips (best-effort, P5). **Not every marker write sits behind that gate**, and the exceptions are the ones a user meets most often: minting a folder identity has no `available()` check ahead of it, so page creation, adding a favourite and both folder moves (REST `POST /move-folder` and MCP `reorg_folder`) surface the `ENOTSUP` as an *error* rather than as a refusal. That asymmetry is deliberate — gating those four is a separate contract change — but it is the whole of the difference between "refuses" and "fails" on such a host, so it is recorded here rather than left to be re-derived. Unmarking is the deliberate exception: dropping a marker is an ordinary portable `remove`, so it still succeeds — an anchor is what a *publication* needs, not a deletion. Only unmarking a space root whose marker also carries the `space` facet rewrites rather than removes, and that one is refused like any other write — but unlike mark and rename it has no route-level `available()` gate ahead of it, so the refusal reaches the client as an error rather than as a 404. The no-partial boundary holds either way: the write is the first step, so the registry is never touched. There is no portable fallback and never a write through a re-resolved public pathname. The **read side is untouched** — `read`, `folderExists` and `scan` are ordinary portable walks — and the boot reconcile deliberately does not consult write availability: it always scans, rebuilds every row it can, and keeps `complete === true` + a clean parse of every marker as the only licence to prune. A host that cannot publish a marker still restores its registry from the markers it can read.
