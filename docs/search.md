# Search: lexical + vector + hybrid + graph (#81)

Search in Notarium is hybrid: a lexical channel (SQLite FTS5) and a semantic one (vectors in `vec0`/sqlite-vec) are fused by rank-based RRF, with an optional third channel over the graph of wikilink connections. This is an **engine capability** (#69, P13), not an infrastructure dependency: no vector — honest degradation to FTS, everything still works. The vector index is fully derived (P2): rebuilt from files, a model/chunker change = drop+rebuild, not a migration. One index per space with a `class` column; class visibility is a read-model invariant (#78), the engine stays bare. Implemented in #81 (S0 of the search roadmap #53); the evolution stages are at the end.

## Model

One index per space: FTS5 + `vec0` side by side in the engine's derived DB (#69), a `class` column (#74/#78) — not an index-per-class. Agent memory lives in the same index (`class=agent-memory`), hidden by the visibility policy and reachable through `agentRecall`. The hybrid is **RRF** (k=60) over a shared note-rowid; channels: `fts` (bm25), `vec` (cosine KNN), `graph` (1-hop wikilink). Channel fusion is computed **in code (JS)**, not in a single SQL statement: SQL returns a pool with per-channel ranks, and the fusion `Σ wₖ/(k+rankₖ)` lives in `hybridSearch` — that is how the 3rd channel and its weights fit in. There is no external reranker (cross-encoder — #82).

The embedding key = **`content_hash(chunker output) × embedder_id × chunker_version`** (P13). This content hash is the vector invalidation arbiter. External-file reconciliation has a separate hash of the complete raw source (frontmatter included); mtime/size/change-token are only cheap prefilters. `embedder_id` (model@dtype + prefixes) and `chunker_version` are part of the index's identity: drift of any of them → wipe the partition + backfill. API embeddings are non-deterministic → identity is by inputs only, not by output.

The embedder sits behind the `libs/embedding` seam (swappable local↔API). The default is a local ONNX `bge-m3` q8 1024d (cloud-oriented; the compact tier e5-small 384d — #87); the runtime is transformers.js, and native deps load **lazily** (never in the engine's static import graph — otherwise the barrel takes down the server where they are absent). bge-m3 is symmetric (no prefixes); e5 is asymmetric (`query:`/`passage:`, baked into `embedder_id` — a forgotten prefix = silent degradation).

The chunker sits behind the `libs/chunking` seam, default **heading-first** (`heading-v1`): split by ATX headings (reusing `core listHeadings`), breadcrumbs `title › h2 › h3`, overlap, topping up small sections and window-splitting large ones; a **strict superset of whole-note** (a note without headings → exactly `title\n\nbody`). whole-note (`whole-v1`) is kept as an export + test, not the default. The chunk-id lives **only inside the engine** (the P1 boundary: on the wire — only note-id): chunks collapse into a note-id (`MIN(distance)`) BEFORE the RRF fusion with FTS and BEFORE the visibility postfilter.

Visibility is a **single CachedStore postfilter** (`isVisibleOn`, #78): the engine is bare (`capabilities.visibility=false`, returns the full population), and every hit from ANY channel carries `class`; the read-model is the sole chokepoint that hides classes by surface. A channel that returns a hit without `class` = a fail-open agent-memory leak (undefined class → user-doc → visible). `recall` (#21) keeps its own graph expansion (`planNeighbours`); the engine graph channel for it is turned off by the scope-gate — no double counting. `capabilities.vector/hybrid` are **fail-fast by fact** (vec_version() + loading the embedder), not hardcoded: vec0 registration did not fire / the model does not load → honestly false, degrade to FTS.

## How it is indexed (write-path)

Embedding is a **background serial queue**, deterministic from content_hash: the write does NOT wait (FTS is visible immediately, the vector catches up); `whenVectorsSettled()` for tests. The boot backfill (`enqueueMissingVectors`) tops up a fresh / wiped (embedder_id/chunker drift) / crash-interrupted index. `content_hash` is ALWAYS computed on upsert (sha256 of the chunker output, chunks joined by NUL — the arbiter == the embedder's input, not the raw title/body).

Multi-chunk crash-safety relies on the **`notes.embedded_hash` sentinel** (the commit-point as the LAST step of embedNote): the predicate "needs (re)embed" = `content_hash != embedded_hash`, and NOT "there is a vector with this hash" — a partial set after a crash all carries the current hash and the second predicate would deem it ready. Wiping the partition zeroes the sentinel. The rowid is recycled (notes keyed on `path` PK, not AUTOINCREMENT): the background embedNote **re-reads the row by rowid AFTER inference** and takes the fresh class — otherwise, over the multi-second inference window, a concurrent rescan/remove could reuse the rowid for a different note → a foreign vector + class (visibility leak). The engine's full-rescan fixes any notes→FTS5→vec0 desync (P2).

**Cooperative yielding to interactivity (#196/#284).** Embedding is CPU-heavy (ONNX on native threads + synchronous vec0 writes on the shared `node:sqlite` — the `async` wrapper is cosmetic, it blocks the loop). On a tight box (~2 cores) the initial boot/lazy-open backfill of a large database starves the event loop → search/navigation/health are unavailable for the entire indexing window (observed live on a 2681-note instance: ~3h, 220% CPU; latency returned to 0.8ms exactly when `pending→0`). #192 closed this ONLY for import (`beginBulk`→`suspendBackground`, hard-pause). #196 extends the approach to boot/lazy-open structurally: a **process-global `BackgroundScheduler`** (`packages/core/src/libs/backgroundScheduler`) — ONE per process, because cores/loop are shared across all spaces (space A's backfill must yield to space B's navigation — the symptom of #222). `runEmbedLoop` calls `await scheduler.awaitTurn()` before each note (subsuming the former per-note `setImmediate`); #284 puts graph enrichment through the same gate before Louvain and between force-layout batches. The turn is granted when in-flight interactive requests = 0 AND silence has held for `quietMs` (**quiet-window**), but no less often than `dripMs` under continuous load (**drip-floor**: convergence on a forever-busy instance + self-healing of a counter leak). The interactivity signal is fed by: the server request-lifecycle hooks (`onRequest` increment, release on close of the response stream `reply.raw 'close'` — the only signal that fires both on a normal finish and on a client-abort POST-with-body, which `onResponse`/`onRequestAbort` miss; long-lived SSE/import/export are marked `config.longLived` and excluded — otherwise a hanging SSE would hold the counter); the MCP handler (it hijacks the reply → counts itself); and the bulk import (it marks the SHARED scheduler → background work in OTHER spaces yields to the running import, which the per-space `suspendBackground` does not cover). `suspendBackground` remains the embedding hard-gate, the scheduler is the soft shared gate. Measurement (2 cores, e5-small, sustained load): interactive latency p50/p95 **148/163ms → ~0ms**; the price is that background throughput is throttled under load (structural throughput across cores = workers, #197). A host without the scheduler keeps the former local macrotask yields (an optional capability, not a hard dependency).

**Parallel embedding across cores (#197).** #196 made the backfill POLITE, but not FAST: inference + write ran serial on a single JS thread, the only parallelism being intra-op onnx (clamped by `EMBED_THREADS`=half-cores, so as not to choke HTTP) → out of N cores only ~2 were busy, and the initial init of a large database is measured in hours. #197 moves inference into a **`worker_threads` pool** (`libs/embedding/embedPool.ts`, implementing the `Embedder` seam): the pool is process-global (like the single embedder — one per process, handed out to all spaces), each worker holds its own ONNX session, `runEmbedLoop` launches up to `embedder.concurrency` (= the number of workers) `embedNote` SIMULTANEOUSLY (serial drain → drain with bounded concurrency; single embedder = concurrency 1 = the former behavior bit-for-bit). **Division of labor:** workers do ONLY inference (they receive chunk texts, return vectors via `transfer` — zero-copy), while the main thread persists ALL vec0 writes and ALL crash-safety invariants (`embedded_hash` sentinel, re-read-after-await, rowid-guard) UNCHANGED — a single writer, the partition-ownership hazard is removed (writing is ≤5% of wall, not the bottleneck — measured). The pool's `id` is built from the same options as the single embedder → swapping single↔pool does NOT invalidate the vector partition. **Priority by `EmbedKind`:** `query` (interactive read-path search) overtakes `passage` (background backfill) in the pool queue — the mapping is already in the seam. The #196 scheduler REMAINS: off-thread inference no longer starves the event loop by itself, but the workers still eat cores → the scheduler keeps the backfill yielding to interactivity (query-embed/nav/health in ANY space), reserving 1-2 cores for HTTP. Measurement (e5-small, 8 cores, real ONNX): main event-loop lag under backfill p50/p95 **463/1190ms → 0.2/3.7ms**, throughput **×2.9–3.2** (sublinear: e5-small is memory-bandwidth-bound; bge-m3 is more compute-heavy → scales closer to linear). The price is **K copies of the model in RAM** (K × ~570MB bge-m3 / ~120MB + runtime e5), so the default K is conservative (see levers). The worker file is a separate tsup entry `dist/embedWorker.js`, resolved via `import.meta.url` (prod `.js` / dev tsx `.ts`, probing both); native deps stay external. A dead worker is respawned, but **bounded**: under a sustained crash-loop (workers dying without progress) or pool exhaustion (the spawn-replacement failed) — backfill embeds honestly degrade to FTS (reject), rather than storming threads / hanging; on a spawn failure at STARTUP — fallback to the in-process single embedder. The worker wraps `createLocalOnnxEmbedder` (the same inference code) — two parallel paths are not maintained.

**Indexing indicator (#199).** The initial backfill runs for minutes/hours (#196), and without a signal this reads as a hang. Progress and mode are exposed outward through the same per-space channel as the rest of the read-model status — **snapshot + SSE `status`, no scan per request**. The engine puts cheap in-memory counters into `SyncStatus.engine.vector`: `mode` = `capabilities.vector` (honest degradation — vec0 does not load / the model does not come up → `'fts'`, the UI shows "Full-text only"), `pending` = `pendingEmbed.size` (the live queue: the boot scan `content_hash != embedded_hash` seeds it, upsert/embed keep it live), `total` = `noteCount` (the population; **done = total − pending**). The scan runs BEFORE the backfill (`ensureReady`), so in the head scenario (boot of a large database) `total` is accurate before the start, while `pending` melts toward 0. Liveness: the engine gives the read-model an `onIndexProgress` subscription (mirroring `watch` — present when `capabilities.vector`); the embed-loop pings it after every note, CachedStore **throttles** (trailing, `INDEX_PROGRESS_THROTTLE_MS`) and sends a fresh `status` frame — like `BULK_EMIT_COALESCE_MS` for `changed`, so the drain does not flood the wire. The client (`SyncProvider` → `widgets/SyncIndicator`) collapses this into a single working state `embedding` ("Building search index…", extinguished when `pending→0`) + a `Search` line in the details card (`Indexing done/total` during the backfill, otherwise the mode). Granularity is **per space** (matching the isolation of per-space SSE #16; its own embed-loop per .db). An important caveat: `total` (rescan-freshness) and `pending` (the live queue) are computed at different points, so a burst of appends between polls can briefly make `pending > total` — the client clamps the denominator, and the next poll brings total up. Not to be confused with the model cold-load (#193 q2): `vectorWarm` is a one-time read-path warmup, while this indicator is about write-path backfill.

**The read/reconcile path does not pull bodies and yields on graph derivation (#222).** The "space hang" spike confirmed: the "minutes" = precisely embedding starvation (#196/#197 — removed, measured live: under backfill on 2 cores / 202% CPU a cold entry into a neighboring space is 0.1s, health 2-3ms). But a SECOND layer surfaced, independent of the vector: the engine's read/reconcile path (`changes`/`list`/`graph`) — synchronous `node:sqlite` on the shared loop, O(corpus). Its graph derivation remains outside `BackgroundScheduler`: it is interactive prerequisite work, distinct from the deferred Louvain/force-layout enrichment gated by #284. Two structural fixes: **(1) projection.** The `changes()` inventory and `list()` select only the meta columns (`NOTE_META_COLS`), NOT `SELECT *` — `metaOf` does not read the body, and pulling it materialized the entire corpus on the hot path. The boot-seed (`cursor=null`) is now meta-only (zero bodies; this is what the client's `notesBarrier` waits for), while the polling delta fetches bodies in ONE atomic snapshot only for the changed rows (`CASE WHEN seq > ? THEN body ELSE '' END`) — a no-change poll no longer re-reads the entire corpus every 120s. `graph()` is the only read that actually needs bodies (wikilink derivation), and it selects meta + body. **(2) cooperative yielding of wikilink derivation.** `graph()` AND its search-channel twin `rebuildGraphAdjacency()` (the adjacency of the #81 Stage 4b graph channel — it runs on the search read-path: the first request waits synchronously, after any edit a background rebuild is kicked) parse EVERY body in a tight synchronous loop WITHOUT their own natural yield point → both are broken up by a time-budget-yield (`coopYielder`, ~8ms): a flat `setImmediate` macrotask, NOT `awaitBackgroundTurn` — both are called on interactive paths (`/api/graph`, the search graph channel), where a scheduler-defer would stall the very request being served. Measurement (2k notes): `rebuildGraphAdjacency` loop-block **94→40ms**, `graph()` (5k) **285→84ms**. The cold reindex (`doRescan`) deliberately did NOT get an explicit yield: it is already loop-friendly by construction — every changed file goes through `await mount.files.read()` (localfs = threadpool-I/O = macrotask), i.e. the reindex yields the loop between files and does not block it longer than a single `upsertRow` (measured: an explicit yield here moved the block <10ms — redundant). Measurement (harness, real engine, 5000 notes/15MB, loop-block = the maximum continuous synchronous block): `graph()` **285→84ms**, boot-seed **66→47ms**, poll(no-change) **72→49ms**, `list()` **63→34ms**; cold first-open — **wall ~17s unchanged** (the same reindex work, FS-I/O-bound), loop-block 70→42ms (that is the seed, not the reindex loop). Live (2 cores): during a 7.9s cold-boot of big, neighboring navigation held **≤62ms**. A deliberate caveat: `applyDelta`/`buildLinkIndex` (core-side, ~O(N) per poll) is NOT yielded — it is an atomic reconcile of the in-memory snapshot, and a yield point would let a concurrent write into the middle of mutating `this.notes`; the cost is small (~40ms once every 120s), the atomicity risk high — left deliberately.

**External edits converge even when size and mtime lie (#267).** The old rescan skipped a known file when `(mtime,size)` matched its indexed row. An editor, git checkout, sync client, restore tool, or coarse-timestamp filesystem can change bytes while preserving both values, so direct `read()` saw the new file but every derived surface (list metadata, FTS, vectors, graph) could stay stale forever. Reconciliation now has three layered signals, none trusted alone: **(1)** an exact watcher path is retained and force-read once on the next reconcile; **(2)** each adapter may return an opaque cheap `changeToken` with its stat (LocalFS uses `dev:inode:ctimeNs`, so in-place mtime restoration and atomic replacement are normally caught on the next poll); **(3)** a persisted rotating cursor source-verifies a bounded batch of otherwise unchanged files on every poll (default 64), so a missed/pathless watcher and an adapter with no useful token still converge across restarts. The final arbiter is a SHA-256 of the complete raw markdown, stored in the separate rowid-keyed `file_fingerprints` table; it is deliberately not the vector `content_hash`, whose input is normalized chunker output and can ignore frontmatter/whitespace that still changes FTS, graph, metadata, or file bytes. Every fingerprint is bound to the exact `notes.seq` materialization it describes, so an interleaved writer or a crash between the row update and fingerprint write can leave only an invalid/missing fingerprint, never a false match that hides stale derived data. Allocation of `seq` and its notes statement are serialized as one publication gate, so this monotonic cursor invariant also holds for genuinely async implementations of the SQL seam, not only the synchronous Node driver. Source verification triggered by watcher/token/sweep with unchanged stat metadata refreshes an equal hash/token without advancing `seq`; an ordinary mtime-changing touch still follows the existing upsert path because `modifiedAt` itself changed. A real source mismatch repairs FTS/list/graph and enqueues vector invalidation. The sweep cursor records bounded attempts rather than waiting for every read to succeed: one stat-visible but unreadable file is retried on a later rotation and cannot starve the rest of the corpus. A failed exact-path read also falls back to rotation after its one immediate attempt, so a burst of watcher errors cannot become an unbounded permanent retry workload. Selection comes directly from SQLite's ordered path index, and full-corpus reconciliation materializes only the cheap token; raw hashes are fetched for the bounded read candidates. With `N` indexed/stat-visible paths, batch `B`, and poll period `P`, a target that is readable on its selected attempt converges without a hint within `ceil(N/B) × P`; exact watcher/token hits remain next-reconcile fast. On a measured warm 5,000-file/15.1 MB corpus, a full source read+SHA was ~1.13 s versus ~0.24 s for stat-only, while both yielded between files (maximum loop gap 2–4 ms); bounded batches keep that I/O amortized.

## How it is searched (read-path)

`search()` is a **capability-dispatch**: `vecReady && embedder && vectorWarm` → hybrid, otherwise FTS-only (`score=-bm25rank`). The hybrid↔FTS switch is by capability, not by a `mode` flag. Degradation: query-embed fails/times out OR the RRF SQL fails → null → FTS for that query (never a 500). The only per-call lever is `SearchOptions.lexicalOnly` (#190): it forces the lexical channel (FTS-only), bypassing vector/graph. This is not a "quality mode" but a semantics choice for a **filter** surface: the Feed filter `?q=` wants term occurrence (population membership), not similarity — a vector neighbor without a shared token reads wrong in a "filter". Interactive quick-jump (Spotlight / the topbar OmniSearch) does not set the lever — there a ranked hybrid is needed. Search surfaces: **Spotlight/OmniSearch** = a ranked jump to a note (`/search`, hybrid); **Feed `?q=`** = a detailed filter over the corpus (lexical membership, composes with folders/tags/dates — `docs/feed-page.md`). The old Search rail panel was removed (#190).

`HYBRID_RRF_SQL` returns a **pool with per-channel ranks** (`fts_rnk`/`vec_rnk` + rowid/path/title/class/body_head/best_chunk), without pre-fusion — JS computes the 3-channel RRF. Per-chunk snippets: `+chunk_text` aux in vec0, RRF carries the text of the best chunk (the SQLite bare-column + `MIN(distance)` = argmin trick); snippet = `COALESCE(fts-snippet, chunk_text, body_head)` — a vec-only hit shows the matched fragment with a breadcrumb.

The `vectorWarm` gate + self-heal remove the cold-load cliff: the model loads lazily (seconds), its warmup is moved off the request-path (`warmup()` seam, fire-and-forget on boot); `vectorWarm` gates the hybrid branch → a cold/reloaded process answers from FTS INSTANTLY, without waiting for the load. The embedder does NOT cache a rejected load (retryable), and `search()` on a cold branch triggers warmup → a failed boot-warmup on a quiet (write-free) corpus self-heals on the next request, otherwise `capabilities.vector` would lie `true` while forever on FTS. `EMBED_QUERY_TIMEOUT_MS` is the secondary net.

## Graph channel (hub-robust 1-hop)

The third RRF channel is our differentiator (the wikilink graph, precedent HippoRAG). seeds = the top-S of the fused fts+vec; for each seed the 1-hop neighbors are taken from the adjacency cache, **excluding** global hubs (the `computeHubs` blacklist, the top fraction by degree) AND the seeds themselves (the graph = frontier expansion, not self-reinforcement); per-seed cap top-L; `strength = Σ seed.base × edge_weight`, `edge_weight = 1/√deg | 1/deg` (hub down-weighting). Neighbors outside the pool are fetched by the batch SQL `WHERE path IN(...)` WITH class (otherwise a fail-open leak). The adjacency cache is in the engine, reusing the canonical `core buildLinkIndex` + `deriveNoteEdges` (correct slug-resolution/ghosts/renames): a **background rebuild + last-good** (the first build is synchronous; a full-rebuild ~1.5s — NOT "cheap", as was thought; the per-edit cliff is removed), invalidation is a dirty flag on mutation. scope-gate: the channel is active only for `scope ∈ {undefined,'user'}` (/api/search); `recall` (`agentRecall`) is inert.

**Deploy default OFF** (`GRAPH_BOOST=on` opt-in; engine weight wGraph=0.5): the only available calibration showed that on a hub-heavy known-item corpus the graph **monotonically hurts** (neighbors = people / adjacent days, not the target; the target is the seed itself). Quality was proven on a synthetic fixture. Flipping the default — when a representative PKM corpus appears (#91).

## Resources, tiers, settings

Levers: **on/off** (`VECTOR_SEARCH`, budget everything→0, fall back to FTS) · **parallelism** (`EMBED_WORKERS` #197 — the size of the worker pool = the cores of backfill parallelism, default `max(1,min(cores−2,4))`: reserve 2 cores for HTTP + a cap of 4 bounds RAM, since each worker = its own model copy; cloud/a powerful box raises it) · **throttle** (`EMBED_THREADS` — now intra-op PER WORKER, default 1, so that K×T ≈ cores−reserve; it was half-cores for a single session — subsumed by the pool) · **model** (`EMBED_MODEL`, the main RAM lever: bge-m3 q8 ~570MB vs e5-small ~120MB/384d — multiplied by `EMBED_WORKERS`). The cooperative yielding of the backfill to interactivity (#196) is tuned by `BACKFILL_QUIET_MS` (the silence window before resuming the background, default 100) and `BACKFILL_DRIP_MS` (the progress floor under continuous load, default 1000) — higher quiet = more in favor of responsiveness on a tight box, lower drip = faster convergence on a forever-busy one. `EMBED_CPU_MEM_ARENA` — speed↔memory (on=fast, but the peak grows on heterogeneous shapes → OOM on a tight swapless box; off=flat ~1.9GB + a throughput penalty). Tiers (README): **off** (FTS) / **compact** (e5-small, homelab/a weak VPS) / **full** (bge-m3, cloud/powerful). **The published image is default-off** (opt-in — a homelabber should not be surprised by ~600MB RAM on the first boot); bare `npm run server` — on (the code default `?? 'on'`), while the dev-overlay (`make dev`) and the published image — off (#200).
Model choice is a **runtime** matter (lazy-download, one image, different env), not a separate build. The vector stack adds ~1.7GB to the image (onnxruntime-node 513MB, of which ~315MB is the unused CUDA provider; + transformers.js); the bge-m3 model ~600MB is downloaded into the container FS on the first embed (not in the image, ephemerally). A "lite" image without onnx/sqlite-vec for FTS-only homelab is optional #87.

**The vector stack as an optional install unit (#200).** The native stack (`onnxruntime`+`sqlite-vec`, ~660MB on disk, ~60% of node_modules) is moved into the deps-only carrier workspace `@notarium/engine-vector` (no code, like `@notarium/desktop`). The engine loads `@huggingface/transformers`/`sqlite-vec` **dynamically** (`import()` with a `string` specifier → not in the static graph even at typecheck; `createRequire` for vec0), and therefore does NOT declare them statically — the carrier holds the declaration. This gives a surgical omit: the default dev install (`make deps`) installs all workspaces EXCEPT the carrier → the stack is not downloaded; `make deps-vector` and the Docker image install fully, npm hoists the stack into the root node_modules, where the engine resolves it. `--omit=optional` does NOT work for this — it is blunt, it also mows down the toolchain's platform natives (esbuild/rollup/sharp/eslint-resolver). The `VECTOR_SEARCH` runtime switch is orthogonal to install: no stack → `on` honestly degrades to FTS; the dev-overlay defaults to `off` under a no-vector install.

**Future user settings = presets by GOAL/RESOURCE, NOT a model choice** (#87/#89). The user chooses "Balanced / Maximum quality / Light" — model/chunking/threads are hidden inside the preset; an "auto" mode by data shape + hardware is the intended direction. The fine knobs (a specific model/threads/pooling/prefixes) are the admin/operator level (#89, role-based). UX rule: **do not attach "best quality" to the big tier unconditionally** — "a bigger model ≠ automatically better search" (see below), it is more honest to say "for heterogeneous databases / powerful hardware".

## Quality and measurement methodology

The eval harness `scripts/eval-search.ts` is an offline measurement over a real corpus (it builds a one-off index, runs a gold set through `store.search()`), computing MRR@10 / recall@10 / **nDCG@10 (primary, BEIR)**; the channel is chosen by capability as in production. The gold is known-item paraphrases with low lexical overlap. The paired harness `scripts/search-bench.ts` measures the LATENCY of the read-path (not quality): it builds an index with a fake embedder (instant random vectors at the real number of chunks) and times a warm `store.search()` — bypassing the multi-hour real build, since the cost of vec0 KNN depends on the number of chunks × dim, not on the values (nailed down in #193).

**The main lesson (do not rediscover): search quality = model × chunking × data shape**, not the model alone. A big model with a long context (bge-m3, 8192) embeds the whole chunk at once → on long HOMOGENEOUS notes (diaries, chat logs) the distinctive fact dissolves in the noise of similar ones → weak discrimination at scale; a short-context model (e5, 512 tokens) truncates the chunk to the head and accidentally focuses on the distinctive part. Measurement on an adversarial corpus of long homogeneous digests: bge-m3 hybrid 0.0567 vs e5-small 0.245 (nDCG@10 0.067 vs 0.274), FTS 0/30 — BUT this is **mechanics-validation, the numbers do NOT transfer** to a real PKM (the corpus is adversarial/unrepresentative). The conclusion is not "bge-m3 is bad" but "bigger ≠ automatically better; it depends on the data".

Methodology: **~25–30 queries = a DIRECTION, not an authority** (leave-one-out, do not fit many weights); absolute weights and the ranking of models are fixed by numbers only on a **representative PKM corpus** (heterogeneous real notes + multi-relevant gold + a calibrated LLM judge) → **#91**. On synthetic / a single corpus — mechanics-validation (the mechanics work: hub suppression, no-regression, the vec channel 0→0.245). The bge family for dense retrieval uses CLS pooling — our embedder hardcodes `mean` (correct for e5, technically sub-optimal for bge; the gain from cls is minor, not the root of the failure); folding pooling into `embedder_id` is a tail of #87.

## Gotchas (non-obvious, verified live)

- **vec0 KNN** is forbidden under an external `ORDER BY` on another column → KNN as `... AS MATERIALIZED (… ORDER BY distance)` (the barrier keeps the constraint from leaking into the RRF sort). An empty vec0 table does not crash KNN (degradation while the vectors catch up).
- **vec0 `partition key` = poison for KNN (#193):** `note_rowid` was the partition key (so that a per-note delete would be a "cheap operation over a partition") → one tiny shard PER NOTE, and KNN without a partition filter pays per-partition overhead → latency grew with the number of **NOTES**, not chunks (measured: 2.1s vs 12ms flat on 2k notes, **~170×**; 116 notes → 0.19s vs 2675 notes → 2.5s — linear in the partitions; the one-core peg is vec0's C code, a shared root with #192). KNN **never used** the partition key (there is no filter on it), and a delete with it was also 3× SLOWER → ripped out, `note_rowid` is now a flat (filterable) metadata column. Lesson: a partition key is justified only if the query **filters** on it; otherwise it is a pure loss.
- **vec-layout version (#193):** the physical shape of the `note_vectors` DDL is versioned by a separate meta key `vec_layout_version` (alongside embedder_id/chunker/dims). A layout drift feeds the same wipe+backfill as a model drift — the index is derived (P2), a migration = a rebuild (the partition is dropped and re-embedded from files; FTS/notes survive). Latency measurement WITHOUT the 16h re-embed: a fake embedder (instant random 1024d at the real number of chunks) — the vector values do not affect KNN latency, only their number × dim.
- **FTS5 `snippet()`** cannot be used in a CTE/window and cannot be used with `rowid IN(...)` → snippets via a 2nd top-level pass (JOIN form), a rowid→snip map.
- **node:sqlite:** vec0 INTEGER columns (rowid / note_rowid metadata / aux integer) must be bound as **BigInt** (a JS number is sent as FLOAT → type mismatch); vectors are a `Uint8Array` over `Float32Array.buffer`. `enableLoadExtension` weakens the sandbox → load only the vec0.so bundle and immediately re-disable (#76, a second line of defense).
- **The cascade trigger `notes_vec_ad`** crashes ALL deletes/polls if a vec-ON index is reopened WITHOUT an embedder (VECTOR_SEARCH=off / degradation) → the else branch of ensureReady does `DROP TRIGGER IF EXISTS`.
- **onnxruntime arena:** the camelCase field `enableCpuMemArena` (the snake_case `enable_cpu_mem_arena` is silently ignored). The arena retains the peak on HETEROGENEOUS shapes (a uniform probe does not reproduce it — a plateau) → OOM on memory-tight without swap; off = flat, but slower.
- **Embedder multi-long-chunk OOM:** sending ALL chunks of a note in a single onnx call → a quadratic attention spike → SIGKILL; the fix = char-budget **sub-batching** (≤8192 chars AND ≤32 texts/call; an over-budget text goes alone).
- **capability lie:** `ready()` cached the REJECTED promise (`pipe ??= import(...)`) → a transient model-load failure poisoned the embedder until restart, `capabilities.vector` lied `true`; the fix = do not cache rejected (`.catch → pipe=null; throw`) + self-heal `warmUpVector`.
- **computeHubs zeroing the graph:** on a sparse/regular wiki the cutoff by descending degree == the minimum → the blacklist catches ALL → the channel is silently inert; the fix `if threshold ≤ minDegree → no hubs`. The hub denominator is the whole corpus, not connected-only. **Graph double-count:** mutually-linked seeds boosted each other → exclude the seeds as RECIPIENTS.
- **Dockerfile:** the base is glibc (node:24-slim) — onnxruntime/vec0 have no musl prebuilt; `COPY packages/engine-vector/package.json` before `npm ci` (the carrier vector-deps #200; otherwise the natives are not installed into the image). The image does a full `npm ci` (all workspaces), so the stack is present — `VECTOR_SEARCH=on` without a rebuild.
- **Measurement infra:** keep eval artifacts (gold sets, index DBs) out of the tree — they are large and disposable; a bge-m3 full-corpus build takes ~16.8h on a tight box (the arena-off throughput penalty + long chunks), so budget for it rather than re-running it per experiment; `pkill -f eval-search` catches its own shell too.

## Roadmap and deliberate boundaries

#81 (S0) is done in full: write-path → read-path → heading-chunking → graph-channel → the final sweep. Stages: **#82** lexical-advanced (FTS builds the match via AND over tokens → a long NL query = ∅: OR/bm25-tuning; cross-encoder rerank; chunking granularity — on homogeneous corpora it matters more than the model). **#83** external API embedders + privacy (data-egress — a high role-gate; atomic-swap of reindexing windows). **#84** scale: ANN (start brute-force, recall 1.00; HNSW when latency becomes the wall), pgvector-symmetry (the seam is laid into the contract, no code), retrieval isolation, per-embed/chunk-size tuning. **#87** model switch / presets / desktop profile (e5-small) / lite image. **#88/#89** the role model + admin pickers (config-precedence `meta-DB > ENV > default`). **#91** a representative corpus — unblocks at once the graph flip, the ranking of models/presets, and chunking tuning.

Deliberately NOT doing: `mode` in SearchOptions (switching by capability); ANN for now (brute-force gives recall 1.00, zero overhead); parallel partitions on a model change (atomic-swap → #83); the old FTS-only path as a separate branch (one path, capability-dispatch).
