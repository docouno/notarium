# Web UI Notarium (provisional)

> Web canon: component levels, state, styles, radius scale. **Provisional** — the web will be deeply reworked (migration to our own design-system library), so the structural details below are a snapshot of the current state, not a long-term contract. Code organization (tier/buckets/module form) is a separate canon outside `docs/`.

### Web (React)

- **Component levels:** `core/` (UI primitives) → `widgets/` (composites of core, local state) → `composers/` (business logic + data fetching) → `layouts/` (page scaffolding) → `pages/` (routing + composition). Dependencies are unidirectional: `pages → layouts, composers`; `layouts → composers, widgets, core`; `composers → widgets, core`; `widgets → core`. Only `composers/` fetch data.
- **Component** = PascalCase folder: `Component.tsx` + co-located `Component.module.scss` (CSS module, classes via `styles.foo`) + optional `types.ts`/`consts.ts` + `index.ts`. Dynamic class names — `styles[\`feed-grid-c${cols}\`]` (Vite `localsConvention: 'camelCase'` keeps both the kebab- and the camelCase key). Concatenating conditional classes — `cx()` from `libs/cx`.
- **Component body order:** `state/refs → derived (useMemo) → handlers → effects → JSX` — it reads top to bottom: what exists → what reacts → what renders. Within the «variables» zone the order is dictated by dependencies (a memo/callback is declared before whoever reads it). This is a guideline, not an ESLint rule. If a `state + effect + handler` bundle of a single concern resists zoning (reads worse when spread out) — that's a signal to **extract the concern into a hook** (domain → `composers/`, generic → `libs/hooks/`, e.g. `useDismiss`), rather than leaving it intermixed: after extraction the concern becomes a single «variable» line, and the order is restored.
- **State** — composer hooks + React Context providers (`useNotes`/`useEditing`/`useSearch`/`useChrome`/`useFeed`/`useAgentsExplorer`), without prop-drilling and without external store dependencies. Providers are `composers/`-level modules (this is exactly «business logic + data fetching»). `AgentsExplorerProvider` sits above both Sidebar and routed content: it owns the four Agents datasets, typed invalidation and per-owner/Space natural/manual state. `AgentsChrome` owns the single Agents `PageFrame`, top pills and local rail; routed list/detail surfaces fill its slots instead of nesting another frame.
- **The right aside is one global, user-controlled secondary surface.** `ChromeProvider.asideOpen` is the only open/closed state across document and Agents routes: entering a page, starting Edit, saving or switching sections never opens or closes it implicitly. A routed surface supplies panels to the shared shell; it does not invent another fixed `<aside>`, width, collapse rule or mobile behavior. Read mode renders current values only; editable controls appear only in Edit/New. The collapsed toggle is separated from page actions by the shared `TopbarActionSeparator`; narrow mode uses the shared modal/inert/focus contract.
- **One role is one card.** A Role's project version is that role's override, not a second role, so the library and the Explorer show the base and hang its versions off the footer; a card whose own placement is a project is a role that never had a base, and simply names that project — the Explorer, the card and the aside all name a Space and a project the way the user named them, never the internal word for the slot. A narrowed reach earns a chip (`2 of 5 projects`); `all projects` is what a Space role always meant and says nothing extra. `Add version` (a submenu of the projects that do not have one yet) is a kebab action because it CREATES something; where an ability belongs is a property of it and is edited.
- **Where an ability belongs is ONE question, and it is a field.** `Belongs to` asks it the same way when creating and when editing, through one segmented control: `Personal`, the Space by its own NAME (never "this space", which stops being true the moment an ability can live in more than one), or `Projects` — these projects and no others, chosen from one list under it. `Space` means the whole Space: every project it has and every project it will have. The Catalog Add dialog reuses the primitive but not the question — it offers two options in generic words (`Personal` and, for a Role, `Project`; for a Skill, `Space`), because an Add picks a destination for a copy, not the reach of something you are authoring. Catalog targets fail closed against `installAvailability`: a missing field or key is unavailable; a Role's project selector contains only installable projects in the destination Space, while a Skill's shared destination requires both the current writable Space and that Space's availability answer. When at least one target is installable, the dialog defaults to Personal if possible and otherwise to the shared destination; a Role also selects its first installable project. With no installable target it explains the storage prerequisite, disables Add and leaves the Catalog readable. The two destination-kind segments remain visible but disabled when unavailable; unavailable concrete Role projects are omitted. There is no second list under either answer, because there was never a second question — an ability’s placement and its reach are the same fact, and a Role and a Skill answer it identically. Where the package ends up living is never asked about: covering more than one project is something only a Space home can do, so a project-placed Role given a wider answer relocates, silently, inside the document’s one Save. An OVERRIDE is deliberately not expressed here — "this project needs a different text" is `Add version` and the `Versions`/`Overrides` links, a relation between two bodies rather than a place. In the authoring field, an option that cannot be taken stays VISIBLE and disabled with its reason on hover, rather than dropped: Personal ↔ Space (a different space, which the note engine cannot move between) and a Role that overrides a Space one (the name above it is taken). The neighbouring `Overrides`/`Versions` fields explain those cases and link both ways: a version has no card of its own.
- **Role/Skill authoring follows the document model.** The leading authored `# H1` is the one human title in cards, Explorer, breadcrumbs, Context and detail; the main column is only the document editor. `name` is a stable generated package key and is not a second user-facing title field. The optional short description and placement/availability controls live in the aside. Role attachments are grouped checkbox rows; answering `Projects` opens one flat checkbox list of that Space's projects, Role and Skill alike, with no `All projects` row above it — `Belongs to` already asked that, and a second control for one answer is the shape this field exists to avoid. The Catalog Add dialog, which has no such segment, does carry an `All projects` switch over its own list, and neither surface offers an Add-button pile. A Role at a project placement names the project it belongs to and, when a base of that name exists, what it overrides: the body differs from that base, and nothing else on screen would explain why. A read page reconstructs one heading from the projection and never repeats it inside the rendered instructions.
- **Ability cards and actions use one visual language.** A homogeneous Roles/Skills grid does not repeat the same entity glyph on every card: the leading slot is a filled green enabled or gray disabled status dot, while scope/provenance stays in the footer. Writable Owned cards add `Edit` to the standard kebab. Labels are the unqualified `Edit`, `Configure context`, `Add version`, `Enable|Disable`, `Add`, and `Delete`; only Owned Roles configure context, System is preference-only, and Catalog only adds.
- **A section owns one vertical rhythm, and a nested document does not restate it.** A document opened INSIDE a section (an Ability, an agent-memory note) sits in the section's own inset: `SettingsLayout` drops the standalone `.doc` top padding for everything it hosts, as one rule — a page that fixes its own `padding-top` fixes only itself and lets the neighbouring route of the same section drift. The document heading is the shared global `.doc-title`, so a reader that renders its title through `.markdown h1` instead is a defect, not a variant.
- **The aside body is `core/AsidePanel`.** Reading metadata, editor metadata and instance settings are the same shape — a column of labelled fields — so they share one primitive instead of each carrying a private `label over value` block. A new control that more than one panel needs becomes a `core/` component (`core/Textarea`), not a class copied into the next page module.
- **One save per screen.** A surface that has a Save commits everything it edits through that Save, including settings that travel on their own endpoint; a second per-setting apply button is a second model of when work is durable. Genuinely operational one-shot actions (Enable/Disable, Delete, Add) live in the standard kebab and are not fields.
- **Every section shows its OWN explorer, scoped the way that section resolves.** The left panel is the section's dataset, not a global tree: Files shows files, Agents shows Roles/Skills/Memory/Sessions. A dataset that resolves per Space is listed per the ACTIVE Space (with the cross-space Personal placement alongside), because a list that mixes in Spaces whose entries cannot win the current resolution is showing state that does not apply; reaching the rest is the global library's job. Owner-global datasets (Sessions) are the exception and say so.
- **Routing** — react-router (data router, library mode). The router is a swappable edge, like the HTTP framework on the backend (P9): it owns URL↔pages, `Link`, and the navigation blocker of the unsaved-guard; data lives in providers, and we don't use the router's loaders/actions.
- **Hooks:** domain hooks/providers — `composers/`; generic hooks with no domain (panel sizes and the like) — `libs/hooks/`. `libs/` in web is a uniform layer of directory-groups (`hooks/`, `routing/`, `markdown/`, …), with modules inside the groups.
- **API services** — naming `{resource}{Action}` (`notesGet`, `noteSave`), typed by the contract.
- **Errors and states — each has its own owner and its own primitive (#65), not one global banner.** Transient feedback for an action (a mutation/save error; future success confirmations) → toasts `useToast()` (`core/Toast`). The state of a whole area (no note / engine unavailable / unknown URL / crash) → `core/StateView` (tone `muted`/`error`). An inline plate within a form/panel flow → `core/Notice`. A modal that requires a decision → `useDialog()`. A render crash is caught by `core/ErrorBoundary` (outermost in `main.tsx` + around `<Outlet/>`, `resetKey`=pathname). A provider's error channels are **scoped by concern** (`listError` for the list, `noteError` for the reader); we don't dump them into a single `error` that «rides» across pages. A machine-readable transport signal (`ApiError.status/reason`) is the basis for choosing the state, not the raw `.message`.
- **Boot without flicker (#65):** the state visible on the first frame is **seeded from the URL synchronously** (`parseAppPath` → initial `mode`/`activeId`/`nav`), rather than flipped by an effect after loading. Independent loads (the sidebar tree / the note reader) run **in parallel**, not serialized. During loading — skeletons in the shape of their target (`core/Skeleton`), not a default/empty screen.
- **State that survives navigation has a URL identity — not only ephemeral component state (#65/#309).** An open note = `/n/<id>`; a generic new-note draft = a URL query (`?new&title&dir&link`) which the seed effect expands on landing. A new Role/Skill has a routed UUID plus an owner-bound, versioned `sessionStorage` payload because its multi-field body must survive reload without leaking across principals. In both cases Back/Forward/reload return to the same document identity; opaque authored bytes need not be stuffed into the URL.
- **Prop forwarding: `{...rest}` comes FIRST**, the component's own props come after (and therefore win). This guards against hidden overrides: the caller cannot accidentally clobber a `type`/`aria-*`/handler that the component owns. Props with **merge semantics** (`className`, `style`, shared handlers) must not be left «to ordering» — we destructure them and concatenate explicitly (`cx(...)`/composition), otherwise rest-first would silently discard the caller's value. Overridable-with-a-default (`type = 'button'`) is set as a default in the destructuring, not by spread order.

### Styles: modules + a thin global layer

- **Co-located CSS modules** (`Component.module.scss`) — the default: a class belongs to a single component → its module. Names in SCSS stay kebab (readable), access from TS — `styles.fooBar`.
- **The global layer — `web/src/styles/`** (imported once in `main.tsx`), only what is global by its nature:
  - `tokens.scss` — the theme as CSS custom properties (`:root`/`[data-theme=dark]`): runtime switching of theme and accent (#1). `$`-SCSS vars — only for non-runtime tokens (breakpoints #26, typography #27).
  - `base.scss` — reset, `body`/`#root`, the `.app` scaffold, scrollbars, `.cm-host` (CodeMirror renders its own `.cm-*` DOM inside).
  - `markdown.scss` — `.markdown` + descendants: HTML from `marked` (via `dangerouslySetInnerHTML`), the class names can't be hashed → global.
  - `shared.scss` — a small set of cross-cutting utility/scaffold classes used by ≥2 components and not worth a component of their own (`.doc`, `.main`, `.loading`, `.gf-section`). An explicit shared layer, not a «dumping ground». Tree states (loading/empty/error) — not here: their single skin is `widgets/TreeState` + `core/EmptyState`/`core/Skeleton`/`core/Notice` (#220).
- **Truly shared primitives are components, not classes:** a button → `core/Button` (variant/icon/active), a stat tile → `core/MiniStat`. We don't smear duplicate classes (`.btn`, `.mini-stat`) across consumers.
- **We keep out of modules only what owns the class name from outside:** `.cm-*` (CodeMirror), the output of `marked`. The tree's DnD highlight (`dragging`/`drop-target`/…) is the `Sidebar` module: JSX attaches the classes, not `libs/dnd`, so they can be hashed.
- **Domain and wire — camelCase; engine dialects stay in the drivers.** The core domain (`packages/core/src/knowledgeStore/knowledgeStore.ts`) is self-contained and does not import the contract; the `/api/*` wire from contract v2 (#54) speaks the domain's language: camelCase, note-id as the only note reference, ISO instants (`toISOString` form; null = the engine honestly doesn't know), `space` instead of `project`. _(#13 brought `project` back onto the wire as an in-space entity handle `(space, slug)` — see «Outward terminology» below; `space` remains an internal boundary and is not exposed outward.)_ Engine dialects (permalink, snake-payload, date-only, etc.) don't escape `engine-*` — the driver normalizes them at its own edge. The mappers at the boundaries remain as thin shape guards: transport — `packages/server/src/apps/server/routes/wire.ts` (selects exactly the contract's fields, nothing internal leaks «by accident»), client — view mappers in `packages/web/src/libs/` (the view types are structurally independent of the zod inference). A substantive divergence of shapes is a contract review, not a mapper's.

#### Radius scale (#230)

Corner rounding — **a single radius language on a token scale in `tokens.scss`** (`:root`), not per-component hardcoding. A component references a token, never `px` — the entire product geometry turns on a single engine. A hardcoded `border-radius: <N>px` in modules is a code smell that goes to review.

| Token | px | Purpose |
|---|---|---|
| `--radius-xs` | 4 | small details INSIDE a control: swatch, icon-buttons ≤24px, checkbox, inline-code, skeletons |
| `--radius-sm` | 6 | compact controls: buttons, nav rows, menu items, inputs, chip-as-plate, badges — the «everyday» radius |
| `--radius-md` | 8 | containers and medium slabs: cards, popovers, dropdowns, code blocks, toasts — **the base** (formerly `--radius`) |
| `--radius-lg` | 12 | large surfaces: modals, the auth card, drop zones, the splash glyph — the roundest rectangle in the UI |
| `--radius-pill` | 999 | full capsules: pill chips, counter badges |

A compound radius (a block's corners) — the same tokens: `0 var(--radius-sm) var(--radius-sm) 0`.

**Off the scale (deliberately left hardcoded):** `50%` circles (avatars/dots/thumbs), the tracks of `Switch`/`Slider` (functional `999px` capsules — they must stay full regardless of the pill token's value), `~2px` indicator strips (tab underlines, the diff/heatmap micro-rounding), and `inherit`/`0` (inheritance/reset) — these aren't slabs. The «too round» threshold: a rectangular slab is no rounder than `--radius-lg` (12px); capsule shape — only deliberately via `--radius-pill`.
